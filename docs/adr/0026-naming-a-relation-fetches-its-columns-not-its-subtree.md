# Naming a relation fetches its columns, not its subtree

**Withdrawn by [ADR-0043](0043-bare-read-and-one-hop-become-the-orms-not-ours.md):** Prisma 8's `.include(rel)` stops at that relation natively, so this rule is the ORM's rather than ours. The `CONTEXT.md` term **One hop** survives with one break recorded in ADR-0043 — `.include()` reaches a one-to-one only from the FK-holding side, so the non-FK side is refused at generation. The depth cap's justification moves to ADR-0043; the cycle guard's re-pointing moves to ADR-0025.

ADR-0024 stopped a read with no `include` from fetching relations, but only at the root: a relation the caller named _bare_ still expanded its entire access-scoped subtree beneath it, down to the read-include depth cap. We decided the rule applies at every level — **naming a relation fetches that relation's own columns, and nothing further** — so an include describes the tree it returns, one hop at a time, however deep the caller goes. The Access Filter then walks only the branches the caller named, rather than walking every relationship of every list and reconciling the result against the request afterwards.

The waste this removes is not marginal. Measured against the real merge path on a seven-list graph, a read naming one relation and none of its subtree evaluated operation-level `query` access on **all six** related lists — three of them on a branch the caller never named, whose computed scope was then discarded — and sent an include three levels deeper than anything requested. Where an access function touches the database, those are wasted queries on every read, and this is the same cost profile that made #848 worth filing.

It also finishes making the read API coherent. ADR-0024's own case against the old default was that three read paths returned three different shapes, "differing by privilege rather than by anything the caller wrote". Leaving the expansion alive one hop down reproduces that fault on a different axis: naming nothing would get you nothing, while naming one relation would get you its whole subtree. Either the rule holds at every level or it is not a rule.

**This is a silent break, of the same class and for the same reason as ADR-0024's.** A read passing `include: { lineItems: true }` and reading `lineItems[0].product` gets no `product` key, no error, just less data. Its blast radius is narrower — it reaches only reads that already pass an `include` _and_ rely on nested data they did not name — but the migration note leads with detection, as ADR-0024's did: find caller includes whose consumers walk past the named relation. We ship it as a minor while the package is pre-1.0, on the same population argument ADR-0024 used.

## Considered Options

- **Skip access evaluation on unnamed sibling branches, but keep expanding a named relation's subtree**: the non-breaking half, and rejected. It removes the wasted access calls without changing any returned data, but it relocates ADR-0024's incoherence instead of fixing it — a read's shape would still depend on depth rather than on what was written — and it earns none of the simplifications that motivate the change, because the unbounded walk remains on the path.
- **Ship the break behind a warned deprecation window** — one release where an include that would lose a subtree logs the relations about to stop arriving, then the break. Genuinely attractive, because unlike ADR-0024's break this one _is_ detectable at the call site: the engine holds the caller's include and knows exactly what it is about to stop returning. Rejected on population grounds — every release before the break lands adds consumers written against the old shape — and because it means keeping the full walk for a release purely to diff against it.
- **Separate depth budgets for caller-named branches and engine-folded declarations** (ADR-0025): rejected. It caps precisely the tree that can explode and leaves authored trees alone, but "how deep can this read go" would stop having a single answer, and a read mixing both kinds of branch would count them differently. ADR-0025 already declined the same split from the other side.
- **Raising the depth cap or making it configurable** now that it bounds authored trees rather than generated ones: deferred. The number's justification changes here, but changing the number on a guess is worse than changing it in response to a caller who actually hits it.

## Consequences

- **The depth cap keeps its value and its refusal, but not its reason.** It no longer bounds an engine-generated walk that could explode across the relationship graph; it bounds a tree the caller wrote. The refusal stays fail-closed per ADR-0022 and stays a single budget shared with ADR-0025's declaration folds, but the error must say it is declining a tree more expensive than the engine will serve — not that the Access Filter cannot scope one. An error that states the old reason sends whoever hits it looking in the wrong place.
- **The cycle prune survives by changing what it guards.** After this change the relationship graph is never walked unprompted, so nothing caller-supplied can cycle — a caller include is a finite literal. Declared dependencies (ADR-0025) can, and they are folded in by the engine rather than written by a caller, so the guard is re-pointed at them and re-commented accordingly. Left describing the old hazard it would read as dead code and be deleted, taking the new protection with it.
- **ADR-0025 must land first.** Once a named relation stops expanding, a declared dependency is the only way a computed field on a nested list sees a relation. Landing this first would leave those fields with no route to their data at all, and would put the cycle guard in the position of guarding something that does not exist yet.
- **ADR-0024 is extended, not amended.** Its rule was always the right one; it was applied at one level when it needed to apply at all of them.
