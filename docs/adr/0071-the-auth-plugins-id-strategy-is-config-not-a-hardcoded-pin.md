# The auth plugin's id strategy is config, not a hardcoded pin

Status: accepted

## Context

ADR-0048 gave `authPlugin` a per-list `db.idField` pin so an app-level default could never reach a table better-auth owns and assumes is string-keyed; ADR-0060 named the pin `uuid7` and had the adapter declare `disableIdGeneration: true, supportsUUIDs: true, supportsNumericIds: false` to match. Both records described the pin as a fixed constant, and `packages/auth/src/config/plugin.ts` implemented it exactly that way: `db: { ...derived.db, idField: 'uuid7' as const }`, unconditionally, on every list the plugin injects.

Two problems followed, both raised in review of #1221 (ADR-0060's implementation) and tracked as [#1239](https://github.com/OpenSaasAU/stack/issues/1239):

1. **No escape hatch.** `uuid7` already agrees with the config-level default (`config.db.idField ?? 'uuid7'`), so the pin only ever changed behaviour for an app that had deliberately set a different `db.idField`. `adopt-better-auth-tables.ts` exists precisely to diff clean against a live better-auth install; a live install whose `id` columns hold non-uuid text ids (a nanoid-shaped strategy, adopted onto the stack's `cuid2` column type) could no longer keep its Auth lists on that strategy — the generator emitted a `pg/uuid` column regardless, and both the contract diff and any migration over existing rows failed.
2. **The `extendList` branch never saw the pin.** `extendList` forwards only `fields`/`hooks`/`mcp` (by design — `db` is the application's own concern for a list it declared itself, same posture as ADR-0013 takes on access). An app that declares one of the derived list keys itself keeps whatever `idField` its own config resolves to, while the adapter's `supportsUUIDs: true` / `supportsNumericIds: false` was asserted unconditionally for every model, regardless of which branch produced it. The two could disagree with no error anywhere.

## Decision

- **`authPlugin` gains an `idField?: 'uuid7' | 'cuid2'` option.** `'int autoincrement'` is excluded from the type: the Auth adapter treats every id as a string (`isIdentity` in `src/adapter/index.ts`, and better-auth's own `consumeOne`/`transform.output` assume the same), so an integer id is not a shape the adapter can ever hand back correctly.
- **Resolution order, computed once in `init`:** an explicit `authPlugin({ idField })` wins; otherwise the Auth lists inherit the app's own `db.idField` default — precisely the fallback chain any other list gets (ADR-0048) — falling back to `'uuid7'` when neither is set. This closes problem 1 without an app having to touch `authPlugin` at all when its global default is already the string strategy it wants: only an app whose Auth lists need to _diverge_ from the app-wide default reaches for the new option.
- **A resolution of `'int autoincrement'` is refused at config time**, naming the fix (`authPlugin({ idField: 'uuid7' | 'cuid2' })`), rather than silently minting an integer id the adapter cannot round-trip.
- **The `addList` and `extendList` branches are required to agree.** For a list the app declares itself (the `extendList` path), `init` reads that list's own resolved `idField` (`listIdColumn`, the same contract-driven accessor `.opensaas/`'s boundary coercion uses) and compares it against the plugin's resolved strategy. A mismatch throws, naming the list and both values, rather than letting the two branches silently diverge the way problem 2 could. `extendList` still forwards no `db` on success — the check only ever refuses a disagreement, it never overwrites the application's own config.
- **`adoptBetterAuthTables()` grows a matching `idField` option**, passed straight through to the returned `AuthConfig` fragment, so the common adoption case (`adoptBetterAuthTables({ idField: 'cuid2' })`) is one line rather than a separate `authPlugin({ idField, ...adoptBetterAuthTables() })` composition — though both spellings work, since the recipe is pure config (per its own doc comment).
- **The adapter's `supportsUUIDs`/`supportsNumericIds` are derived, not asserted.** `authIdCapabilities(config, registry)` reads the resolved strategy off the `user` model's own list (every Auth list is required to agree, per the point above, so any one of them speaks for all) via `listIdColumn`, and returns `{ supportsUUIDs: strategy === 'uuid7', supportsNumericIds: false }`. `supportsNumericIds` stays unconditionally `false` — the Auth lists are never `'int autoincrement'`, by the refusal above — but is now computed alongside `supportsUUIDs` rather than hand-paired with it, so the two can't drift independently if a later change touches one and not the other.

## Consequences

- **This is additive for every existing app.** No `authPlugin({ idField })` call and a `uuid7` app default (explicit or absent) resolve exactly as before; the new checks only ever fire for a config that previously produced a silent mismatch.
- **better-auth's `supportsUUIDs`/`supportsNumericIds` are provably inert under the shipped `disableIdGeneration: true`** for every path this adapter exercises today — traced against `@better-auth/core@1.7.1`'s `get-id-field.ts` and `factory.ts`, `disableIdGeneration` short-circuits both the id-generation decision and the `useUUIDs` transform branch before either flag is read, and `supportsNumericIds` only matters when `advanced.database.generateId === 'serial'`, which `assertNoUnsupportedPassthroughKeys` already refuses. Deriving them correctly is still the right call: it is a compile-time-cheap guarantee against a future better-auth release reading either flag somewhere else, and it removes a hardcoded claim (`supportsUUIDs: true`) that a `cuid2`-adopting app's own adapter instance would otherwise have been carrying incorrectly regardless of whether anything currently reads it.
- **ADR-0048 and ADR-0060 are amended in place** (blockquotes at the top of each), not superseded: their surrounding decisions (uuid7 as the config-level default, the ORM minting every auth id, `disableIdGeneration: true`) are unchanged.
- **`packages/auth/CLAUDE.md`** gains the escape-hatch section under "Adopting an existing better-auth install", naming the resolution order, the refusal, and the `extendList` agreement check.
- **No contract or migration changes for any list that doesn't opt in.** The Auth lists' emitted column type is unaffected unless an app sets a non-default `idField` (via `authPlugin` or its own `db.idField`), which is exactly the case this record makes possible for the first time.

## Considered options

- **Leave the pin hardcoded and document the limitation.** Rejected: it is the status quo the issue reports as a defect, not a documented trade-off — an app cannot complete a from-scratch adoption of a text-id better-auth install at all, which is one of `adopt-better-auth-tables.ts`'s two stated purposes.
- **Drop the pin entirely and let the Auth lists always inherit the app-wide `db.idField` default, with no per-plugin override.** Rejected: it reopens the `'int autoincrement'` case with no way to opt the Auth lists out, and gives an app on a mixed-strategy setup (most lists `int autoincrement`, Auth lists needing a string) no way to diverge without changing its own global default.
- **Force the `extendList` branch to adopt the plugin's resolved `idField` outright**, overwriting whatever the app-declared list's own `db.idField` says, rather than checking agreement and refusing a mismatch. Rejected: a plugin silently rewriting a config value the application owns on a list the application declared itself is a bigger authority violation than the refusal, and out of step with how `extendList` already treats `access` (ADR-0013) — ownership of a list's own config belongs to whoever declared it.
- **Let `supportsUUIDs`/`supportsNumericIds` stay hardcoded, on the grounds that they are provably inert today.** Rejected: "inert until better-auth changes something we don't control" is not a property this codebase relies on elsewhere, and the acceptance criterion is that the adapter's declared capabilities cannot contradict the emitted column type — a hardcoded `true` next to a `cuid2` column is a contradiction regardless of whether anything currently reads it.
