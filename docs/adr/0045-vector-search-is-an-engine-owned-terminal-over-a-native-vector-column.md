# Vector search is an engine-owned terminal over a native vector column

`packages/rag/src/storage/pgvector.ts` runs `$queryRawUnsafe`, casting `("field"->>'vector')::vector` inline and hand-rolling an access filter beside it. [#1043](https://github.com/OpenSaasAU/stack/issues/1043) asked whether that ports to Prisma 8's typed SQL builder or keeps a hand-rolled filter behind an allowlist.

Both options were drawn against the wrong surface. [ADR-0041](0041-the-secured-surface-is-an-opaque-wrapper-over-a-prisma-8-collection.md) built the secured surface over a Prisma 8 `Collection` — the ORM. The pgvector extension's distance functions were found on `db.sql`, the typed SQL builder: a third surface, which ADR-0041's wrapper does not cover and [ADR-0038](0038-access-enforcement-stays-in-terminal-operations-with-the-spi-as-a-tripwire.md)'s engine stamp does not stamp. Porting to the typed builder does not move RAG inside the seat; it moves RAG to a place with no seat.

So the question is not which surface the plugin builds its query on. It is that **a plugin should not be building this query at all**. Vector search becomes a terminal the engine owns, and everything the plugin needed in order to reconstruct scoping from the outside — `listKey`, `config`, a filter-to-SQL translator — stops existing.

## Decisions

- **The embedding column is a native `Vector(n)`, with metadata in its own column.** `embedding.ts`'s `Json` type existed for cross-backend portability ("so the same schema works across the pgvector/sqlite-vss/JSON storage backends"); [#1040](https://github.com/OpenSaasAU/stack/issues/1040) deleted `sqlite-vss.ts` and left one provider. A native column is the precondition for both a typed distance expression and a vector index.
- **`dimensions` becomes a contract-time constant. The field's declaration is authoritative; the generate-time check is best-effort.** `ragPlugin`'s `beforeGenerate` fails the run when a field's declared dimension disagrees with its provider's — but **only where that provider's dimension is statically known**. It is known for OpenAI (`MODEL_DIMENSIONS` maps each model to a fixed size) and unknown for Ollama, whose config carries only `baseURL` and `model` and whose provider leaves `dimensions` at `0` until a live `embed()` call succeeds. Generation must never depend on a running Ollama, so **`OllamaEmbeddingConfig` gains a required `dimensions`**, and a custom provider either declares one or is exempt from the check. The generator itself learns nothing about embedding providers: providers are config-time objects and [ADR-0040](0040-the-generator-emits-a-typescript-contract-module-not-psl.md) has the generator emitting a literal contract from config, so the check belongs to the plugin. Changing a provider's dimension is a migration, because it is a schema fact.
- **The vector index is declared on the embedding field**, not in `db.indexes`: `embedding({ index: { method: 'hnsw', … } })`. The field is the one place that owns the column, the distance function and the operator class together, so it can derive the opclass and reject a disagreement. `db.indexes` is a list-level, column-name-based API with no vocabulary for access methods or build parameters, and ADR-0040 has just frozen it.
- **The column type is chosen from the dimension, not fixed to `vector`.** pgvector's `hnsw` and `ivfflat` indexes cap `vector` at **2,000 dimensions**, and this package already ships a built-in provider above that line — OpenAI's `text-embedding-3-large` is 3,072. So an indexed field over 2,000 dimensions emits **`halfvec`** (indexable to 4,000) rather than `vector`, at the cost of half precision. Above 4,000, or where half precision is unacceptable, generation **fails with a named error** rather than emitting an index definition the database will reject. Declaring no index leaves `vector` at any dimension, since the cap is the index's, not the type's.
- **`distanceFunction` moves to the field for the same reason** — it is what the opclass must agree with — and `distanceToScore` survives. Callers want a 0–1 similarity, not a raw distance whose direction differs per function; `<#>` returning a _negative_ inner product is precisely the trap the conversion exists to hide.
- **The access filter is injected into the vector query.** One scoped query, so top-K is computed over the set the session can see. Ranking first and filtering after leaks nothing, but returns fewer than `limit` whenever the session cannot see most rows — which is what `LIMIT limit * 2` was guessing around.
- **`minScore` becomes a distance bound in the `WHERE` clause.** Every supported distance function is monotonic in the score, so the inversion is expressible as a bound, and both the `* 2` multiplier and the JavaScript post-filter are deleted. **Exactness is conditional on the scan, not on the filter.** An exact (sequential) scan returns exactly the top-K that qualify. An **approximate HNSW scan does not**: pgvector produces candidates from the index and applies the `WHERE` clause to them, so a selective access filter can still yield fewer than `limit` rows while enough authorised rows exist. The engine therefore enables pgvector's **iterative index scans** (`hnsw.iterative_scan`) for these queries, and the guarantee is stated honestly: exact under an exact scan, and under an approximate scan bounded by the scan budget. Deleting the over-fetch is justified because the access filter is now _in_ the query, not because approximate search became exact.
- **Semantic search is a core-owned terminal on the secured surface:** `context.db.Article.where(…).nearest('embedding', vector, { limit })`. It inherits operation access, field visibility, hooks and silent failure from the same place every other terminal does, and `listKey`/`context`/`config` stop being parameters. Core gains vector vocabulary; RAG keeps the field builder, providers, chunking and generation hooks.
- **`nearest()` returns `{ item, score }` — a named exception to ADR-0041's exactness rule.** The return type is a wrapper, not a row, so "a terminal's result matches the caller's `.select()` exactly" still holds of `item` and the score sits beside it rather than being smuggled in as a field the list does not have. The raw distance is not exposed.
- **Searching requires read access to the embedding field.** [ADR-0031](0031-a-predicate-cannot-name-a-field-the-session-cannot-read.md) applies unchanged: ordering by a field is naming it, and a returned score is a measurement of its contents. Hiding a large vector from the admin UI is a `ui` concern, not an access one.
- **The embedding and its metadata ship write-denied to application code, and the plugin writes them under sudo.** They are plugin outputs — the same shape as [ADR-0036](0036-plugin-derived-credential-fields-ship-read-denied.md)'s read-denied credential fields. The denial is _not_ self-enforcing: field-level write denial **throws** rather than dropping the key (`filterWritableFields`, per #568), and the plugin's own `resolveInput` puts the vector into `resolvedData` — so a naive denial would fail every ordinary create and update that generates an embedding. `checkFieldAccess` already returns `true` under sudo, so **the generation path is a sudo write** and needs no new privileged mechanism. Manual-embedding users opt the denial off explicitly.
- **`packages/rag/src/storage/` is deleted, not ported** — `access-filter.ts` (including `prismaFilterToSQL`), `pgvector.ts`, `json.ts`, `json-file.ts`, `types.ts`'s `VectorStorage`, and `PgVectorStorageConfig`. `sqlite-vss.ts` was already condemned by #1040.

## Considered Options

- **Keep a hand-rolled filter behind an operator allowlist.** Rejected on the code's own admission: `prismaFilterToSQL`'s docblock records that an unhandled operator is dropped rather than thrown, which **widens** the `WHERE` clause. A fail-open filter contradicts [ADR-0022](0022-access-control-fails-closed-when-it-cannot-scope.md), and it is worse than an admitted bypass because it looks like enforcement.
- **Declare vector search a `context.prisma`-class bypass** — return IDs and let the caller do a scoped read. Honest, and it was the fallback if the terminal proved impossible. Rejected because the terminal is possible.
- **A public `context.sql`, an opaque wrapper mirroring `context.db` over the SQL builder.** Chosen mid-discussion and then superseded within it: once `nearest()` is core-owned, the SQL query is built inside the engine where scoping already happens, and the seat's only known consumer no longer needs it. Building a second curated surface to chase Prisma's SQL DSL, for a demand nobody has stated, is speculative. Recorded as fog rather than built.
- **A plugin terminal-registration seat on the wrapper.** More general, and tiptap or storage might use it. Rejected: ADR-0041's subset is curated precisely so that omission is the signal, and every plugin-registered terminal is a new place the scoping guarantee can be got wrong by code core does not own.
- **Auto-injecting the filter in `beforeCompile` for SQL plans.** Rejected on the grounds [#1037](https://github.com/OpenSaasAU/stack/issues/1037) already established — no per-request session slot, no stability commitment — and because it would make ADR-0038's deliberately-deletable tripwire undeletable.
- **Keeping `Json` and the JSON storage backends as a no-extension path.** Rejected: with a native column the JSON backends cannot read the same column, so the interface would span two incompatible schemas rather than two query strategies. If a no-extension path is wanted it is a different field type, not another backend for the same one.

## Consequences

- **Adopting `@prisma/orm-extension-pgvector` requires a registration seat that does not exist.** #1040 deleted `prismaClientConstructor`, the db config's only extension point, and ADR-0038's tripwire needs the same seat. This record makes the hole concrete and hands it to [#1056](https://github.com/OpenSaasAU/stack/issues/1056); it does not fill it. Deciding a config-surface question spanning the tripwire and ADR-0040 from RAG's corner would settle it from the wrong ticket.
- **A verification gate.** It is UNKNOWN whether the pgvector extension surfaces distance functions on the ORM `Collection` (an `orderBy` over a `Vector` column) or only on `db.sql` — every documented example was `db.sql`, and the `prisma` CLI is broken at `8.0.0-rc.8`, so nobody can check today. If the ORM path exists, `nearest()`'s internals are simpler and no SQL-builder access is needed at all. **No decision above changes either way**; this is an implementation detail behind a terminal, which is part of why the terminal is the right boundary.
- **Existing Json embeddings are regenerated, not migrated.** Embeddings are derived data and the source text is still there. `rag-ollama-demo` and `rag-openai-chatbot` reseed; no `Json → Vector` conversion is written.
- **Vector search can finally use an index.** Today every search is a sequential scan, which the `Json` column forced. This is the change's performance argument, and it is why shipping the native column without the index declaration was rejected — that would pay the cost (dimensions-as-migration) without the benefit.
- **ADR-0041 is amended in place** for the added terminal and the `{ item, score }` exception to its exactness rule.
- **ADR-0031 and ADR-0022 are confirmed, not changed.** Both were load-bearing in the reasoning: 0031 decides the field-access question outright, and 0022 is what rules out the hand-rolled filter.
- **Four of the decisions above were corrected under review**, each against code in this repository: Ollama's dimension is not knowable at generate time, `text-embedding-3-large` exceeds HNSW's dimension cap, a write denial throws rather than drops (so it would have broken the plugin's own hook), and an approximate scan does not honour an exact `LIMIT` under a selective filter. The decisions' intent survived all four; their stated mechanisms did not, and the gap between the two is where a design record is most likely to be wrong.
- **Everything here was reasoned against `8.0.0-rc.8`.** The extension's API surface, and the ORM-versus-`db.sql` question above, should be re-checked at GA alongside the map's other CLI-dependent conclusions.
