# The generated bundle is loaded by the host bundler, via explicit import extensions and static import

The generator emits the **Generated bundle** (`.opensaas/context.ts` plus the `prisma-client/**` tree) as TypeScript with extensionless relative imports, which only a TS-aware loader (`tsx`) or a bundler can resolve. A plain Node process type-strips the `.ts` but then fails on the extensionless sub-imports, and a host that pushes the bundle out of its compile graph (a `webpackIgnore`d dynamic `import()`) gets no file tracing, so the `prisma-client/**` subtree goes missing from the serverless output. We make the bundle loadable by the host's bundler: emit explicit import extensions by default, and sanction statically importing the bundle so `next build` (or any bundler) compiles and traces it.

## Decisions

- **Explicit import extensions, by default.** The generator emits relative imports with explicit extensions rather than extensionless, so the bundle resolves identically under `tsx`, vitest, and a bundler — and is traceable. This is the default output, not a flag: explicit extensions are universally compatible, so existing `tsx`/test/`seed-data` consumers are unaffected.
- **The host bundler owns loading; static import is the sanctioned path.** The supported production model is to statically import the Generated bundle so the host build (`next build`) compiles and file-traces it into the serverless output — not a runtime `webpackIgnore`d dynamic `import()`. This is viable because the generated `types.ts` now type-checks cleanly (the duplicate-`createdAt` `TS2300` was removed when auto-timestamps became opt-in; see ADR-0004).
- **The bundle stays alias-free; the app owns its config's reach.** The bundle imports only relative paths and npm packages. What the app's own `opensaas.config` pulls in (e.g. lazy `import('@/workflows/…')` that reaches `xero-node`/`twilio`/Keystone resolvers) is the app's architecture, not the bundle's loadability — the stack documents this boundary but does not own it.
- **A pre-compiled JS entry is deferred.** Emitting a compiled `.opensaas/context.{mjs,cjs}` for a genuinely bundler-less plain-Node target is a later option, taken only if such a target becomes a real requirement. The Next/Vercel bundler target is served by the above.

## Why this is worth recording

A future reader will see explicit extensions and a "statically import the bundle" deploy recipe and wonder why — especially since the repo previously forced the bundle out of every compile graph with a `webpackIgnore`d dynamic `import()`, precisely to dodge an un-type-checkable artifact. The answer is that the artifact now type-checks and is meant to be bundled by the host. Reversing this — returning to a runtime dynamic import, or shipping a separate compiled bundle by default — would either reintroduce the missing-file-tracing deploy failure or eagerly drag the whole app dependency surface into every route, so the trade-off is worth pinning down.
