# Plugin tables derive through the same registry as the base Auth models

Status: accepted

Two independent code paths turned better-auth schema into stack lists: `deriveAuthLists` (the four base models plus the conditional `rateLimit`, reading `getAuthTables` per ADR-0033) and `convertBetterAuthSchema`/`convertTableToList` (better-auth plugin tables — e.g. the MCP plugin's `oauthApplication`/`oauthAccessToken`/`oauthConsent`). Neither was a superset of the other, so a fix landed twice or once: `bigint: true` → `BigInt` was fixed in the plugin converter (#917) and separately, by hand, in the core lists. `convertBetterAuthSchema` also deliberately dropped every reference field to a bare column, on the stated grounds that "better-auth uses one-way references; OpenSaaS requires bidirectional relationships" — a premise that was never actually true (list-only refs have supported one-sided declarations all along), and the consequence was a reachable data-integrity defect: better-auth's own `deleteUser` only deletes `session`/`account` rows itself and relies on the database cascade for everything else, so a plugin table with no FK constraint was left orphaned — including `oauthAccessToken`, i.e. live credentials whose owner no longer exists.

## Decision

`deriveAuthLists` now derives plugin tables through the same registry and field-derivation pass as the base models, instead of a separate converter. The app's better-auth plugins (`authPlugin({ betterAuthPlugins })`) are passed straight into `getAuthTables({ plugins })`, which already merges each plugin's own `schema` into its result — both a standalone table (`oauthApplication`) and a schema extension of a base model (e.g. the `anonymous` plugin's `user.isAnonymous`) arrive pre-merged, so the latter needs no special-casing at all.

Concretely:

- **One model registry, built before any field is derived**, mapping every table key (base or plugin) to its derived list key. A reference can cross from a plugin table to a base model or to another plugin table, so the whole set has to be known up front. Resolving a reference against a model outside the registry throws a clear error naming the model and field — the same failure mode ADR-0033's base-model derivation already has, now generalized rather than silently degrading to a bare column.
- **Plugin table list keys are PascalCased from better-auth's resolved `modelName`** (`oauthApplication` → `OauthApplication`), with `db.map` set back to the original whenever the case changed — the same round-trip fix #991 needed at the admin-UI layer, now also true of the Prisma model name itself. Base models are untouched: their list key is still exactly the configured `modelName`, never re-cased.
- **A reference to the target's `id` becomes a real `relationship()`** — FK constraint, `onDelete` (mapped from better-auth's full set of referential actions, not hardcoded to cascade), index/uniqueness, and a reverse collection on the target list, exactly like a base-model FK. This is what closes the orphaning: `oauthApplication`/`oauthAccessToken`/`oauthConsent`'s `userId` references now cascade for real.
- **A reference to a non-`id` field stays a plain (indexed) scalar column.** better-auth's own oidc-provider schema references `oauthApplication.clientId`, not its `id` — `relationship()` can only express an `id`-based FK, so pointing one at `clientId` would target the wrong column. This is the one reference shape the consolidation deliberately still declines, same outcome as before, now for a stated reason instead of a blanket "no references" policy.
- **Reverse relations land on whichever list a plugin table references**, including a base model, since the registry (and therefore every list) is assembled in one function call before any list config is built — no ordering dependency between "add the base lists" and "add the plugin tables" the way the old two-pass `addList`/`extendList` loop in `authPlugin`'s `init` needed. That loop is now a single pass over `deriveAuthLists`'s one combined `lists` record.
- **Plugin tables ship closed**, per ADR-0013 — no `access` passthrough exists for them, matching `convertBetterAuthSchema`'s prior behavior. An app that needs access declares the list itself under the derived key, which the field-only `extendList` merge leaves standing.
- **Out of scope, deliberately:** `createdAt`/`updatedAt` on a plugin table are still dropped rather than derived (matching `convertTableToList`'s prior behavior) — better-auth's own plugin schemas don't declare a JS-level default/`onUpdate` for them the way the base models do, and adding `db.timestamps` unconditionally would add columns some plugin tables don't declare at all.

## Consequences

- The separate `convertBetterAuthSchema`/`convertTableToList` converter (`packages/auth/src/server/schema-converter.ts`) is deleted, not wrapped. `deriveAuthLists` is the only better-auth → stack-list translation in the package.
- The generated schema for the base models is unchanged except where a plugin table adds a reverse collection (e.g. `User.oauthApplications`) — verified by `generated-fk-shape.test.ts` diffing the Session/Account/Verification model blocks with and without the MCP plugin enabled.
- `auth-lists-drift.test.ts` (#988) now also compares the MCP plugin's OAuth tables field-by-field against `getAuthTables`' own output, not just the four base models.
- A live end-to-end test (`mcp-oauth-cascade-e2e.test.ts`, opt-in like the existing rate-limiter e2e guard) signs up a real user against a real generated schema, attaches OAuth rows, deletes the user through better-auth's own `/delete-user` endpoint, and asserts the database cascade removed them — the concrete defect this ADR closes, proven against a live database rather than only at the config level.
- This absorbs #994 (which had specified the same FK fix against list-only refs, before ADR-0033 shipped the base models' bidirectional-ref convention) — the FK column name is controllable on a bidirectional ref already, so #994's premise (list-only refs as the only viable shape) no longer applies, and its fix is superseded by this consolidation rather than landed separately.

See issue #992 for the full triage history, including the confirmed orphaning and the correction that bidirectional refs were viable all along.

Because plugin tables derive through this same registry and scalar-field-derivation pass, they are also in scope for ADR-0036's credential field read-deny — see that ADR (as amended by issue #1014) for the plugin-table credential set and the `credentialFields` seam.
