# A to-one relation reads as nullable by arity, not by column

Status: accepted

[#1063](https://github.com/OpenSaasAU/stack/issues/1063) established that Prisma 8 scopes a to-one include natively — a refinement `where` that excludes the related row leaves the parent row in the result with the relation `null` — so the hand-rolled `toOneAccessFilters` tree and its post-query null-forcing are deleted. Deleting them exposes a question the tree had been answering in TypeScript we control: a **required** to-one (`relationship({ ref: 'User.posts', db: { isNullable: false } })`) is declared non-null by its column, yet under access control it is absent from any read whose session may not see the related row. Prisma's own row type for that case says `IncludedRow` with no `| null` while its runtime hands back `null`; [ADR-0052](0052-the-generated-types-declare-the-contract-remainder-and-instantiate-core-generics.md) fixed _where_ our answer lives — core's include-narrowing generics over the contract, never generated text — and left _what_ it says to this record.

**A to-one relation a caller names is typed `Row<Target> | null` on every secured read, whatever its foreign-key column's nullability. A to-many is `Row<Target>[]`. Arity is the only input; the column is never consulted.** This is not a widening we tolerate but the true type: access control makes every to-one conditionally absent, so a type that promised presence would be wrong for exactly the reads the stack exists to secure.

## The type follows the decode rule, not the column

Prisma 8 decides what an included to-one _returns_ by cardinality alone — `isToOneCardinality(cardinality) ? rows[0] ?? null : rows` (`orm-client.mjs:2287`, `8.0.0-rc.8`) — and the child is a correlated subquery in the parent's projection, so an empty scope decodes to `null` without touching the parent. Its _type_ consults something else: `IncludeRelationValue` (`orm-client.d.mts:721`) drops `| null` when `IsToOneRelationNullable` finds the model owns the foreign key and every local column is non-nullable. The runtime and the type disagree because they read different facts, and the runtime is the one that is right under a refinement.

Our type reads the same fact the runtime does. Core's `Row`/`SecuredList` include narrowing takes the target list and the relation's cardinality from the contract's relation graph and produces `Row<Contract, Remainder, Target> | null` for `'1:1' | 'N:1'` and `Row<…>[]` for the rest. It never instantiates `IncludeRelationValue`, `IsToOneRelationNullable` or `DefaultIncludedRow` — the secured surface's result types were already ours under [ADR-0041](0041-the-secured-surface-is-an-opaque-wrapper-over-a-prisma-8-collection.md), and the included row is our `Row`, so an included relation carries its list's computed fields and stored-field overrides exactly as a root row does (Field Visibility runs at every level; a type that said otherwise would be lying one hop down).

This also settles a fact [#1070](https://github.com/OpenSaasAU/stack/issues/1070) recorded against the CLI-emitted contract: at this rc, Prisma's type for an included to-one resolves to `… | null` unconditionally and its fields to `{ [x: string]: unknown }` — the nullability chain falls through on a lookup miss. That is Prisma's defect on Prisma's surface. Because ours is computed from the relation graph and not from `IncludeRelationValue`, it reaches neither our callers nor our decision.

## Why `null`, and not any of the alternatives

**A throw** is the wrong consumer. ADR-0022 throws when the engine _cannot compute_ a scope; here it computed one, Prisma applied it, and the scope was empty — that is a result, not a failure to scope. ADR-0031 throws when a predicate _names_ a denied field, because "may you ask?" must fail identically for a match and a miss to close a probing oracle; ADR-0044 fixed that "may you see?" omits silently for the same reason silent failure exists. A throw here would leak the one bit Silent failure is defined to withhold: that a related row exists which this session may not read.

**Dropping the parent row** would keep the column's promise — "if you cannot see the author, you cannot see the post" — and it is the option a reader will reach for. Rejected on three grounds. It makes the parent's _row set_ depend on what the caller named: a bare read of `Post` returns the row and `Post.include('author')` drops it, so `count()` and `include(…).all().length` disagree, which is the shape-varies-by-what-you-wrote fault ADR-0024/0026/0043 spent three records removing. It lets one list's `query` rule silently become another list's row filter — action at a distance across lists, the class ADR-0025 exists to prevent. And it is a post-query filter over a result Prisma deliberately keeps whole — hand-rolled read machinery re-entering through the door #1063 just closed.

**A discriminated marker** (`{ kind: 'denied' }` reaching the caller) distinguishes "denied" from "absent", which is precisely what Silent failure forbids. The marker the deleted tree carried never reached a caller — `field-visibility.ts` turned it into `null` before any hook ran — so it was always an implementation detail, and there is nothing in it to preserve.

**A narrower type for a `sudo()` context** — where a required to-one really is always present — would be true, and is rejected anyway. ADR-0032 keeps `sudo(): Context`, one interface per shape; a second `Row` per list keyed by privilege would double every generic ADR-0052 instantiates, and a value read under `sudo` and handed to ordinary code needs the wide type at the boundary regardless. One type, and the null-check is the cost of reading through a secured surface even when the session happens to be privileged.

## The to-many case is the same pattern, already spelled

Everything in this record concerns one denial: the **related list's operation-level `query` access** scoping the relation's rows. The relationship field's own field-level `read` rule is a different denial with an answer already on record — the key is stripped, as for any denied field, and ADR-0044 omits it before the query where the rule is row-independent — and nothing here changes it. A to-many the related list's `query` access scopes away is `[]`, indistinguishable from a genuinely empty relation, and nobody has asked for a marker there. The to-one `null` is that rule reaching its natural spelling for arity one, not a new rule. The `{ kind: 'denied' }` branch existed only to skip a query Prisma 7 could not scope; under Prisma 8 an outright `false` from the related list's `query` rule lowers to a never-matching predicate on the refinement, the same path a to-many takes, so there is one mechanism for "scoped" and "denied" and the key the caller named is present and `null` rather than absent. Omitting the key here would make the result's _shape_ vary by session for a rule that is about rows, not fields — ADR-0041 promises a terminal's result matches the caller's `.select()` exactly — and would blur the two denials into one spelling.

## Considered Options

- **`null`, by arity (chosen).** True under access control, consistent with Silent failure's single-record spelling, ADR-0041's empty-value rule (`null` from `first`), the to-many `[]`, and the `StoredRow | null` ADR-0052 already gives a declared to-one in a hook's `item`. Mirrors the runtime's own decode rule.
- **`null` only where the column is nullable; presence where it is not** — Prisma's typing, adopted. Rejected: it is the type/runtime gap this record exists to close, restated as policy.
- **Throw on a denied required to-one.** Rejected — the wrong consumer of the classifier, and a leak of existence.
- **Drop the parent row when a required to-one is denied.** Rejected — row set varies by what the caller named, one list's rule scopes another list's rows, and it is a post-query filter over a result the ORM keeps whole.
- **Expose a denial marker.** Rejected — Silent failure forbids the distinction, and the marker never reached a caller to begin with.
- **A privilege-narrowed `Row` for `sudo()`.** Rejected — doubles ADR-0052's generics for a guarantee that evaporates at the first boundary.
- **Omit the key rather than set it `null` for an outright-denied to-one.** Rejected — shape varying by session, against ADR-0041's exact-selection promise.
- **Wait for Prisma to fix `IncludeRelationValue` and inherit its type.** Rejected — the secured surface's types are ours by ADR-0041/0052 and must be right whether or not upstream moves; inheriting would also re-import the `{ [x: string]: unknown }` row the emitted contract currently produces.

## Consequences

- **Every to-one read is a null-check.** `post.author` on an included row is `User | null` even when `authorId` is `NOT NULL`. This is the visible cost and it is honest: the same read returns `null` today through the deleted tree, only untyped. Application code that dereferenced a required relation without a check was already wrong for a non-privileged session; it now fails `tsc` instead.
- **Read and write faces of a required to-one differ, deliberately.** `CreateInput` still requires `connect` on a non-nullable foreign key with no default (ADR-0050/0052 read that from the contract), so a required relation is required to _write_ and nullable to _read_. That asymmetry is the shortest accurate statement of what access control does to a relation.
- **The foreign-key column is untouched.** `authorId` keeps its contract type (`Char<36>`, non-null) beside `author: null`, so a caller can see that _a_ related row exists. That is the parent list's own scalar, governed by the parent's field-level `read` rule, and it is exactly what the deleted tree returned; a config that must hide it puts a `read` rule on the column. Nothing here changes what is disclosed, only what is typed.
- **The non-FK side of a one-to-one needs no special case.** If [#1097](https://github.com/OpenSaasAU/stack/issues/1097) drops ADR-0043's generation refusal, that side is a to-one whose foreign key lives on the other table and is nullable in fact (a user without a profile); the arity rule already types it `| null`.
- **Prisma's type gap is worth reporting and nothing here waits on it.** Two defects at `8.0.0-rc.8`, one resolution chain: `IncludeRelationValue` omits `| null` for a resolvable non-nullable FK-side to-one while the runtime returns `null` under a refinement; and against a CLI-emitted `contract.d.ts` the chain misses, yielding `| null` unconditionally with the included row's fields as `{ [x: string]: unknown }`. Both live on the Unsafe surface, which hands Prisma's types to the application unchanged, so an upstream fix improves that surface; the secured surface is unaffected either way.
- **ADR-0041's empty-value rule gains a row: a to-one include denies to `null`, a to-many to `[]`**, and the lowering of an outright `false` on a related list is a never-matching refinement predicate on both. **ADR-0052's deferred "what"** is this record.
- **Silent failure's glossary entry names the case**: a relation the related list's `query` access scopes away is `null` (to-one) or `[]` (to-many) in the row it hangs off, whatever the column says — and says in the same breath that a field-level `read` denial on the relationship field removes the key instead.
- **The consumer sweep widens by one type-check.** Every first-party read of a to-one off an included row — examples, the admin UI's relationship cells, MCP's projection — compiles against `| null`; most already handled it because the runtime already returned it.
