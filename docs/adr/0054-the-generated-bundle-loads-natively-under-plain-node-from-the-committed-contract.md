# The Generated bundle loads natively under plain Node, from the committed contract artifact

> **Amended 2026-09-05 by [Delete the Node build, enforce erasable-only output, and retire the scaffolder's `--db` flag](https://github.com/OpenSaasAU/stack/issues/1138)** (Prisma 8 map). The anchor named below was **deleted, not re-targeted**. `e2e/starter-auth/04-node-build.spec.ts` and `examples/starter-auth/scripts/node-build-create-user.mjs` are gone: the examples do not build until the spec's example conversion, and better-auth has no Prisma 8 adapter to run through until [ADR-0060](0060-better-auth-is-driven-by-a-stack-authored-auth-adapter-over-the-unsafe-surface.md) is implemented, so re-targeting them would have committed a spec that cannot pass. The property this record asserts is instead proven at CLI level by `packages/cli/tests/bundle-node-load.test.ts`, which runs `opensaas generate` over the contract fixture and imports the emitted `.opensaas/context.ts` with the real `node` binary, no flags and no loader; the erasable-only contract is held by `packages/cli/tests/bundle-typecheck.test.ts`. Neither exercises better-auth. A better-auth-shaped anchor should return with the example conversion — tracked on [#1178](https://github.com/OpenSaasAU/stack/issues/1178).

[ADR-0008](0008-generated-bundle-is-bundler-loadable.md) made the **Generated bundle** loadable by the host's bundler — explicit `.ts` import extensions, statically imported so `next build` compiles and file-traces it — because the `prisma-client/**` tree it carried went missing from serverless output whenever it fell out of the compile graph. [ADR-0011](0011-node-build-makes-the-bundle-loadable-without-a-bundler.md) then added an opt-in **Node build**, a `tsc`-compiled twin under `.opensaas/dist/`, because the `.ts` bundle could not execute in plain Node and one live module — better-auth's adapter, wired in the host's `auth-server.ts` — is imported by the Next server _and_ by bundler-less consumers. Both records reason from an artifact Prisma 8 deletes: there is no generated client package, so the bundle stops carrying a code tree and starts importing a JSON file. [#1067](https://github.com/OpenSaasAU/stack/issues/1067) asked whether either record survives a client constructed from a contract.

The answer differs per record. ADR-0008 survives with its reasons replaced. ADR-0011 is withdrawn, because the two facts it rested on — a generated client full of `enum`/`namespace` that type stripping chokes on, and a Node that strips types only behind a flag — are both gone.

Verified for this record, against `8.0.0-rc.8`: the five `@prisma/orm-*` runtime packages ship JavaScript only (the sole non-JS file in each tarball is `LICENSE`); the 188 modules reachable from `@prisma/orm-postgres/runtime` contain no `import.meta.url`, `createRequire`, `__dirname` or package-relative file read, so nothing locates files at runtime that a tracer would have to ship (the graph does reach `node:crypto`, `node:fs/promises`, `pg` and `pg-cursor` — a Node target, as today); a bundle-shaped tree — `.ts` relative imports, `import contractJson from '../prisma/contract.json' with { type: 'json' }`, `import type` from `contract.d.ts`, a `declare namespace`, top-level `await`, a Promise-valued config — ran under plain Node 24.10 with no flag; and `tsc` 7.0.2 reports TS5097 on that tree without `allowImportingTsExtensions` and is clean with it.

## Decisions

- **The `prisma-client/**` tree is deleted and nothing generated stands in for it.** The bundle's runtime imports become npm packages — `@prisma/orm-postgres/runtime`, `@opensaas/stack-core` — plus one JSON artifact. ADR-0008's tracing problem _dissolves_ rather than relocating: a statically imported JSON module is inlined by every bundler at build time, so there is no file to trace. The `outputFileTracingIncludes` pin the deploy guide documents for `prisma-client/**` is deleted with the tree it pinned.

- **The runtime is constructed from the committed `contract.json`, not from the builder value.** `.opensaas/context.ts` imports `../prisma/contract.json` with `{ type: 'json' }` and calls `postgres<Contract>({ contractJson, … })`, with `Contract` from `../prisma/contract.d.ts` — the artifact [ADR-0052](0052-the-generated-types-declare-the-contract-remainder-and-instantiate-core-generics.md) keys every generated type off. Not `postgres({ contract })` over the Contract module's export: the JSON is what `db verify` signs and migrations hash ([ADR-0040](0040-the-generator-emits-a-typescript-contract-module-not-psl.md)), and the runtime should execute those bytes rather than a re-derivation of them; Prisma's own caveat is that `typeof contract` types ignore per-instance codec parameters; and importing the builder value would load `@prisma/orm-postgres/contract-builder` — 143 modules — into every server route for a value the JSON already carries. `postgres()` re-derives the contract from JSON on construction ([#1045](https://github.com/OpenSaasAU/stack/issues/1045) measured 2.4 ms on a 41-model contract), once per process under the existing singleton.

- **ADR-0008 stands, re-grounded.** Explicit `.ts` extensions stay the default and gain a second reason: Node's native type stripping refuses extensionless specifiers, so the extension is what makes the bundle loadable there at all. Static import stays the sanctioned path and gains a new reason: it is what puts the JSON import inside the compile graph, where it is inlined — a `webpackIgnore`d dynamic import would make `contract.json` a runtime file read that nothing traces, ADR-0008's recorded failure on a different file. `allowImportingTsExtensions: true` stays the one consumer requirement: TypeScript permits type-only `.ts` and `.d.ts` specifiers without it, but the value import of `../opensaas.config.ts` trips TS5097. The `create-opensaas-app` template keeps setting it. The bundle stays alias-free, and the rule gains teeth: Node does not resolve tsconfig `paths`, so a config that wants to be plain-Node-loadable must keep its _value_ imports alias-free too. Type-only alias imports are erased, so the examples that write `import type { Lists } from '@/.opensaas/lists'` are unaffected.

- **ADR-0011 is withdrawn; the Node build is deleted.** Its decision turned on two facts. The generated client emitted `enum`/`namespace` that type stripping chokes on — that client no longer exists, and the bundle's own output is `declare namespace` and `interface`. And type stripping was version-gated and experimental — it is on by default since Node 22.18 / 23.6, warning-free since 22.18 / 24.3, stable since 24.12 / 25.2, and Node 20 reached end-of-life in April 2026, so every supported line loads the bundle natively. `output.buildTarget`, `node-build.ts`, the `.opensaas/dist/` layout, the staged copy of the config and the CLI's `@typescript/native` dependency go with it. What ADR-0011 wanted — one specifier both runtimes load — is now `.opensaas/context.ts` itself.

- **The bundle is erasable-only by contract, and the contract is tested.** Native loading holds only for erasable syntax — no `enum`, no runtime `namespace`, no parameter properties, `import type` on every type-only import — so the generator's output is checked under `erasableSyntaxOnly` and `verbatimModuleSyntax` in the CLI's own tests. The plain-Node anchor ADR-0011 required survives: ~~`04-node-build.spec.ts` and `scripts/node-build-create-user.mjs` re-target from `.opensaas/dist/context.js` to `.opensaas/context.ts`, proving under the real `node` binary that better-auth creates a user through the natively loaded bundle.~~ _Amended by [#1138](https://github.com/OpenSaasAU/stack/issues/1138): both were deleted instead, and the anchor is `packages/cli/tests/bundle-node-load.test.ts` — the real `node` binary over a generated bundle, but without better-auth. See the amendment at the top of this record._ The Node floor the stack states is **22.18**; 24 is the line CI tests.

- **`db.client`'s lazy factory runs inside `.opensaas/context.ts`, where `prismaClientConstructor` ran.** The generated `getPrisma()` awaits the config promise — the [ADR-0014](0014-orm-client-access-stays-async-document-the-sync-escape-hatch.md) case, a Promise when plugins are present — and then calls `config.db.client?.pg?.()` once, under the existing `globalThis` singleton. No boundary ADR-0008 governs is crossed: the bundle has always imported the config; the config never imports the bundle at runtime; the Contract module imports neither; and the CLI never reaches the factory, because the emitted `prisma.config.ts` carries `db: { connection: process.env.DATABASE_URL }` and does not import the app config. [ADR-0049](0049-extension-packs-are-declared-the-tripwire-is-stack-owned.md)'s purity split holds exactly — the callback lives in the one emitted file with no purity constraint.

- **ADR-0014's synchronous recipe is re-spelled, not changed.** The shared plain module that used to hold `prismaClientConstructor` now holds the `pg` factory; `opensaas.config.ts` names it as `db.client.pg`, and a synchronous-construction consumer builds `postgres<Contract>({ contractJson, pg: pgFactory() })` from the same JSON import. Still a second connection, still the raw client, still one shared module for connection selection.

## Considered options

- **Keep the Node build as an opt-in for "whatever Node the host runs".** Rejected: the host Node that cannot strip types is end-of-life, and keeping a compiled twin of a bundle Node loads natively means two artifacts that can drift, for a consumer that no longer exists. ADR-0008's reasons for deferring a compiled form — a compile step on every generate, a risk of dragging the app's dependency surface into the emit — return as the reasons to delete it.
- **Emit a compiled `.js` form as the default instead.** Rejected: it forfeits the host bundler's own transpile, ADR-0008's model, adds the compile step to every generate, and solves nothing the `.ts` form does not now solve.
- **`postgres({ contract })` over the Contract module's export.** Rejected above: the wrong artifact for verification, the wrong types per Prisma's caveat, and the builder loaded at runtime for no gain.
- **Copy `contract.json` into `.opensaas/` so the bundle imports only siblings.** Rejected: two committed copies of the signed artifact, and the bundle already reaches one level up for the config.
- **A conditional `exports`/`imports` map switching the entry per loader.** Rejected by ADR-0011 for resolver-fragility reasons that still hold, and no longer needed.

## Consequences

- **`.opensaas/` shrinks to four files** — `context.ts`, `types.ts`, `lists.ts`, `plugin-types.ts` — none of them Prisma's. The **Generated bundle** term in `CONTEXT.md` is rewritten and **Node build** is removed.
- **A syntax requirement on the app side, documented not enforced.** A plain-Node consumer of the bundle needs the app's `opensaas.config.ts`, and what it imports at runtime, to be erasable TypeScript with alias-free value imports. Plugins are compiled JavaScript and unaffected. The `create-opensaas-app` template adds `erasableSyntaxOnly` and `verbatimModuleSyntax` so the type-checker reports a violation before Node does.
- **Two items join the CLI re-verification gate ([#1070](https://github.com/OpenSaasAU/stack/issues/1070)):** a `next build` — webpack and Turbopack — of a bundle carrying `import … with { type: 'json' }`, since the attribute is standard syntax that TypeScript accepts under `module: esnext` but no bundler has been observed compiling this bundle; and `prisma contract emit --output-path prisma/` producing the sibling `contract.json` / `contract.d.ts` the imports above assume.
- **ADR-0008 and ADR-0014 are amended in place; ADR-0011 is withdrawn.** Nothing is superseded: the bundler model stands and the async seam stands.
- **The auth adapter question surfaces as graduated fog, not settled here.** ADR-0011's live module is better-auth's Prisma adapter, and better-auth 1.7.2 has no adapter for a Prisma 8 client — its Prisma adapter drives Prisma Client's per-model delegates, which do not exist. ADR-0049 assumes the adapter is handed the Unsafe surface; what that adapter _is_ becomes its own ticket. This record fixes only how the bundle loads. _Settled by [ADR-0060](0060-better-auth-is-driven-by-a-stack-authored-auth-adapter-over-the-unsafe-surface.md): a stack-authored Auth adapter over the Unsafe surface; the anchor script keeps its shape and now proves that adapter under plain Node._
