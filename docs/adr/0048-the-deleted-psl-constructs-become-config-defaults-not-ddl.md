# The deleted PSL constructs become config defaults, not DDL

Prisma 8 deliberately drops three constructs the generator emits today: `@default(cuid())`, `@updatedAt`, and implicit many-to-many. None is a rename — each is a behaviour change — and ADR-0040 settled the artifact they have to be expressed against (a TypeScript `defineContract` module) while explicitly leaving what they _become_ open. This record closes that.

## Decisions

### Ids

- **`uuid(7)` is the default id.** It is time-sortable, so Postgres — now the only provider — gets sequential B-tree inserts instead of index fragmentation. The cuid default was inherited from Keystone, and Keystone parity is out of scope for the Prisma 8 stack, so its only justification is gone.
- **`db.idField` names the strategy per list, with a config-level default.** The set is `uuid7 | cuid2 | int autoincrement`. An app that wants CUID, or small sequential integer keys, says so in one line; an app that wants neither never sees the option.
- **Singleton ids are derived from `isSingleton`, not from `db.idField`.** A singleton emits `Int @id @default(1)` — restoring the default ADR-0004 stripped for Keystone 6 parity. Declaring `db.idField` on a singleton is a generation error rather than a silently-ignored option: one knob, and it fails loudly, matching how ADR-0040 handled `db.indexes` `sort:`.
- **Plugin-injected lists pin their own strategy.** `authPlugin` sets `db.idField` explicitly on every list it injects, so an app-level default cannot reach into a table better-auth owns and assumes is String-keyed (ADR-0033). The pin is visible in the generated contract rather than being engine behaviour, which is the same posture ADR-0034 takes on plugin-derived tables. _Named by [ADR-0060](0060-better-auth-is-driven-by-a-stack-authored-auth-adapter-over-the-unsafe-surface.md): the pin is `uuid7`, and the ORM mints — the Auth adapter disables better-auth's own id generation, so Auth lists share every other list's id shape._
- **The id type is per-list, read from `contract.d.ts`.** Int ids make the id type vary by model; the contract already knows each model's id column, so the secured wrapper and `.opensaas/types.ts` read it from there rather than declaring an id type of their own. No stack-level `string | number` union crosses a package boundary.
- **One contract-driven boundary coercion.** Admin URLs, MCP tool arguments and server-action params are strings on the wire. A single place reads the list's id type from the contract and parses accordingly, shared by admin routing, MCP argument validation and the generated Zod schemas. A parse failure is a 404 or a validation error, never a silent `NaN`.
- **Existing dev databases are recreated, not migrated.** Ids change shape for every list. This is a standing rule for the Prisma 8 effort, not a per-ticket consequence: no example ships a database, no id in a seed script is stable, and reseeding is the only supported path.

### Timestamps

- **`updatedAt` becomes an application-side guarantee, with no database backstop.** `temporal.updatedAt()` lowers to `timestampNow` on the ORM's mutation path, so a write that does not go through the ORM — the raw-SQL bypass ADR-0038 acknowledges, `db update`, `psql` — leaves the column stale. A backstop would mean a trigger, which after ADR-0040 has nowhere to live: PSL is not emitted and `extendPrismaSchema` is deleted. Reintroducing that escape hatch to defend one column against writes that already bypass every other guarantee in the stack is a worse trade than losing the guarantee.
- **`createdAt` and `updatedAt` share one spelling.** Both go through `field.temporal.*`, so there is one mechanism to find and maintain rather than two — **conditional on `temporal.createdAt()` still lowering to a column default**. If it turns out to write application-side instead, keep the asymmetry and document it: a real guarantee is not worth trading for a uniform spelling. This sits on the CLI re-verification gate.
- **The no-op-update semantic change is accepted.** `@updatedAt` fires on any `UPDATE`; `temporal.updatedAt()` fires only on non-empty update mutations, so `update({})` stops moving the timestamp. No consumer in the repo issues an empty update, and a row that did not change arguably did not change. Recorded here as a deliberate behaviour change rather than an accident of the port.
- **ADR-0004's auto-timestamps-off default stands, on new grounds.** Its recorded justification was non-destructive Keystone migration, which is out of scope — leaving the default correct but unjustified. It survives because a generator should not add columns nobody declared.

### Implicit many-to-many

- **The config shape is deleted, not translated.** `many: true` on both sides becomes a generation error naming the two lists and the fix. Prisma 8's compiler rejects the implicit form outright, no example in this repo uses one (every `many: true` in all thirteen is the to-many side of a one-to-many), and the loudest justification for it — Keystone join-table adoption, `joinTableNaming`, `db.relationName` — the map already ruled out of scope. This is the same "replaced, not translated" move ADR-0040 made on the field-builder contract and ADR-0043 made on the non-FK side of a one-to-one.
- **The app authors the junction as an ordinary list**: two to-one relationships, a surrogate id, and `db.indexes: [{ fields: [a, b], unique: true }]` for the pair invariant — an API that already exists and that ADR-0040 froze in place. The junction is a real list, so it gets real access rules under ADR-0013, rather than being a synthesized table the access engine cannot see.
- **ADR-0018 is amended, not superseded.** Across an explicit junction there is no disconnect: removing an edge deletes the junction row, gated on the junction list's own delete access. The non-destructive default survives in substance — removing an edge must not destroy an endpoint row — and `removeAction: 'delete'` keeps meaning "delete the far endpoint too".

## Why this is worth recording

The three constructs look like a porting exercise and are not. Each replacement moves a guarantee across a boundary: an id's shape moves from a Keystone inheritance to a deliberate choice, `updatedAt` moves from the database to the application, and a join table moves from something the generator synthesized to something the application owns and must secure. A future reader will find `updatedAt` stale after a manual `psql` write and reasonably assume a bug — it is not; it is this decision, and the trigger that would have prevented it was rejected because ADR-0040 deleted the only place it could have lived.

**Composite primary keys were considered and ruled out of scope.** A junction with `@@id([aId, bId])` is a better table than a surrogate id with a unique index, and it is what Prisma would have synthesized. But nothing in Prisma 8 forces the feature, and adopting it would end `id` being universal — every surface assuming `item.id` (admin URLs, MCP tool arguments, hook arguments, field visibility, ADR-0018's remove control) would need a key abstraction instead. That is a config-API effort in its own right, not a step on the route to Prisma 8. If it is ever taken up, one boundary is already drawn: a `relationship()` pointing at a composite-keyed list would be refused at generation rather than growing multi-column foreign keys through the include builder and every to-one filter.

Supersedes nothing. Amends ADR-0004 (its surviving defaults are re-recorded here on non-Keystone grounds) and ADR-0018 (junction-row removal). Resolves issue #1047. Numbered 0048: 0046 was taken by the streaming decision (#1054) and 0047 by the row-lock decision (#1050), both concurrently.
