# A transaction-boundary hook reports the outermost transaction

Status: accepted

A list's `afterTransaction` fires when the **outermost transaction the write participates in** settles, and reports **that** transaction's outcome — not the return of its own write. A write that joins a transaction it did not open (a **joined write**) has its `afterTransaction` deferred until the **transaction owner** — `context.transaction()`, or the Write Pipeline when it opened the transaction — observes the settle, and the owner then flushes it with the real outcome.

## Context

Two shipped features compose into a silently wrong result (issue #899). ADR-0010 makes every write transactional; ADR-0012 lets a caller span several writes in one interactive transaction by rebinding the secured context to the transaction client. Because a Prisma transaction client exposes no `$transaction`, a write inside that callback takes the Write Pipeline's "join, don't nest" fallback and runs directly against the active client. The transaction-boundary bracket did not know this: it treated its own `runTransaction()` returning as a **settle**, recorded `{ status: 'committed' }`, and ran `afterTransaction` immediately — while the outer transaction was still open and could still roll back. An external side effect dispatched on `'committed'` therefore escaped a rollback, which is precisely the failure the compensation bracket exists to prevent.

Triage established the defect is wider than the reported case. The hook-facing context's `db` is also rebound to the transaction client (so hook writes are atomic with the write, per ADR-0010), which means a hook issuing its own `context.db` write produces a joined write too. Reproduced with no interactive transaction anywhere: a `beforeOperation` writing a second list, then a throwing `afterOperation`, yields zero persisted rows and a `'committed'` `afterTransaction` on that second list. The rule is therefore stated over transaction ownership generally, not over `context.transaction()` specifically.

ADR-0012's claim that the boundary-hook semantics are unchanged under an interactive transaction was wrong; that line now carries a pointer here.

## Considered options

- **Defer to the owner's settle (chosen).** Existing hooks become correct with no application change, and the guarantee is one sentence. Costs a deferral queue threaded through the same context rebind ADR-0010/0012 already use, and moves when hooks fire.
- **Expose a "you are nested" signal and leave the hook firing eagerly.** Rejected: it leaves `status` lying and every existing hook broken until its author rewrites around a new flag. A flag whose meaning is "ignore the field next to me" is a worse contract than the bug.
- **Settle a self-failed write early** (fire `'rolled-back'` the moment the write itself throws, defer only successes). Rejected: correctness becomes provider-dependent. A write that throws _after_ its SQL ran, whose error the callback swallows before committing, is rolled back under PostgreSQL (the failed statement aborts the transaction) but not necessarily under SQLite. The uniform rule — `'committed'` if and only if the write succeeded **and** the transaction committed, with the write's own error taking precedence over the transaction's — holds on every provider.
- **Re-read the row at flush time** so a committed hook sees final state. Rejected: a query per deferred write, undefined behaviour when the row was later deleted, and it raises a scoping question (whose session?) for a read nobody asked for.

## Consequences

- **`afterTransaction` fires later, and can now say `'rolled-back'` where it always said `'committed'`.** The deferred `item` is the row **as that write persisted it**, not a re-read at commit time, so a later write to the same record in the same transaction leaves it stale. It is still surfaced, because discarding a value already in hand would break every hook that reads it.
- **A rejected `context.transaction()` no longer implies rollback.** If the transaction commits and a deferred hook then throws, `transaction()` rejects with `AfterTransactionError` over already-final data. Transaction errors keep precedence over hook errors, so a serialization failure still reaches the caller ahead of any hook error and a retry loop keyed on it is unaffected (**amended by ADR-0042**: on Prisma 8 that failure arrives as a stack-owned `SerializationFailure`, not as an unwrapped `P2034`) — but a retry loop that catches broadly would re-apply a committed transaction.
- **`afterTransaction` always receives a context bound to the base client**, never the transaction client. Compensation must not be written through the transaction that rolled back, and by flush time a transaction client is closed. **This held on the top-level path from the start; the joined path was fixed to match by issue #1348 — see the amendments below, which also narrow this from the "both halves of the bracket" the decision originally claimed to `afterTransaction` alone.**
- **The bracket is symmetric in pairing, not in time.** `beforeTransaction` stays eager — it runs before its write — so under an interactive transaction it runs with that transaction already **open**. A hook designed for slow external work therefore holds locks it was meant to avoid, and a base-client write from it can block on rows the transaction is writing. Both are documented hazards with one remedy: keep it fast, or hoist the external call above `context.transaction()`. Skipping the hook instead would take its compensator down with it.
- **One bracket per write, flushed in write order.** Brackets from separate writes never merge, since each already ran its own `beforeTransaction`; the existing per-write `(listKey, operation)` dedupe is unchanged.
- **An unowned join reports optimistically, and is the one case where the outcome is not a fact.** When the stack did not open the enclosing transaction — an application managing its own `prisma.$transaction`, or a test double that cannot open one — there is no settle signal and no owner to flush, so the hook fires at write time as before. Deferring instead would mean never firing, which is worse. The two cases are indistinguishable at runtime (a real transaction client and a bare mock present the same shape), so this is documented rather than warned about: a warning would fire on every correct mock-based test.

_Amended in place by [PR #1347](https://github.com/OpenSaasAU/stack/pull/1347) (issue #1156), in fact only: the base-client clause above **did not hold for a joined write**. Deleting the test doubles that had been hiding it showed the deferred hook is handed the joined write's own transaction-bound context; by flush time that transaction is closed, so a compensating write was refused with `Cannot use a transaction operation after the transaction has ended` rather than surviving the rollback it compensates for. The top-level path behaved as written. Which way the divergence would be resolved — the code moves to the rule, or the rule moves to the code — was left open as [#1348](https://github.com/OpenSaasAU/stack/issues/1348); resolved below in favour of the rule._

_Resolved by issue #1348: the code was fixed to match the rule, not the other way around — a security-sensitive boundary hook silently getting the wrong context is a worse contract than the deferral queue needed to fix it. But the fix is narrower than the original decision text above: only `afterTransaction` moves to the base client. `beforeTransaction` keeps running through whatever context the write itself carries — on a joined write, that context is already bound to the enclosing (still-open) transaction, which is exactly where an eager hook running before its own write is supposed to be. Forcing it to the base client too would trade a problem `beforeTransaction` doesn't have (its own bracket half was never the one that outlived a closed transaction) for the single-connection-pool contention the very next bullet already documents as a `context.transaction()` hazard — real risk for no gain, on every joined `beforeTransaction` that does its own `context.db` write, not just the ones with a compensator to run.

`AccessContext` carries an internal `_baseContext` pointer alongside `_transactionOwner`: `undefined` on a context that IS the base client, and set to the ultimate base whenever a context is bound to (or joins) a transaction — by the Write Pipeline's `bindContextToTransaction` for a write's own transaction, by `getContext`'s transaction-child construction for `context.transaction()`, and carried through unchanged by `sudo()`/`withSession()`. It is deliberately not itself the context a hook runs with: `resolveAfterTransactionContext` in `write-pipeline.ts` rebuilds `db`/`ormHandle` from `_baseContext`'s ormHandle/opener while spreading the ISSUING write's own context for everything else — `session`, `_isSudo`, `plugins` — so a joined write issued through `tx.sudo()`/`tx.withSession()` keeps that elevation for its own `afterTransaction` rather than silently falling back to the enclosing transaction's pre-elevation session. (An earlier version of this fix pointed hooks straight at the stored ancestor context and lost exactly that elevation — caught in review before landing.) `runWithTransactionBoundary` takes this resolved context as a distinct `afterTransactionContext` parameter, separate from the `context` parameter `beforeTransaction` still uses unchanged.

The three shapes are pinned in `packages/core/src/context/transaction-boundary.test.ts`, each proven falsifiable by reverting the corresponding piece of the fix: `a deferred compensator on a joined write runs its own write through the base client` (the `context.transaction()` join), `a deferred compensator on a hook-issued joined write runs through the base client` (a hook's own nested `context.db` write joining a top-level write's transaction), and `a joined write's own tx.sudo() elevation survives into its afterTransaction compensator` (the elevation-preservation case)._

_Amended by [ADR-0050](0050-nested-relation-input-leaves-the-secured-write-surface.md) in enumeration only: with nested relation input gone, walking the input tree for "the lists involved in this write" yields exactly one list. Everything else here is untouched — the deferral queue, the transaction-ownership rule and the unowned-join caveat were stated over transaction ownership generally, never over nesting. `context.transaction()` becomes the primary way to write several lists, so the joined-write path this record fixes goes from an edge case to the main road._
