# Field-level access fails closed on a non-boolean result

Status: accepted

`checkFieldAccess`, the single evaluator shared by every read and write path, handled a field rule's `false` and `true` results and then fell through to an unconditional `return true` for anything else. `FieldAccessControl`'s public type advertised a third legal result — a Prisma filter, `boolean | PrismaFilter<TItem> | Promise<...>` — so a rule written to scope access by row (`read: ({ session }) => ({ ownerId: { equals: session?.userId } })`) type-checked, was accepted by every caller, and silently granted the field full access instead. We decided the runtime and the type must agree, and chose to make field access reject a filter rather than evaluate one: `FieldAccessControl` now returns `boolean` only, and `checkFieldAccess` throws `InvalidFieldAccessResultError` for any result that isn't a strict boolean, in place of the old fallback (#913).

This was not a fresh design call so much as enforcing one already on record. ADR-0001 states the contract in as many words: "operation-level access returns `boolean | PrismaFilter` (a filter scopes rows), while field-level access returns `boolean` only (a denied field is removed, never used to exclude rows)." The type and the runtime had simply drifted from that sentence — an unused `matchesFilter` helper sitting in the same module, written to evaluate exactly the filter case and called by nothing, was the clearest evidence the drift was accidental rather than a considered relaxation.

## Considered options

- **Reject the filter (chosen).** Narrow `FieldAccessControl` to `boolean | Promise<boolean>`, delete the dead `matchesFilter` helper, and throw `InvalidFieldAccessResultError` for any non-boolean result reaching the evaluator. A rule that needs to depend on the row or the write payload evaluates the condition itself and returns a boolean — which every existing field rule in this codebase and its examples already does. This matches ADR-0001's stated contract instead of extending around the bug, and it makes the `create` case (no `item` to test a filter against) a non-issue rather than a special case to design: neither operation ever honours a non-boolean, so there is nothing to answer only for `create`.
- **Honour the filter.** Wire the unused `matchesFilter` helper (or a real filter evaluator) up to `item`, so a filter-returning rule means what its author wrote. Rejected: it contradicts ADR-0001's field-visibility/row-filter split directly, `matchesFilter`'s own implementation only understood `equals`/`not` and would need to grow into a second, partial reimplementation of Prisma's filter language to be trustworthy, and `create` has no `item` to evaluate against — honouring the filter everywhere else and falling back to something else for `create` reintroduces exactly the kind of per-operation special case ADR-0001 avoided by giving field access one evaluator across every path.
- **Deny silently instead of throwing.** Return `false` (as though the rule denied the field) rather than throw. Rejected: a filter-returning rule is a config bug, not a session this session is being denied — silently hiding the field reads as "working as configured" and can sit undiscovered for a long time, the same failure mode the codebase already rejects at the write path (#568: a denied field throws rather than being silently dropped) and in the read pipeline for unscopable includes (ADR-0022). Throwing surfaces the bug at the first evaluation, in development, rather than shipping a field that quietly never appears.

## Consequences

- **This narrows a public type.** `FieldAccessControl`'s return type drops `PrismaFilter` from its union. A config that returned a filter from a field rule stops compiling; nothing in this repository's packages or examples did, and the previous behaviour for anyone who had was already the bug this record fixes (silent full access), so there is no correct existing usage this displaces.
- **The evaluator throws, it does not return `false`, when a non-boolean reaches it.** `InvalidFieldAccessResultError` is a sibling of `AccessScopeDepthExceededError` and `ResolveOutputCycleError` (ADR-0022, ADR-0023): a loud engine failure distinct from `ValidationError`, because this is not bad user input, it is a rule that cannot be interpreted as an access decision at all. Callers that already distinguish thrown errors from `false` (`filterWritableFields`'s #568 throw, the write pipeline, `nested-operations.ts`'s connect gate) need no further change; the admin UI's `isFieldPotentiallyWritable` already treats any throw from `checkFieldAccess` as "cannot decide statically, keep the affordance" and defers to the secured commit, which now throws for real instead of silently widening access.
- **`sudo` is unaffected.** `checkFieldAccess` still short-circuits to `true` before a sudo context ever calls the field rule, so a sudo-invoked filter-returning rule never reaches the throw.
- **`matchesFilter` is deleted, not wired up.** It was dead code with a real security cost — an evaluator sitting next to a fail-open default it was clearly meant to close and didn't — so once the type stops admitting filters at all, keeping it around as unreachable code would only replace one form of a "reads as coverage that does not exist" with another.
