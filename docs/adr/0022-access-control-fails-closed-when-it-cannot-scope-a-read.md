# Access control fails closed when it cannot scope a read

The read-side Access Filter (`buildIncludeWithAccessControl` / `mergeIncludeWithAccessControl` in `packages/core/src/access/access-filter.ts`) recurses to a bounded depth (`READ_INCLUDE_MAX_DEPTH`, currently 5) when auto-scoping relation `include`s, and used to signal "I could not compute a scope here" with the same bare `undefined` it also returned for two unrelated, benign cases: a list with no relationships, and a read issued from inside a `resolveOutput`/virtual-field context (to prevent hook-triggered infinite loops). `mergeIncludeWithAccessControl` treated all three identically — "nothing to merge against, pass the caller's `include` through unchanged." For the depth-cap case that default is wrong: a caller-supplied `include` naming a relation at or past the cap was returned to the database **unscoped**, with no row filter and, independently, with its own field-level `read` access and `resolveOutput` hooks never evaluated by the post-query phase (`filterReadableFields`, which capped its own recursion at the same depth). The two independent caps happened to line up, so the leak compounded: unfiltered rows carrying unfiltered fields (issue #830).

We decided the engine **fails closed** at this boundary: `buildIncludeWithAccessControl` returns a discriminated result (`scoped` / `nothing-to-scope` / `depth-exceeded`) instead of an overloaded `undefined`, and `mergeIncludeWithAccessControl` throws a new `AccessScopeDepthExceededError` when a caller explicitly names a relation the engine hit `depth-exceeded` trying to scope. The **auto**-include (no caller `include` at all) stays silent when it hits the cap — nothing unscoped is returned, the relation is simply not fetched, and throwing there would make deep schemas unreadable by default. Inside a `resolveOutput`/virtual-field context, the builder now **scopes without expanding**: each relation still receives its own access `where`, but the builder does not recurse into that relation's own nested relations — preserving the original loop-prevention (no recursive include-building means a self-referential relation still terminates) while closing the "no scoping at all" gap that was the second, more easily triggered half of #830. The post-query phase (`filterReadableFields`) no longer caps its own recursion at all: by construction, everything it walks is a materialized, finite, acyclic tree bounded by whatever the (now fail-closed) pre-query phase permitted, so a separately-tracked cap there was redundant and was the mechanism that let a correctly row-scoped relation still return unfiltered fields.

## Considered Options

- **Raise or remove `READ_INCLUDE_MAX_DEPTH`**: doesn't fix the bug, only moves the cliff — a caller could always nest one level deeper than whatever the new limit is. The cap exists as a cost bound (unbounded caller-supplied nesting is a resource-exhaustion vector independent of access control) and stays.
- **Make the depth cap configurable per app**: same objection — configurability changes where the cliff is, not whether falling off it fails open or closed.
- **Silently drop the relation past the cap instead of throwing**: considered and rejected for the **caller-include** case specifically. A caller who explicitly asked for a relation and silently got back `undefined`/absent data has no signal that anything was denied versus "the relation doesn't exist" or "there's no data" — the same silent-failure argument the stack already applies to denied operations elsewhere, but here the _right_ behavior is closer to a thrown, developer-visible error than to Keystone-style "no field/`[]`" semantics: this is a structural query shape the engine cannot express safely, not a per-row access decision. The **auto**-include (no caller ask) does still drop silently, matching every other silent-failure precedent in the stack.
- **Log a warning and pass the unscoped data through anyway**: rejected outright — a warning that nobody is watching in production is exactly the "invisible failure" the issue calls out. If the engine cannot prove a read is scoped, it must not return it.
- **Collapse the two write-side `MAX_DEPTH` declarations (`nested-operations.ts`, `transaction-boundary.ts`) into the same constant as the read-side cap**: rejected. They bound conceptually different things — nested-write payload depth is a cost bound with no access-control meaning, while the read-include cap is now a security boundary. Named separately (`NESTED_WRITE_MAX_DEPTH` vs `READ_INCLUDE_MAX_DEPTH`) so a future change to one doesn't silently retune the other. The write-side gap this ADR does **not** address (`processNestedOperations` has the same "silently stops" shape, unverified for a write-side leak) is tracked separately as issue #835.

## Consequences

- `AccessScopeDepthExceededError` (exported from `@opensaas/stack-core`) is a new failure mode application code may need to handle for reads with a caller-supplied `include`: it is distinct from `ValidationError` (this is not a user-input validation failure — the read may be perfectly well-formed, the engine simply cannot prove it is safe to scope) and from the framework's usual "return `null`/`[]`" silent-denial convention (this is a structural rejection, not a per-row access decision, so it is loud on purpose).
- This is a **behavior change**, not just a bug fix in the conventional sense: a read that previously returned deeply-nested data (unscoped, which was the bug) now throws instead. Any application relying on a caller `include` nested past the cap — which could only ever have been relying on the unscoped leak, since the alternative was never available — must restructure that query into separate, shallower reads. Shipped as a **minor** version bump on `@opensaas/stack-core` with the changeset leading with this behavior change.
- A read issued from inside a `resolveOutput` hook now carries real row-scoping (an access `where` per immediate relation) where it previously had none at all. Hook authors who relied on an _unscoped_ nested read from inside `resolveOutput` (again, only reachable via the bug) will now see a narrower result set.
- `filterReadableFields`'s own depth cap is gone; its only remaining bound is whatever `include` shape the pre-query phase produced. A cyclic **schema** does not create a cyclic **result** — Prisma materializes a fresh object per fetched relation — so this is safe as long as the pre-query phase's own cycle guard (`buildIncludeWithAccessControl`'s `visitedLists` back-edge check) stays correct; that guard is a separate, already-correct mechanism this change does not touch.
- The distinction the code now encodes — `scoped` vs `nothing-to-scope` vs `depth-exceeded` — replaces a single overloaded `undefined` return. `buildIncludeWithAccessControl` and `mergeIncludeWithAccessControl` are package-internal (not exported from any public entry point), so this signature change carries no semver cost of its own; only the new thrown-error behavior does.
