# The dev database is a stack-run in-process Postgres, shared with the test harness

Status: accepted

> **Amended 2026-09-03 by [Prototype opensaas dev over pglite-socket](https://github.com/OpenSaasAU/stack/issues/1112)** (Prisma 8 map). The graduated verification set ran against `@electric-sql/pglite@0.5.8` / `pglite-socket@0.2.11` and `prisma@8.0.0-rc.12`, and corrected one decision: **query-level serialisation is not connection isolation.** `pglite-socket` multiplexes every TCP connection onto one PGlite backend — a single Postgres session — so `pg`'s default pool (which uses several connections concurrently, each relying on session-global state: the unnamed prepared statement, the unnamed portal, the transaction) corrupts itself against it (`unnamed prepared statement does not exist`, `bind message supplies N parameters`, `portal "" does not exist`, `create() did not return a row`). `maxConnections` ≥ pool size stops connection *rejection*; it does nothing about this. The fix is to drive the dev database through **one connection** — the generated runtime passes `pg: new Pool({ max: 1 })` on the `'dev-database'` path, i.e. ADR-0049's `db.client.pg` lever, not just a raised sidecar `maxConnections`. See the Verification bullet in Consequences for the full result set.

[ADR-0003](0003-deployment-uses-postgres-and-prisma-migrate.md)'s amendment bought the local loop on `prisma dev`: a CLI-owned, PGlite-backed Postgres with nothing to install, which is what the cold-clone claim rides on. The Prisma 8 CLI has no such command — `prisma dev <entry>` is Prisma Composer's app runner and refuses without an entry — and the only route left to Prisma's PGlite is `startPrismaDevServer()` from `@prisma/dev`, which Prisma labels undocumented and unstable. This record decides that **the stack runs the dev database itself**, over `@electric-sql/pglite` and `@electric-sql/pglite-socket` — the same in-process Postgres [ADR-0057](0057-engine-tests-run-against-an-in-process-postgres-through-the-clients-construction-options.md) already stands up for `pnpm test` — from one core module that `opensaas dev` and the test harness both call. The `DATABASE_URL` escape survives with one meaning: set it, and no dev database starts.

## Context

The facts behind this were gathered on [#1070](https://github.com/OpenSaasAU/stack/issues/1070) and [#1095](https://github.com/OpenSaasAU/stack/issues/1095) against `prisma@8.0.0-rc.12`, `@prisma/dev@0.25.2` and `@electric-sql/pglite-socket@0.2.11`:

- `@prisma/dev` is a wrapper over the primitive ADR-0057 uses. It depends on `@electric-sql/pglite@0.4.3` and `@electric-sql/pglite-socket@0.1.3`; its "one connection at a time" is the socket server's `maxConnections`, set from its own `connectionLimit`. What it adds — a named-server registry, a `prisma+postgres://` HTTP endpoint, a shadow database for a `prisma migrate dev` that no longer exists, and `@experimental` WAL, streams and query-insight surfaces — has no consumer here, and adopting it would carry two PGlite versions in one install beside the harness's `0.5.8`.
- PGlite via either route ships pgvector: `CREATE EXTENSION vector` and the distance operators work, and `prisma db init` installed the extension through its contract space. The extension caveat that carved out the RAG examples is gone.
- The socket server binds TCP or a unix socket, so Windows is a TCP binding rather than an unsupported platform. Queries are serialised across connections in one WASM heap, and a connection holding an open transaction holds the queue — the first-use contract-marker deadlock ADR-0057 recorded carries over to any app on the same primitive.
- PGlite's data directory is opened by one process at a time. Every other process — `prisma db update` in a second terminal, a seed script, `psql` — reaches the database through the socket or not at all.
- The current cold start is three steps, not two: the scaffolder auto-runs `generate` then `db:push`, and every example README lists `generate`, `db:push`, `dev`. Under Prisma 8 the middle step needs a reachable database, so something has to start PGlite before `db update` can run.
- `opensaas dev` already exists in the CLI as a config watcher that regenerates on change; no example's `dev` script uses it.

## Decisions

- **The stack owns the dev database.** Core exports `startDevDatabase({ dataDir, extensions, maxConnections })` on its own subpath, starting an in-process PGlite behind a `pglite-socket` server on a free loopback TCP port. `opensaas dev` and ADR-0057's `createTestContext` both call it, so the dev loop and the engine suite are one primitive, one version and one set of workarounds. `@prisma/dev` is not used; the instability argument ADR-0003 raised against it stops applying to a loop that never imports it.
- **`opensaas dev` is the loop.** It starts the dev database, runs `generate` (which shells to `prisma contract emit`) and `prisma db update`, spawns the app command — `next dev` by default, `opensaas dev -- <command>` otherwise — and keeps watching `opensaas.config.ts`. The child is **not** handed a `DATABASE_URL`: it finds the database through the same state-file lookup every other process uses, which is what lets the generated runtime tell a dev database from an escape. A config change regenerates **and reconciles again**, and **generation is staged behind reconciliation**: the watcher emits the new contract to a staging location, plans `db update` against it, and only promotes the contract and the generated bundle into place once the plan has applied — so the app never reloads a contract the database does not carry. A destructive plan on boot stops with Prisma's consent prompt; a destructive plan mid-session, inside the watcher, leaves both the bundle and the database at the previous schema, prints the plan and the `pnpm db:update` instruction, and leaves the app running rather than prompting into interleaved output. `pnpm db:update` is therefore the stack's `opensaas db update`, which passes consent through to Prisma and promotes the staged artifacts on success. It is a foreground sidecar: no daemon, no start/stop commands, no registry; the database dies with the process. Every example's `dev` script becomes `opensaas dev`.
- **The cold start is `create` then `dev`.** The scaffolder's post-step shrinks to install and `generate`; the first `pnpm dev` creates and reconciles the database. `pnpm db:update` stays for mid-session schema edits and **requires the dev loop to be running**, failing with a clear message otherwise. It does not open the data directory in-process as a fallback: that would be a second way into the same store.
- **Discovery is one rule: `DATABASE_URL` set means no dev database.** The generated `prisma.config.ts` and `.opensaas/context.ts` both call one core helper, `resolveDatabaseUrl()`, which returns the URL **and its provenance** (`'env' | 'dev-database'`): the environment variable if set; otherwise the state file the sidecar wrote at `.opensaas/dev-db.json` (URL and pid); otherwise a **throw** naming both remedies. A deploy that forgets the variable gets that error, never a silent PGlite. Ports are never fixed — twelve examples under the root `pnpm -r --parallel dev` each get their own — and Next finds the database through exactly the lookup a seed script or a second-terminal `db update` does, since the sidecar injects nothing. A project using ADR-0049's `db.client.pg` factory is on serverless Postgres and sets the variable itself; the factory is untouched.
- **Persistence is the data directory, reset is deleting it.** `.opensaas/dev-db/` survives restarts and is already gitignored through `.opensaas/`; `pnpm clean` removes it. There is no reset command: the map's standing rule is that dev databases are recreated and reseeded, never migrated.
- **`verifyMarker: false` on the dev database only.** The generated runtime disables Prisma's first-use contract-marker read when `resolveDatabaseUrl()` reports `'dev-database'` provenance — never on a URL string's shape, which is why the sidecar must not inject one — because the sidecar's own `db update` verified and signed the marker moments earlier and the read would deadlock a first request that opens a transaction — `context.transaction` is the main road under ADR-0050. On the escape, Prisma's default stands.
- **The escape hatch is re-derived to one purpose.** ADR-0003 justified `DATABASE_URL` on four cases. pgvector leaves it (the loop runs the RAG examples; how the extension space is materialised is [#1096](https://github.com/OpenSaasAU/stack/issues/1096)'s). e2e leaves it locally — Playwright against a production Next build is many connections but serialised queries, which the sidecar takes once **the app itself holds a single connection** (`pg` pool `max: 1`; see the 2026-09-03 amendment — raising the sidecar's `maxConnections` alone is not enough). Windows leaves it provisionally, on the TCP binding, pending the verification below. What stays is **a Postgres the stack does not own**, chosen for parity or contention: CI, the row-lock gate, real pool concurrency. Never because the loop cannot do something.
- **CI keeps service containers, on parity.** The single-connection limit and the unstable-API argument are both gone; the container is justified because the scaffold declares PostgreSQL ≥ 15, PGlite reports 17.5, and production is a real Postgres with extensions installed the production way. The image is pgvector-capable at Postgres 17. The nightly cold-clone job is the one place CI exercises the sidecar, and that is its purpose.

Settled here without a decision turning on them: the database is PGlite's one database, `postgres`, so `db update`'s consent token is `postgres`; `maxConnections` is 20 — headroom for the several single-connection clients that share the sidecar (the app on its `max: 1` pool, the CLI, seeds, a `psql`), since the 2026-09-03 amendment pins the app to one connection rather than a pool of ten; the state file is rewritten on every boot and its pid lets a stale one be ignored.

## Considered options

- **A stack script over `startPrismaDevServer()` (`@prisma/dev` ≥ 0.25.2).** Cross-process lookup by server name and concurrent connections for free. Rejected: the unstable label is real, the extras have no consumer, and it pins a second PGlite beside the harness's — the one-primitive argument is exactly what it gives up.
- **A Prisma Composer entry so `prisma dev <entry>` works as documented.** Rejected: the stack's dev loop would become Composer's app model with Next as a node inside it, and the Composer path is documented as unsupported on Windows.
- **Drop the cold-clone claim; the escape is the only loop.** Rejected: it trades the zero-install property for all twelve database-backed examples to avoid shipping a runner the test harness already needs.
- **No stack code: `pglite-socket`'s own `pglite-server --run "next dev" --include-database-url`.** The honest minimum, and it works. Rejected: the injected URL reaches only the child, so a second-terminal `db update` needs a fixed port in `.env`, which collides across examples and with a real Postgres on 5432 — discovery is precisely the part a stack CLI exists to own.
- **A detached daemon (`opensaas db start`/`stop`).** Survives app restarts but needs lifecycle commands, a registry and an is-it-already-running story; Prisma 7's `--detach` shape. Rejected for the foreground sidecar's absence of state.
- **A separate `opensaas db serve`, leaving `dev` as the watcher.** Rejected: reconcile-on-change is what the watcher was missing, and one process tree is the point.
- **A warm-up query instead of `verifyMarker: false`.** Rejected: it papers over a check that buys nothing after the sidecar's own `db update`, at the cost of an unexplained statement on every boot.
- **Injecting `DATABASE_URL` into the spawned app**, the `pglite-server --run` shape. Rejected on review: the child would take `resolveDatabaseUrl()`'s env branch, be indistinguishable from an escape, and keep the marker check the deadlock fix depends on removing.
- **Generate first, reconcile second, in the watcher.** Rejected on review: a refused destructive plan would leave Next reloaded onto a contract the database does not carry, with the marker check that would have caught it switched off. Reverting the bundle after the fact was rejected in favour of never writing it early.

## Consequences

- **ADR-0003 is amended a third time**: its local-database bullet and CI paragraph now point here, and items 1 and 3 of its verification gate are closed by this record. **ADR-0057 is amended**: the harness calls the same `startDevDatabase`, and its rejection of `startPrismaDevServer()` is now the dev loop's rejection too. **ADR-0014 is amended**: the one shared module for connection selection is `resolveDatabaseUrl()`. `CONTEXT.md` gains **Dev database** and **Database escape**.
- **A verification set was graduated as a prototype** ([#1112](https://github.com/OpenSaasAU/stack/issues/1112)) because the shape of `opensaas dev` is itself something to react to. **Verification (2026-09-03, throwaway prototype on `pglite@0.5.8` / `pglite-socket@0.2.11` / `prisma@8.0.0-rc.12`):**
  - **Next's pool + concurrent `db update` — passes only with the app on one connection.** With the default `pg` pool the app fails under any real create/edit/delete load, and a second-process client (a seed, a concurrent `db update`) crashes it (see the 2026-03 amendment for the mechanism). With `pg` pool `max: 1` the app runs cleanly through a concurrent transaction + `.include()` mix (72/72), two independent single-connection sessions coexist (120/120), and a single connection at 32-concurrent is clean (192/192). This is the load-bearing correction; `maxConnections: 20` on the sidecar stays, but only as headroom for the *other* single-connection clients (seed, `psql`, a second-terminal `db update`), not to let the app pool spread.
  - **`verifyMarker` deadlock — reproduces and the fix holds.** With the default (`onFirstUse`) marker, a first request that opens `context.transaction` stalls past 8s; with `verifyMarker: false` on the `'dev-database'` path it returns in ~15ms. Next's generated context took the state-file branch with no inherited `DATABASE_URL` (`provenance: 'dev-database'`, `envDatabaseUrl: null`), which is what makes the marker suppression targetable.
  - **Staged reconcile under a destructive edit — mostly holds, one build rider.** The watcher stages the emit, plans it, sees `operationClass: 'destructive'`, promotes nothing, prints the plan and the `pnpm db:update` instruction, and Next keeps serving the old schema. `opensaas db update --confirm postgres` applies and promotes (the consent token is the database name, `postgres`). **But** the already-running Next keeps its cached client and then queries the dropped column (`column Post.note does not exist`, 500) until the process restarts — a fresh process and the on-disk contract are consistent, so **the loop must restart the app child after a destructive promote**; HMR does not refresh a client cached across it. Two mechanics for the build: `db update --to` takes a hash/ref/dir name, **not a file path**, so staging is Prisma's emit-beside-source plus the config's contract path, not a `--to <staged.json>`; and the CLI keeps a `migrations/` graph whose advanced ref can shadow the source contract, so the loop must control refs (or the ghost of a prior schema reappears in the plan). The sidecar's CLI spawns must be **async** — a `spawnSync` blocks the event loop the socket is served on and deadlocks the first `db update`.
  - **`psql` — connects, no hang.** libpq 14.20's `psql` connects to `pglite-socket@0.2.11`, reports `PostgreSQL 18.3 (PGlite 0.5.8)`, runs single statements and multi-statement scripts, and a `psql` transaction correctly holds the query queue while a second `psql` waits (~2.5s for a 3s `pg_sleep`). The #1070 hang was `@prisma/dev`'s `0.1.3`; the docs can offer a `psql` recipe against the Dev database.
  - **Twelve sidecars at once — no collision.** Twelve `startDevDatabase` instances came up on twelve distinct free ports, each answered `select 1`, no port/state-file/WASM-memory collision (~8s wall for all twelve).
  - **Windows — unverified.** The prototype ran on macOS; no Windows machine or CI was available. ADR-0003's Windows-on-the-escape line stays provisional until this is run on Windows.
- **The consumer sweep widens.** `packages/cli/src/commands/dev.ts` gains the sidecar, the staged reconcile and the spawn, and the CLI gains `db update` as the promoting wrapper `pnpm db:update` points at; core gains the `startDevDatabase` and `resolveDatabaseUrl` modules, with PGlite, `pglite-socket` and `pglite-pgvector` optional peers of core and regular dependencies of the CLI at one pinned version; the generator emits `resolveDatabaseUrl()` into `prisma.config.ts` and `.opensaas/context.ts` and, on the `'dev-database'` path, both passes `verifyMarker: false` and binds the client to a single-connection pool (`pg: new Pool({ max: 1 })`) — see the 2026-09-03 amendment; the dev loop restarts the spawned app after a destructive promote so the running client stops querying a dropped column; every example's `dev` script becomes `opensaas dev` and every README drops its `db:push` step; the scaffolder's post-step drops `db:push`; `.env.example` files stop shipping a default `DATABASE_URL`; the e2e global setup and its `db.ts` seed through the lookup; the nightly cold-clone job exercises `create` then `dev`; CI images move to a pgvector-capable Postgres 17.
- **`pnpm db:update` changes meaning.** It was a command you ran before `dev`; it is now a command you run _during_ `dev`, and it says so when nothing is listening.
