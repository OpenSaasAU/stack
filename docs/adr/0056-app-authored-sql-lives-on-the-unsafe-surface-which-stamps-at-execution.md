# App-authored SQL lives on the Unsafe surface, which stamps a plan when it executes it

Status: accepted

[ADR-0045](0045-vector-search-is-an-engine-owned-terminal-over-a-native-vector-column.md) chose a public `context.sql` mid-discussion and superseded it within the same session: once `nearest()` was engine-owned, the seat had no consumer, and it was recorded as fog with two triggers — a second consumer appears, or the tripwire proves unable to see SQL built outside the engine. Neither fired as recorded, and the second **inverted**: [#1073](https://github.com/OpenSaasAU/stack/issues/1073) measured that raw plans reach `beforeCompile`, and this record establishes that typed `db.sql` plans do too, carrying the same structured AST the ORM lane mints. The question therefore has a structural answer that does not rest on demand, and we are closing it on those grounds rather than deferring it again.

**No scoped seat is built. The Unsafe surface is the address for every application-authored SQL query, typed or raw.** It hands out Prisma's typed SQL builder and raw tag untouched, executes their plans through executors it owns, and applies the intentionally-unscoped stamp **at execution** — a plan is an unstamped value until the surface runs it, and no application ever writes a stamp. The surface has a transaction-bound shape. The secured surface gains no SQL escape of any kind.

## What typed SQL adds is exactly what the engine cannot scope

Read against `8.0.0-rc.8` (`@prisma/orm-family-sql`; paths are Prisma's monorepo):

- A `db.sql` query builds to a `SqlQueryPlan` with `meta.lane === 'dsl'` (`packages/2-sql/4-lanes/sql-builder/src/runtime/builder-base.ts:193`) whose AST is the same `SelectAst`/`InsertAst`/`UpdateAst`/`DeleteAst` class the ORM lane produces (`:154-198`), with `withWhere` on select, update and delete (`packages/2-sql/4-lanes/relational-core/src/ast/types.ts:1655`, `:2033`, `:2093`). Every plan handed to an executor runs the middleware chain (`packages/2-sql/5-runtime/src/sql-runtime.ts:291-307`). So the tripwire sees a typed query — and, because it is structured, could in principle rewrite one.
- Over the `Collection`, the builder adds joins of every kind (`packages/2-sql/4-lanes/sql-builder/src/types/shared.ts:55-104`), `groupBy`/`having` (`types/select-query.ts:55-64`, `types/grouped-query.ts:50-55`), arbitrary projection expressions (`types/shared.ts:36-53`), `EXISTS`/`IN` subqueries (`runtime/functions.ts:215-226`), `fns.raw` fragments (`:227`), `DISTINCT ON` (`types/select-query.ts:66-80`), and `RETURNING`/`ON CONFLICT` on mutations (`types/mutation-query.ts:49-101`). It has no lock clause, no CTE, no `UNION`, and no window-function builder.
- Its results **are** codec-decoded: decoding is selected by AST kind, not lane (`packages/2-sql/5-runtime/src/codecs/decoding.ts:104-146`), and each projection item carries a `CodecRef` resolved from contract storage. The raw lane decodes too, from the author-declared `returnsRow` spec (`:77-102`); only `affectedCount()` is undecoded (`:81-83`). [#1031](https://github.com/OpenSaasAU/stack/issues/1031)'s note that SQL-builder rows skip decoding is corrected here.

Set the two lists side by side. A typed query the engine _could_ scope — one table, a predicate in the Where vocabulary, a projection of that table's columns — is already what `where()` and `.select()` express on the secured surface under [ADR-0055](0055-the-secured-surface-accepts-a-where-vocabulary-the-engine-lowers.md). Everything the builder adds beyond that is the set [ADR-0041](0041-the-secured-surface-is-an-opaque-wrapper-over-a-prisma-8-collection.md) excluded `groupBy` for: Field Visibility has nothing to apply to a projected expression, a grouped result leaks the shape of denied rows, and a raw fragment is opaque. A scoped seat over typed SQL would admit only the subset that needs no seat.

## Why a scoped seat is rejected on the mechanism as well

It is not merely redundant; each step of building it is a fail-open trap of the family ADR-0045 deleted `prismaFilterToSQL` for.

- **A second lowering of the Where vocabulary.** ADR-0055 lowers the vocabulary onto Prisma's where lambda in one place, total or throwing. Scoping a `SelectAst` means lowering the same vocabulary onto SQL-AST expressions — two interpreters of one rule kind, the drift ADR-0030, ADR-0031 and ADR-0044 each spent a record eliminating.
- **`withWhere` replaces the whole clause.** `SelectAst.withWhere` constructs a new AST with the given `where` (`ast/types.ts:1655-1657`); preserving the caller's predicate means reading `ast.where` and re-ANDing, which Prisma's own docstring recommends (`packages/2-sql/5-runtime/src/middleware/sql-middleware.ts:41-45`) and which is exactly the hand-merge ADR-0055 removed from the secured surface.
- **Outer joins move the predicate.** Scoping a left-joined table in `WHERE` turns the join inner; the scope belongs in `ON`. So the seat would have to rewrite join conditions per alias — a middleware can resolve an alias to a list (`ctx.contract.domain.namespaces[ns].models[M].storage` carries `{ table, namespaceId, fields }`), but there is no shipped reverse index, and the rewrite is a query planner we would own.
- **Column refs are ambiguous inside `EXISTS`.** ADR-0055 already found `collectColumnRefs()` tags refs inside an `EXISTS` with the child table only, so ADR-0031's denied-field walk cannot tell whose column a self-referential subquery names.
- **The session cannot reach `beforeCompile`.** ADR-0045 rejected auto-injection there for SQL plans; a scoped seat would therefore be a _terminal_ that accepts an app-built plan — and a terminal that refuses most of what the builder can express is the dishonest passthrough ADR-0041's subset principle exists to prevent.

## The Unsafe surface's SQL shape

- **It carries the builders untouched.** Prisma's typed builder (`sql`) and raw tag (`raw`) are passed through; there is no curated subset, because the point of this surface is total fidelity with the cost stated. `fns.raw` fragments, `RETURNING`, `DISTINCT ON` — all reachable.
- **It owns the executors.** Rows come from `query(plan)` and statistics from `execute(plan)`, the pair Prisma defines on `RuntimeScope` (`packages/2-sql/4-lanes/relational-core/src/runtime-scope.ts:23-26`). The bare client exposes neither directly — its keys are `sql, orm, enums, nativeEnums, raw, context, contract, stack, connect, runtime, prepare, transaction, close` (`packages/3-extensions/postgres/src/runtime/postgres.ts:56-74`) and rows come from `db.runtime().query(plan)`. The Unsafe surface does **not** hand out the bare client: `runtime()` and `prepare` are not exposed. This is ADR-0041's opacity argument applied to the audited surface — it can only promise to stamp what it executes if its executors are the only ones reachable. `prepare` stays out until [#1076](https://github.com/OpenSaasAU/stack/issues/1076) decides what a once-at-`prepare()` `beforeCompile` means.
- **`query()` returns Prisma's own `AsyncIterableResult`**, unchanged. [ADR-0046](0046-a-secured-read-materialises-and-does-not-stream.md) named this surface as the destination for a caller that needs a cursor; this is its spelling.
- **The ORM lane on this surface is out of this record's scope.** [ADR-0049](0049-extension-packs-are-declared-the-tripwire-is-stack-owned.md) says the Unsafe surface stamps every ORM query it builds; ORM terminals execute themselves, so that stamp cannot be applied by these executors and its mechanism is #1076's to reconcile with the tripwire's fate. _Resolved by [ADR-0059](0059-the-engine-stamp-is-an-ambient-origin-the-executing-surface-enters.md): the ORM lane is a transparent Proxy over Prisma's `orm` that enters the unsafe origin around every call, so "does not hand out the bare client" now covers `orm` as well as `runtime()` and `prepare`._

## The stamp is applied at execution, not at build

- Every typed query kind carries `.annotate()` (`types/select-query.ts:36-38`, `types/grouped-query.ts:35-37`, `types/mutation-query.ts:46-48`, `:68-70`, `:91-93`), but **the raw lane has none** — a `RawRowQuery` is `returns`/`buildAst`/`build` and a `RawAffectedCountQuery` is `build` alone (`packages/2-sql/4-lanes/sql-builder/src/types/raw-query.ts:122-143`), and `planFromAst` never writes an `annotations` key (`packages/2-sql/4-lanes/relational-core/src/plan.ts:47-56`).
- **Every built plan is frozen** — `plan`, `plan.meta` and `plan.meta.annotations` (`builder-base.ts:188-197`). Nothing can annotate a plan after `.build()` except by constructing a new plan object, which the executors accept since they take any `SqlOrmPlan`. #1073 measured that a copied raw plan carrying a hand-attached `meta.annotations` survives to `beforeCompile` and reads back.
- So the one mechanism that covers both lanes uniformly is **the executor copying the plan with the intentionally-unscoped stamp before handing it to the runtime**. A plan is an unstamped value until the surface executes it. An application never calls `.annotate()` for the stamp; the typed builder's `.annotate()` stays available for the application's own audit metadata, in its own namespace.
- **This is a constraint handed to #1076, not a decision about the tripwire.** Whatever the tripwire becomes, the Unsafe executor is the one place a non-engine plan acquires its mark. It is robust to every option that ticket lists: under narrowing or an async-context origin the executor is still the audited act, and under stack-built plans it is the same copy-and-stamp the engine would use for its own raw statements — which is also the only way [#1077](https://github.com/OpenSaasAU/stack/issues/1077)'s raw row lock can be stamped, raw having no `.annotate()`.

## Amendment — the executor enters the origin instead of copying the plan (ADR-0059)

[ADR-0059](0059-the-engine-stamp-is-an-ambient-origin-the-executing-surface-enters.md) took the async-context option. "The executor is the audited act" survives exactly; the copy-and-stamp mechanism above does not. `query(plan)` and `execute(plan)` enter the unsafe origin around the execution they perform — a plan is an unmarked value until the surface runs it, as before, and no application writes a mark, as before. `query()` keeps returning Prisma's lazy `AsyncIterableResult` as the section above requires, through a scope-preserving wrapper whose `then`/`next` re-enter the origin, because the result executes on first consumption and a naive return would close the scope first (measured: refused naively, covered wrapped, streaming intact) — and the engine's own raw statements, [#1077](https://github.com/OpenSaasAU/stack/issues/1077)'s lock included, are covered by their terminal's scope rather than by a copied annotation. The typed builder's `.annotate()` stays available for an application's own audit metadata in its own namespace; nothing of ours reads it. `prepare` stays unexposed on the measured fact that a prepared statement executes with no `beforeCompile` at all.

## A transaction-bound shape

Prisma's `tx` is itself an executor (`PostgresTransactionContext` extends `RuntimeScope`; `postgres.ts:48-54`) and carries `sql`, `orm`, `enums` and `nativeEnums` — but **no `raw`** (`:341-372`). A raw statement inside a transaction is built from the client's raw lane, which is contract-scoped rather than connection-scoped (`createRawLane` runs once per client), and run through `tx.query`. The transaction context therefore carries a transaction-bound Unsafe surface with the same builders and executors bound to `tx`, closing over the client's raw lane. Without it a migration script or bulk re-embed inside `context.transaction` must close over the outer client and hand plans to a `tx` it cannot reach — the awkwardness [ADR-0047](0047-a-row-lock-is-an-engine-owned-two-statement-terminal.md) named. Same shape as the secured surface's second, transaction-bound interface under ADR-0032.

## The secured surface gains no SQL escape

No `fns.raw` fragment inside `where()`, no `sql()` terminal, no typed-SQL projection. ADR-0055 closed the vocabulary; this record confirms rather than reopens it. Any SQL reaching the secured surface would be the fail-open translator ADR-0045 deleted, under a new name.

## Demand is absent, and is recorded last

The repository's only application-authored SQL is `packages/rag/src/storage/` (deleted by ADR-0045), `examples/rag-openai-chatbot/scripts/install-pgvector.ts` (DDL, ported under ADR-0049) and a `$executeRawUnsafe('...')` placeholder in the plugin how-to's test example. Nothing in the tree would use a scoped SQL seat. ADR-0046's rule stands: absence of demand would justify deferring, never closing. The sections above are what close it.

## Considered options

- **A scoped terminal on the secured surface accepting an app-built single-table `SelectAst`.** Rejected on both counts above — its admissible subset is already the secured surface, and its mechanism is a second vocabulary lowering plus a join rewriter.
- **Both — a narrow scoped seat and the Unsafe address for the rest.** Rejected: the narrow seat admits nothing the secured surface lacks, and two addresses for one capability is the ambiguity a named destination exists to remove.
- **Handing out the bare client.** Rejected: `runtime().query(plan)` would execute an unstamped plan, so the stamp-at-execution guarantee would hold only by convention.
- **Stamping at build — typed queries via `.annotate()`, raw exempted by `meta.lane === 'raw'`.** Rejected: it puts the stamp at every application call site, the fail-open shape #1033 warned of, and a lane exemption is a tripwire decision (#1076) this record should not make from the SQL side.
- **Exposing `prepare()` now.** Rejected until #1076 settles the once-at-prepare hole; nothing in the repo prepares a statement.
- **Auto-injecting the access filter in `beforeCompile` for `dsl` plans**, now that they are known to be structured. Rejected for the reasons ADR-0045 already gave — no per-request session slot, no stability commitment, and an undeletable tripwire — which the new facts do not touch.
- **Re-recording the fog with a corrected trigger.** Rejected: the spec is handed off with a hole labelled "maybe", and a decision on demand is weaker than one on structure.

## Consequences

- **The cost is stated rather than discovered.** A query on this surface gets no access filter, no Field Visibility, no `resolveOutput`, no computed fields, no hooks. `execute()` returns statistics, not rows. Scoping is the caller's alone. What it does get: codec-decoded values, Prisma's streaming result, and the full builder.
- **`CONTEXT.md`'s Unsafe surface entry is rewritten.** Its "raw SQL is outside this entirely — raw plans never reach the tripwire" is false after #1073, and its "vector search runs here" was stale after ADR-0045 made `nearest()` engine-owned. The entry now names the SQL and raw lanes and the stamp at execution.
- **ADR-0045's `context.sql` option is amended** to point here; **ADR-0046's "the Unsafe surface is the named answer" gains its spelling.** ADR-0038's raw-observability paragraph is deliberately **not** amended here — #1076 already owns that correction, and two tickets editing one paragraph on parallel branches is the collision the map warns about.
- **One item leaves the CLI re-verification gate.** #1073 recorded the SQL-DSL `.annotate()` as unverifiable because `db.sql` appeared empty for a programmatically-built contract. `db.sql` is a Proxy with a `get` trap and no `ownKeys` trap (`packages/2-sql/4-lanes/sql-builder/src/runtime/sql.ts:33-64`), so `Object.keys()` is `[]` even when populated; against the same contract, `db.sql.public.User.select(…).annotate(…).build()` yields a stamped `dsl` plan. `defineContract` populates `storage.namespaces[ns].entries.table` in-process — no `contract emit` is needed for the lane to exist.
- **The consumer sweep widens:** `docs/content/reference/context-api.md`'s `prisma` section becomes the Unsafe surface's SQL recipe (builders, `query`/`execute`, the cost list), the plugin how-to's `$executeRawUnsafe` placeholder is rewritten, and `install-pgvector.ts`'s port runs `CREATE EXTENSION` as the raw tag (`raw.sql`, `.affectedCount()`)through`execute()`.
- **A re-verification note.** Prisma ships raw guardrails that regex-refuse `insert|update|delete|create|alter|drop|truncate` on the raw lane by default (`packages/2-sql/5-runtime/src/guardrails/raw.ts`, per #1033). The ported DDL script and any raw mutation will meet them; whether they are configurable per client, and whether the Unsafe surface should relax them, is an implementation question for the build effort, not a decision here.
- **The surface's identifier stays the build effort's to fix** (ADR-0038). This record names its shape.
- **Everything here was reasoned against `8.0.0-rc.8`** from shipped sources and a live runtime round-trip on a programmatic contract; the builder's method list should be re-checked at GA with the rest of the map's re-verification items.
