# Transactions lose isolation levels and database errors become stack-owned

Status: accepted

Prisma 8 has no isolation-level API and no `P####` error codes, and the two guarantees this stack publishes on top of them — `context.transaction(fn, { isolationLevel })` and an unwrapped `P2034` for the caller's retry loop — have no counterpart to forward to. Both are replaced rather than ported:

- **`context.transaction` takes no options.** `isolationLevel`, `maxWait` and `timeout` are deleted along with the `TransactionIsolationLevel` union. Transactions run at the connection default (Read Committed on PostgreSQL).
- **The documented concurrency gate becomes a row lock.** `SELECT … FOR UPDATE` on the contended parent row inside the callback, with `pg_advisory_xact_lock()` as the alternative where no such row exists. `Serializable` + retry is withdrawn as the recommended pattern.
- **Driver errors are normalised into stack-owned types at the engine terminals.** A serialization failure (SQLSTATE `40001`) becomes `SerializationFailure`; a unique violation (`23505`) becomes a unique-violation error carrying the per-field messages `parsePrismaError` builds today. Each ships an `is*` predicate. `DatabaseError.code` is removed — it exists only to carry a `P####` string.
- **The violated columns come from a generated constraint map.** The generator emits its own module mapping each unique constraint's name to the OpenSaaS **field** names it covers; a unique violation is resolved by looking up `SqlQueryError.constraint` in it. No prose is parsed anywhere.

## Context

[The transaction and error research](https://github.com/OpenSaasAU/stack/issues/1036), against `prisma/orm` at `8.0.0-rc.8`, established two negatives with high confidence. `grep -rn "isolationLevel"` over the whole ORM source returns zero hits; the port ledger records the four upstream isolation-level tests as deliberately non-ported ("no `isolationLevel` in facade"), with `timeout` and `maxWait` alongside them. And `P2002`/`P2034` are not renamed but gone: a unique violation is a `SqlQueryError` with `sqlState === '23505'`, a serialization failure is the same class carrying raw SQLSTATE `40001`, untranslated, with no retry helper anywhere in Prisma 8.

Both of this repo's discriminants are string compares — `prismaError.code === 'P2002'` in `parsePrismaError`, `err.code === 'P2034'` in the documented retry loop — so both fail **silently** on Prisma 8 rather than loudly. The unique-violation branch falls through to a generic message and loses its per-field form errors; the retry loop stops retrying and rethrows. That silence, not the API loss, is what makes this a decision rather than a rename.

The trade on error detail runs in both directions. `SqlQueryError.constraint` is a structured, locale-independent field, which **fixes** the English-prose regex in `prisma-errors.ts` outright. But `.column` is unpopulated for `23505` and the column list appears only inside `.detail` as `Key (tenantId, slug)=(…) already exists.` — so the known limit moves from the constraint name to the column list rather than disappearing. `parsePrismaError`'s one real consumer needs the columns, not the name.

ADR-0012's mechanism is not in question. #1037 found the rebind untouched by the access-engine decision, and Prisma 8's `tx.orm` is a full ORM client bound to the transaction connection, so "rebind the secured context to the transaction client" ports directly. What breaks is one paragraph of ADR-0012's options contract and one consequence.

## Considered options

- **Preserve `isolationLevel` by issuing `SET TRANSACTION ISOLATION LEVEL` as a raw statement.** Rejected. Reachable only below `db.transaction()`, at `withTransaction` or `connection.transaction()`, where `tx` is bare (`execute`/`executePrepared`, no `.orm`) — so the whole ADR-0012 rebind would be rebuilt against a lower runtime level to keep an option name. The research found no hits for `SET TRANSACTION` anywhere in the ORM source and no documentation of the pattern, leaving its pooling safety unknown; the docs pages could not be re-checked from this session (egress-blocked). Adding the option back if GA ships one is trivial; unwinding a hand-rolled runtime path is not.
- **Keep `isolationLevel` in the signature and throw on use.** Rejected: it keeps a lie in the type. A deleted option is a compile error at every call site, which is the loud failure this ADR exists to produce.
- **Withdraw the exactly-N guarantee entirely** and make `context.transaction` atomicity-only. Rejected, though defensible with no external users: it would leave ADR-0012 without the motivating use case (issue #614) it was written for. A row lock answers the same question at Read Committed.
- **Let callers branch on the driver error** (`SqlQueryError.is(e) && e.sqlState === '40001'`). Rejected: answering a silently-broken raw discriminant with another raw discriminant re-arms the same trap one ORM version later, and couples every application to a Prisma internal class.
- **Ship `retryOnSerializationFailure` now.** Deferred, unchanged. ADR-0012's reasoning — that baking a retry policy into core prejudges backoff and limits the caller is better placed to choose — is untouched by Prisma 8.
- **Keep `DatabaseError.code`, populated with the SQLSTATE.** Rejected: half-normalising is the trap. One stack-owned error beside one raw string invites callers straight back onto the string.
- **Recover the columns by parsing `.detail`.** Rejected: the same locale-fragile limit relocated, not deleted.
- **Recover the columns by looking the constraint name up in Prisma's runtime contract** (`db.contract`). Rejected as unverified — the research named it plausible but explicitly unchecked, and it could not be checked here either. The generator already knows the answer at generate time without asking Prisma.
- **Emit the constraint map inside the generated contract module.** Rejected: ADR-0040 requires that module be standalone and fully literal for the `prisma contract emit` shell-out. The map is a separate generated artifact; `.opensaas/types.ts` is also wrong, since #1039 shrank it to type declarations.

## Consequences

- **`Serializable` is no longer available, and no application code can ask for it.** Any invariant that depended on it must be re-expressed as a lock. The documented capacity gate becomes: take `SELECT … FOR UPDATE` on the parent row first, then read the count and branch, then write — all inside `context.transaction`. `CLAUDE.md`'s `{ isolationLevel: 'Serializable' }` example and its "serialization failures (Prisma `P2034`) propagate so the caller can retry" line are both rewritten.
- **The secured surface has no locking terminal.** The recommended gate is not yet writable through `context.db`; `.forUpdate()` is a new terminal, and which terminals the engine can scope is an ADR-0041 question. It is [handed on as its own ticket](https://github.com/OpenSaasAU/stack/issues/1050) rather than settled here.
- **Normalisation lives in the engine-owned terminals** (ADR-0041), not in `context.transaction` — a unique violation arrives from a plain `create()` with no transaction anywhere. `context.transaction` inherits the guarantee because every operation inside it runs through the same terminals. `context.prisma` is deliberately excluded: the bypass handle yields raw driver errors, consistent with its bypassing everything else.
- **A constraint the generator did not emit gets no per-field errors.** The map covers what we generate; an index managed by hand in the database falls through to the existing generic path (`'A record with this value already exists'`, no field errors) — the same outcome as today when columns cannot be resolved. Adopting a live database's own indexes is already out of scope for this migration.
- **`prisma-errors.ts` survives as a concept with its halves swapped.** `constraintName` becomes trivial (a structured field), `fields` becomes the derived part (a generated lookup). `stripIdentifierQuotes`, the `originalMessage` regex, the `driverAdapterError.cause` normalisation and the locale known-limit docblock are all deleted. Postgres' 63-character identifier truncation and the one-row-violates-two-indexes caveat are properties of Postgres, not Prisma, and still stand.
- **No `P####` literal may survive anywhere in the repo** — source, tests, `CLAUDE.md`, changelogs, docs examples. The check is mechanical (a grep in CI or a lint rule) and is part of the migration, not an afterthought: a stale `err.code === 'P2034'` in a documentation example is how a dead discriminant reaches an application.
- **ADR-0012 is amended, not superseded.** Its decision and its rebind mechanism stand; its "`options` … pass through to Prisma" paragraph and its "Selectable isolation, including `Serializable`" consequence are replaced by pointers here.
- **ADR-0028 keeps its rule and loses one sentence.** "Transaction errors take precedence over hook errors, so a serialization failure still reaches the caller unwrapped and the documented `P2034` retry loop is unaffected" holds in substance — precedence is unchanged — but the failure now reaches the caller as `SerializationFailure`, not unwrapped. The warning that a broadly-catching retry loop would re-apply a committed transaction is unchanged and now matters more, since the typed error makes narrow catching easy.
- **Verified against a release candidate.** Every finding behind this ADR is from `8.0.0-rc.8`. If GA ships an isolation-level option, reinstating it is additive and does not disturb the error decisions, which stand on their own.
