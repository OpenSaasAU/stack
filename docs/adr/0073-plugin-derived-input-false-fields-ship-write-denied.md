# Plugin-derived `input: false` fields ship write-denied

Status: accepted

A derived Auth list field that better-auth itself marks `input: false` — a field its own API refuses to accept from a client — ships with a field-level `create`/`update` deny that the plugin sets when it derives the field, composing with (never replacing) the field's existing credential read-deny (ADR-0036) where both apply. This covers `User.emailVerified` unconditionally, and — once the `admin()` plugin is registered — `User.role`, `User.banned`, `User.banReason`, `User.banExpires` and `Session.impersonatedBy`, plus any other better-auth plugin field marked `input: false` the stack has never specifically seen. An application can reopen a seeded deny, per operation, via `authPlugin({ fieldAccess })`.

## Context

ADR-0013 settled that a plugin-injected list ships closed and the application opens it, most commonly with a whole-row owner rule: `update: ({ session, item }) => session?.userId === item.id`. That rule is a decision about which **rows** a session may write, not which **columns** — the same gap ADR-0036 closed for reads. Before this decision it was open for writes too: nothing stopped a signed-in user's own `context.db.User.update({ where: { id: me }, data: { role: 'admin' } })` from succeeding once the owner rule allowed touching the row at all, even though better-auth's own `updateUser` endpoint has always refused `role` (issue #1618).

better-auth already draws this line for us, field by field, in the same resolved table definitions `deriveAuthLists` already reads (`DBFieldAttribute.input`, default `true`): a field marked `input: false` is one its own client-facing API will never accept, because the value is meant to change only through a dedicated, guarded flow — the admin plugin's `setRole`/`banUser`/`unbanUser`, better-auth's own email-verification flow for `emailVerified`. The signal is not hypothetical or stack-invented; it is the exact boundary better-auth itself already enforces at its own edge, and it derives automatically for any plugin the stack has never specifically written code for.

## Considered options

- **Derive the write-deny from `input: false` (chosen).** No hardcoded field list to keep in sync with every better-auth plugin the stack might grow support for — a future plugin marking a new field `input: false` closes the same hole with no stack change, the way ADR-0036's `CREDENTIAL_FIELDS` table cannot (it is deliberately curated, since "credential" isn't a flag better-auth exposes). The cost is the one already accepted for ADR-0036: an application that relied on writing one of these fields through `context.db` — most plausibly `emailVerified` on an app that never installed the deny — sees that write start failing.
- **A hardcoded field list, curated like `CREDENTIAL_FIELDS`.** Rejected: `input: false` already exists as an upstream, per-field signal for exactly "a client must not set this" — hand-curating a parallel list would drift from it the moment a plugin update adds or removes a flag, and give the stack no story for a plugin it has no first-class support for at all.
- **Leave it to the application, documented as a footgun.** Rejected for the same reason ADR-0036 rejected it for reads: the unsafe configuration (a whole-row owner-update rule paired with an `admin()`-managed `role` field) is exactly the shape the starter, the with-auth template and `auth-demo` shipped, so "documented" was not reaching anyone in practice — it took a live QA pass to find it.
- **Only fix the shipped example/template access rules, without a stack-level deny.** Rejected as insufficient on its own: it closes the hole for the four base fields covered by the examples' own field-level overrides but does nothing for an application that writes its own owner-update rule, or that registers `admin()` without copying the example's care. Done in addition to the stack-level deny (the templates now also demonstrate `fieldAccess` for `email`), not instead of it.

## Consequences

- **This changes behaviour for an application that writes one of these fields today.** One with a whole-row (or otherwise permissive) update rule on `User` that relies on writing `emailVerified`, or `role`/`banned`/`banReason`/`banExpires` under `admin()`, through `context.db` will start seeing that write refused. Pre-1.0 packages ship a breaking behaviour change as a **minor** release (ADR-0036 sets the same precedent), so the changeset text carries the field list explicitly rather than leaving it to the version number.
- **A denied field-level write throws, not strips.** This is the existing field-level write-access behaviour (`checkFieldAccess`, `packages/core/src/access/field-access.ts`) — a write naming a denied field fails loudly, and the row is left unchanged. This differs from ADR-0036's read-deny, which strips the field from an otherwise-successful read; a write has no equivalent "succeed anyway, minus the one field" shape to fall back to.
- **`sudo()` and the Auth adapter are unaffected**, for the same reason ADR-0036 states: `sudo()` skips field-level access, and better-auth's own flows (sign-up, `setRole`, `banUser`, email verification) write through the Auth adapter over the Unsafe surface, which bypasses access control entirely. Nothing in better-auth's own operation depends on these fields being writable through the secured surface.
- **The deny composes with the credential read-deny, never replaces it.** A field that is both a credential (ADR-0036) and `input: false` (this decision) ships with both `read` and `create`/`update` denied — `withFieldAccess` in `derive-auth-lists.ts` merges the two access objects rather than one clobbering the other, so a future field carrying both flags is covered on both axes automatically.
- **`authPlugin({ fieldAccess })` is the reopening seam ADR-0036 explicitly deferred** ("add a passthrough and leave the defaults open... worth building when a concrete need to re-open a specific field appears"). It is additive/override, not additive-only like `credentialFields`: an entry replaces exactly the operations it names, on top of whichever seeded rule (credential read-deny, write-deny, or neither) already applies — but it can never set `read` on a credential field, so ADR-0036's read-deny stays permanently closed regardless of this option. The common case it exists for is letting an admin session change another user's `role` from the admin UI, which needs both an operation-level rule that permits an admin to touch someone else's row and a `fieldAccess` entry that reopens `role` specifically — the two are independent axes, and both must agree before the write goes through.
- **The rule is keyed on the flag, not a hardcoded field list** — like ADR-0036's rule is keyed on "confers a credential" rather than a name. A better-auth plugin the stack has no first-class support for still gets its `input: false` fields write-denied the moment its schema merges into `getAuthTables`'s result, with zero stack code aware of that plugin's existence.
- **A create-denied field with a `defaultValue` still lets `create` succeed for an omitted field.** `User.emailVerified` (and `User.banned`) carry both — better-auth's own schema always gives `emailVerified` a `false` default — so without a way to say "let the default settle even though nobody but sudo may write it," `context.db.User.create()` would throw for every session, every time, the moment this deny applies. The seeded `DENY_WRITE` sets a new core option for exactly this, `FieldAccess.allowCreateDefault` (`packages/core/src/access/types.ts`): a field's own declared default is exempted from its `create` deny when the caller and every hook left the field omitted, while an explicit attempt to set it is still refused. It is opt-in and off by default in core, so an application's own session-dependent `create` rule (denies one session, allows another — the ordinary case a `defaultValue` does **not** rescue) is unaffected; ADR-0073's deny is unconditional (denies every session, sudo aside), which is exactly the shape this flag is for.
