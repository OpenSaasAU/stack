# Access control belongs to the application, not plugins

Status: accepted

Operation-level access on a list is the **application's** responsibility, never a plugin's. A plugin may inject or extend lists (fields, hooks, relationships), but it must not define or override the operation-level access of a list — and the plugin engine treats an extension that carries `access.operation` for a list that already exists as a **config-time error**, because that is a silent, security-relevant overwrite of rules the application (or an earlier list owner) set. Combined with the engine's existing deny-by-default (`checkAccess` returns `false` when no access control is present), this means a plugin-injected list with no application-supplied access is **closed**, not open: the safe direction. The application opens it explicitly by owning the access rules.

## Context

The plugin engine merges an extension's access into the target list by spreading operation keys (`{ ...existing.operation, ...extension.operation }`), so an extension's rules win per operation. The auth plugin relied on this: it seeded its Auth lists (User/Session/Account/Verification) with permissive defaults (`query: () => true`, self-only update/delete) and forwarded that `access` through `extendList` whenever a list already existed under a derived key. Two bad outcomes followed:

- An application that declared its own `User` (or any list colliding with a derived/plugin key) had its access rules silently replaced by the plugin's permissive defaults — an admin-only list quietly becoming "anyone can read / update themselves", with no error and no warning. This is the same class of blocker ADR-0007 was written to prevent, resurfacing through the extension/merge path.
- The Auth lists shipped world-readable by default. Because better-auth's own flows operate through the raw Prisma client (the driver adapter), they **bypass** access control entirely, so login never depended on those permissive rules — the only thing the permissive default actually did was expose every user and session to any `context.db` reader and to the admin UI. The default was pure footgun.

The generalisation is that whoever owns a list is the only party entitled to set its access, and a plugin extending a list it did not create is not that party. Consent to change access must sit with the list owner (the application), not with the plugin — a plugin-held opt-in flag would just let a plugin re-authorise itself and re-silence the overwrite from the application's point of view.

## Considered options

- **Application owns access; plugins never set operation access on lists they don't create; extensions carrying `access.operation` for an existing list throw (chosen).** Loud, secure-by-default, and needs no access-composition semantics. Deny-by-default makes "no application access" mean closed, which is the safe failure mode. The cost is a DX shift: to read a plugin-injected list through `context.db`/the admin UI, the application must supply access for it — and for lists it does not itself declare (Session/Account/Verification), it needs a first-class app-side seam to do so, which does not fully exist yet and is tracked as follow-up work.
- **Plugin-side opt-in flag (`overrideAccess: true`) that suppresses the throw.** Rejected: the opt-in lives with the wrong party. A plugin could hardcode the flag and the overwrite becomes silent again from the application's perspective — defeating the guardrail. If an application ever genuinely wants a plugin to manage a list's access, the right shape is an **app-side** allowlist (the owner consenting by name), added when that need is real, not a plugin-held flag.
- **AND-compose extension access with existing access (tighten only).** Rejected: composing access functions that may return either booleans or Prisma filters is complex and surprising, and it still lets a plugin inject rules onto a list it doesn't own.
- **Warn but apply.** Rejected: a security-relevant change that stays effectively silent in non-interactive/CI runs is not a guardrail.

## Consequences

- **The plugin engine enforces the invariant.** An extension providing `access.operation` for a list that already exists is a config-time error naming the plugin and the list. A plugin sets access only on a list it creates via `addList`; it may never override an existing list's access. This is the reshaped scope of the reported extension/merge bug.
- **The auth plugin stops forwarding `access` on its extend paths.** When it merges Auth fields into a list that already exists, it forwards fields/hooks/mcp only — the list's own access stands.
- **Plugin-injected lists default closed.** Stripping plugins' permissive defaults so injected lists rely on deny-by-default, and giving the application a first-class seam to grant access to lists it did not declare, are coupled (closed-by-default is unusable without the seam) and are tracked as follow-up hardening rather than bundled into the guardrail fix.

  _Update (2026-07-15):_ the follow-up seam is resolved. Rather than a top-level core surface, an application authors access for a plugin's injected lists **through that plugin's own config** — a passthrough keyed by the plugin's model names (e.g. `authPlugin({ access: { user: { … }, session: { … } } })`) that the plugin applies **when it creates each list**, so the access rides along with the list's `@@map`/`@@schema`/fields and cannot drift from the plugin's shape. This stays consistent with the principle: the application authors the access; the plugin is only the conduit (it never injects its own policy). Plugins ship their created lists **closed** — no permissive defaults — so absent an app-authored override a list is deny-by-default. The auth plugin's own identity helpers (`getUser`/`getCurrentUser`) resolve through `sudo()` so they do not depend on the application's User access policy. Exposing an app-authored `access` passthrough is a **convention** for list-injecting plugins, implemented for the auth plugin first; a generic core surface is deferred until a second plugin needs it. Removing the permissive defaults is a breaking change (major version for the auth package).

- **`addList` ownership is unchanged.** A plugin that genuinely owns a list still creates it and may set its access at creation; the guardrail only fires on `extendList` into a pre-existing list.
