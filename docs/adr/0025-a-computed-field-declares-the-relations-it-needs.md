# A computed field declares the relations it needs

ADR-0024 made a bare read fetch scalars, and accepted as a consequence that a computed field whose hook reads a relation off `item` silently degrades. This is the fix we deferred: a field may **declare** the relations its `resolveOutput` cannot compute without, and the read fetches exactly those, wherever that field is computed. The declaration is what earns the data — a hook that reaches for an undeclared relation finds nothing there — and it is scoped by the Access Filter like anything else a read asks for.

A declared dependency is **private plumbing, not an implicit `include`**. The relation is fetched for the field's benefit and stripped from the result unless the caller named it too. This is what keeps ADR-0024's win intact: if declarations widened results, the shape of a bare read would once again depend on the config of fields the caller may never read — a quieter version of the default we just removed. It also makes a declaration refactorable, since adding or removing one changes a field's implementation rather than the payload of every read of that list. The fragment-`query` path already behaves this way (its projection drops anything unrequested), so this makes the two read shapes agree rather than diverge.

Declarations fold in at **every level a field is computed**, not just at the root of a read. Computed fields already run at every level of a returned tree, so a root-only rule would mean the same field returning a correct total at the root and nonsense one hop down — shape varying by position, which is the exact non-uniformity ADR-0024 collapsed. Root-only would also _appear_ to work today, because a caller-named relation still auto-expands its subtree, and would break silently when that expansion is removed.

Value semantics are **session-relative, with no escape**. A dependency the session cannot query is not fetched, and the hook sees nothing in its place; a dependency the Access Filter scopes yields only the visible rows. The field computes either way, on whatever it can see. We considered withholding a field whose dependencies were denied, and rejected it: a field declaring two relations and granted one should still produce a value, and all-or-nothing would throw that away. The consequence is real and belongs in the field author's head — a total over a scoped relation is a projection of what the session can see, not a fact about the row. Computing the true figure is not an option we can offer, because the true figure leaks the values of the rows the session was denied. A field that genuinely needs the unscoped view must take a privileged read inside its own hook and own that decision explicitly.

## Considered Options

- **Declarations widen the result** (an implicit `include`): rejected. Simpler to implement and nothing is fetched-then-discarded, but it makes a read's shape depend on field config the call site cannot see, and puts the `include` and fragment paths back into disagreement about what comes back.
- **Dotted paths** (`needs: ['lineItems.product']`): rejected. It is a new path grammar — parser, validation, error messages, and template-literal types to stay typed — for reach that recursion already provides, since a dependency of a dependency is pulled in by the next level's own declaration. The object form (mirroring the existing include grammar) stays available as a non-breaking widening if a single hook ever genuinely needs two hops.
- **Restricting declarations to virtual fields**: rejected. The same degradation hits any field whose `resolveOutput` reads a relation, so a virtual-only fix leaves the bug class reachable through another door — and it is _more_ work, since the natural home for the option is the base field config and restricting it means writing a validation to reject it elsewhere.
- **Withholding a field whose dependencies were denied**: rejected, as above — it discards a partially-computable value to signal something the field author is better placed to interpret.
- **Skipping declarations for fields that will not be returned** (a fragment did not select them): deferred, not rejected. It is the right end state, but computed fields currently run unconditionally and are discarded afterwards, so fetching selectively without _computing_ selectively would leave hooks running against absent dependencies. Flipping that invariant inside this change would mean defending two decisions at once — the same reasoning by which ADR-0024 deferred this one. Tracked separately.

## Consequences

- **A declaration can fail the build.** Because declarations fold in recursively, a chain of them can exceed the depth the Access Filter can scope. A closure that cannot fit from any starting point is a hard error at generation time, naming the chain; one that only overflows because of where a caller started is the existing depth denial at runtime. Both are refusals rather than silent truncation, consistent with ADR-0022 — the stakes are money-shaped fields returning a number short by whatever sat past the cap.
- **The failure mode for an undeclared relation is unchanged, and still silent.** This gives authors a way out of ADR-0024's degradation; it does not detect that they need one. The type-level constraint narrows the gap by rejecting a misspelled or non-relation declaration at compile time, which is the half of the typing work that carries correctness weight; narrowing the hook's `item` so a declared relation is non-optional is ergonomics on top.
- **Every field type gains the option**, third-party ones included, and the generation-time closure check walks all fields rather than only virtuals.
- **ADR-0024 stands unchanged.** A bare read still returns scalars; declarations do not add relations to what a caller receives. This ADR only gives a field a way to see data it names, on the same access terms as everyone else.

## Amendment — the cycle guard is this ADR's (ADR-0043)

ADR-0026 re-pointed the relationship-graph cycle guard: once nothing walks the graph unprompted, a caller's `include` is a finite literal and cannot cycle, so the only thing left that can is a declaration closure — which the engine folds in rather than the caller writing. [ADR-0043](0043-bare-read-and-one-hop-become-the-orms-not-ours.md) withdraws ADR-0026, and the guard's record comes here rather than going with it, because a guard belongs with the thing it guards.

The guard runs at generation time and again, defensively, at runtime. **Its comment must describe declaration closures, not the graph walk.** ADR-0026 named the hazard of leaving it otherwise and the hazard is unchanged: a guard annotated against a walk that no longer exists reads as dead code, and deleting it takes the live protection with it.
