# authPlugin mirrors better-auth config and its lists can adopt existing tables

`authPlugin` is a thin wrapper over better-auth: the OpenSaaS auth lists (user/session/account/verification, plus a fifth `rateLimit` when the database-backed rate limiter is in use — see below) are **derived from the better-auth config the developer already writes** — list keys from better-auth's per-model `modelName`, table/column maps from its `fields` — rather than from a separate, stack-invented set of knobs. On top of that, the lists can be placed in a non-`public` database schema. Together this lets a project with pre-existing better-auth tables (e.g. `AuthUser`/`AuthSession`/`AuthAccount`/`AuthVerification` in an `auth` Postgres schema) adopt the plugin and reach **Schema parity** with no destructive migration.

## Decisions

- **The plugin mirrors better-auth.** List keys, table `@@map`, and field-name mappings are taken from the standard better-auth config (`modelName`, `fields`, additional fields). The plugin does not introduce a parallel `listKeys` configuration surface. `getAuthLists`/`convertBetterAuthSchema` derive the OpenSaaS lists from that config. The runtime `userListKey` (currently a hardcoded `'user'` TODO) is resolved from the configured user model.
- **A fifth model, `rateLimit`, is conditionally derived.** Unlike the other four (always present), the `RateLimit` list only exists when `authPlugin({ rateLimit: { storage: 'database' } })` is set — better-auth itself only creates this table under that same condition (`getAuthTables` in `@better-auth/core` gates it on `options.rateLimit?.storage === 'database'` alone, not `enabled`). It follows the same derivation path as the other four (`modelName`/`fields`/`tableName`/`schema` adoption knobs, closed-by-default access per ADR-0013), with two shape differences forced by better-auth's own table: no `createdAt`/`updatedAt` (better-auth's rate-limit table has neither), and `lastRequest` is a `bigInt()` (a millisecond epoch, which overflows a 32-bit `Int` — see #907/#909). `key` carries a unique constraint that is load-bearing, not cosmetic: the limiter races concurrent requests into a `create` and relies on the resulting constraint violation to serialise them.
- **Auth lists are relocatable to a schema.** A plugin-level `schema` option (with a per-list override) places the generated auth lists in a non-`public` Postgres schema via the stack's existing multi-schema support (`@@schema`).
- **"Adopt" means a clean diff, not ownership.** With keys, schema, and field shapes matching the live tables, the generated auth lists diff clean against the existing database — they are modelled for runtime and types without producing a migration. An "adopt existing better-auth tables" preset/recipe sets these defaults.
- **The app's User is separate from the auth identity.** The plugin no longer assumes its user list is the application's `User`. An app may keep its own domain `User` (keyed however it likes) distinct from the better-auth user; linking the two is the application's concern (a relationship/field it declares), not the plugin's.
- **The auth user FK mirrors better-auth's exact shape.** The `Session.user` / `Account.user` foreign keys deliberately (a) **omit** the generator's default `@@index([userId])` (via `isIndexed: false`) and (b) carry **`onDelete: Cascade`** (via a field-level `extendPrismaSchema` rewrite). This is not a generator regression — it is what makes an adopted auth schema diff **clean** against a live better-auth database, which emits no separate FK index and cascades user deletes; without it, adoption would surface a spurious `@@index` and a referential-action change. The tradeoff is that these FK columns are unindexed by default (matching better-auth, which relies on the `token`/`identifier` lookup indexes rather than a `userId` index); a project that wants the index can override `isIndexed` on the relationship. Implemented in #679/#698; see `userRelationshipDb` in `packages/auth/src/config/derive-auth-lists.ts` and the generated-schema regression test in `packages/auth/tests/generated-fk-shape.test.ts`.

## Why this is worth recording

The plugin previously hardcoded the four list keys and the `public` schema, and silently `extendList`-ed any existing `User` — which would overwrite an app's own `User` and force a destructive auth migration. A future reader will wonder why the auth lists are derived from better-auth config and freely renamable/relocatable rather than fixed; the answer is that adopting a real, pre-existing better-auth installation on a separate schema is a first-class requirement, and reversing it (re-fixing the keys/schema) would reintroduce the destructive-migration blocker. This was the key blocker reported during the migration.

A future reader will also wonder why `rateLimit` is a fifth model rather than a variant of one of the first four, or why it isn't just derived whenever `rateLimit` is configured at all: it is genuinely a fifth better-auth model (its own table, its own field shape), and gating on `enabled` rather than `storage` would produce a schema that differs between an environment where the limiter happens to be toggled off and one where it's on — exactly the kind of dev/prod schema drift this plugin otherwise avoids by deriving lists from config rather than from runtime state.
