# A synthetic back-relation is a declared relationship wherever a caller can name one

Status: accepted

A list-only `ref` (`ref: 'Other'`, no target field) makes schema generation synthesize a back-relation on `Other`'s model (`from_<List>_<field>`, `getSyntheticFieldName`) because the ORM requires an opposite field there, even though no list config declares one. The write path already resolves this key back to the declared relationship field it stands for (`resolveSyntheticReverseRelation`, #978) and runs it through the same access/hooks pipeline a declared relationship gets. The read path did not: `buildAccessScopedInclude` treated any key it could not resolve to a declared relationship as "not governed by access control" and passed it through unscoped, and `filterReadableFields` treated the same key as an ordinary non-relationship value and returned it verbatim — no operation-level `query` access on the owning list, no field-level `read` gates, no virtual fields computed (#1082). We decided the read path adopts the write path's rule rather than growing a second one: **a synthetic back-relation is the declared relationship field it stands for, wherever a caller can name one.** Both `buildAccessScopedInclude` and `filterReadableFields` resolve an otherwise-unrecognised key via `resolveSyntheticReverseRelation` before deciding it's ungoverned, and scope/gate/compute through it exactly as they would the declared field — a synthetic back-relation is always to-many (a list-only ref has one construction site and no arity branch), so both paths take that branch unconditionally.

The other half of the fix is what happens to a key that resolves to NEITHER a declared relationship nor a synthetic one: it is now **rejected** rather than passed through. This restores the fail-closed rule #1009/#916/#912 already established for `data`/`where`/`orderBy` — an engine that cannot compute a scope for a key must deny it, not guess that it's harmless. `_count` is the one carved-out exception (see Consequences) — its own scoping is a separate, already-tracked bug (#1082's own "Out of scope").

## Considered options

- **Only scope the synthetic key, leave the "not declared → passthrough" branch as-is for everything else.** Rejected: it would have fixed exactly the one key shape reported and left the underlying defect — an unrecognised `include` key is trusted by default — in place for the next Prisma-generated field nobody thought to declare. The write path already learned this lesson at #564/#978; the read path should not need its own second incident to learn it too.
- **Re-derive the synthetic name by string-parsing `from_<List>_<field>` at the call site**, instead of calling `resolveSyntheticReverseRelation`. Rejected: the write path already owns this resolution and the name format is `getSyntheticFieldName`'s alone to define; a second parser drifts the moment either changes, which is exactly what reusing the existing function prevents (#978's own reasoning, restated here for the read path).
- **Branch on arity for a synthetic key.** There is nothing to branch on: a list-only ref has exactly one construction site in `getPrismaRelation` and no arity option, and a to-one back-relation is structurally impossible for it — a single opposite row cannot represent an unbounded set of rows referencing it. Always-to-many needed no decision to weigh.
- **Scope `_count` in the same pass.** Rejected as its own bug with its own design — an unscoped `_count` leaks a row count regardless of ANY relation's access, declared or synthetic, and folding it in here would conflate two different keys' worth of reasoning under one ticket.
- **Mandate, in this record, whether the Prisma 8 secured surface emits an unreferenced back-relation at all.** Rejected: whether that builder even requires an opposite field is unverified, and a mechanism-specific mandate risks being wrong in either direction before that surface exists. The rule below is stated so it survives the mechanism change intact.

## Consequences

- **A caller relying on the previous fail-open behaviour sees a smaller response.** A read that named a synthetic back-relation in `include` and received rows regardless of the owning list's `query` access, with admin-only fields intact and virtual fields silently `undefined`, now receives exactly what that list's access control allows — fewer rows, fewer fields, and virtual fields populated instead of missing. The extra rows and fields it received before were never authorised; this is a security fix, not a regression.
- **An `include` key that is neither declared, synthetic, nor `_count` now throws `UndeclaredIncludeKeyError`** instead of being passed to the database unscoped. This is the same behaviour class as `AccessScopeDepthExceededError` (ADR-0022) and `RelationFilterAccessDeniedError` (#916): a config or caller bug that used to fail silently now fails loudly, for the one key shape that didn't already.
- **A synthetic hop now consumes the read-include depth cap** (`READ_INCLUDE_MAX_DEPTH`) exactly like a declared one, because it goes through the same recursive call. A tree mixing synthetic and declared hops is bounded by their combined depth, not evaluated separately per hop kind.
- **`sudo` is unaffected.** `resolveReadInclude` (`context/index.ts`) never calls `buildAccessScopedInclude` for a sudo context — it folds declared dependencies and uses the caller's `include` as-is, the same as before this record. Nothing here changes what sudo can reach.
- **The rule is mechanism-neutral by design**, for the Prisma 8 secured surface this record does not implement: whatever that builder ends up emitting for the target of a list-only ref, the invariant is that no key reaches the ORM that the Access Filter has not scoped — not that a specific back-relation must or must not exist there.
- **`CONTEXT.md` gains a Synthetic back-relation glossary entry**, and the Access Filter entry is amended: its denial rule now visibly covers a key the config never declared, not only a caller `include` past the depth cap.
