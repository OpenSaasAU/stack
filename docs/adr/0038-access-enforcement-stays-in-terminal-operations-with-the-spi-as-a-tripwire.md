# Access enforcement stays in the terminal operations, with the SPI as a tripwire

> **Amended 2026-08-31 by [Where do extension packs and the access-control tripwire get registered?](https://github.com/OpenSaasAU/stack/issues/1056)** (Prisma 8 map). The tripwire now has a **registration** and a **stamp mechanism**, both named in [ADR-0048](0048-extension-packs-are-declared-the-tripwire-is-stack-owned.md): the generator emits it unconditionally into the runtime client's `middleware` array — never into the app-facing config, so it cannot be omitted and deleting it stays one generator line — and both stamps are Prisma **annotations** in one namespace, the engine applying its own inside the terminal and the Unsafe surface applying the intentionally-unscoped one to every query it builds. Middleware, annotation and terminal write are **one deletable component**, which is what makes this record's deletability promise literally rather than approximately true. The decision below is unchanged.

Prisma 8 offers a seat the engine has never had: `beforeCompile(draft, ctx)` over the typed query AST, which Prisma names authorization as a use case for. We decided **not** to move enforcement there. `context.db` remains the boundary we own — operation-level access, filter merging and field visibility all run in our terminal operations — and the extension SPI is used **additively**: a `beforeCompile` middleware that rejects any query built by neither approved surface. The enforcement path has no SPI dependency; the tripwire is a second line that can be removed without weakening the first.

The argument for moving enforcement into the SPI is that it would secure `context.prisma` and the SQL builder by construction, closing the raw bypass. That argument does not survive [#1033](https://github.com/OpenSaasAU/stack/issues/1033): raw SQL is **observable, not filterable** — `beforeCompile` can reject it, not rewrite it. So the extension seat does not secure raw SQL either; it only makes raw SQL fail loudly, which is exactly what the tripwire above does at a fraction of the coupling. **Corrected by [#1038](https://github.com/OpenSaasAU/stack/issues/1038):** raw SQL is not observable either. `beforeCompile` runs only when the lane produces a `SqlQueryPlan` with an AST; raw SQL arrives as an already-lowered `SqlExecutionPlan` and bypasses the hook entirely (`packages/2-sql/5-runtime/src/sql-runtime.ts`, `8.0.0-rc.8`). Neither seat can so much as see a raw query, so the comparison above is unchanged — but the extension seat is weaker than this paragraph credited it, not stronger. What the seat would actually buy is a security boundary whose correctness depends on an API carrying **no stability commitment**, measured against a pre-release (`8.0.0-rc.8`) whose CLI does not run.

The bypass is also not the live defect. `context.prisma` has four consumers: core's own internals (which are the thing doing the enforcing), `@opensaas/stack-auth`'s better-auth adapter, `@opensaas/stack-rag`'s pgvector search, and one example setup script — `examples/rag-openai-chatbot/scripts/install-pgvector.ts`, which reaches it as `(await rawOpensaasContext).prisma` to run `CREATE EXTENSION`. That last one is DDL against a database, which no access-controlled surface would ever express, and it is named here because the rename below breaks it. The first two are **deliberate** — ADR-0013 states outright that better-auth's flows bypass access control and treats that as correct, so an extension that secured `context.prisma` would break login unless it were opt-out-able, at which point it is a tripwire with extra steps. The third is the real problem, and it is not a bypass at all: `packages/rag/src/storage/access-filter.ts` is a literal copy of core's `checkAccess` and `mergeFilters`, and copies drift. Duplicated enforcement, not absent enforcement, is what this decision has to fix.

**The tripwire carries no policy and no session.** It answers one question — did this query come from a surface that declared how it is scoped? — which both surfaces answer by stamping the queries they build. This is what makes the whole per-session-scoping problem dissolve. [The spike](https://github.com/OpenSaasAU/stack/issues/1045) priced three ways to get a session into middleware, and every one of them costs something: AsyncLocalStorage binds at execution, so a query value that outlives its scope misses the store on an idiom that looks correct; a per-request client costs ~3.8 ms on a 41-model contract against 0.09 µs for today's object-allocation rebind, and `sudo()` rebinds several times per operation rather than once per request; annotations are per call site, so every new call site is a fresh chance to leak. A tripwire that needs no session pays none of that. `withSession` and `sudo` keep today's mechanism unchanged, ADR-0012 stands, and whether an ALS store survives a Next.js server action or the edge runtime stops being a question this architecture has to answer.

**ADR-0013 is not superseded.** It governs _who is entitled to author policy_ — the application, never a plugin — and enforces that at config time when an `extendList` carries `access.operation`. It says nothing about where enforcement executes. Moving enforcement one layer down would have left it intact; keeping it where it is leaves it doubly intact. This record amends it only with that note.

## Considered Options

- **Extension: enforcement moves into `beforeCompile`.** Rejected. It does not deliver the guarantee that motivates it (raw SQL is rejectable, not filterable), it contradicts the raw seam ADR-0013 explicitly endorses, and it makes an API with no stability commitment load-bearing for the security boundary. The one thing it genuinely offers — the mistake becoming unrepresentable rather than merely caught — is delivered by the tripwire without the coupling.
- **Wrapper alone, no extension at all.** The honest minimum, and close to correct: it is exactly this decision minus the tripwire. Rejected because the tripwire is nearly free once it needs no session, and it converts "an unscoped query is possible" into "an unscoped query throws" — the ADR-0022 posture applied to a route ADR-0022 did not cover. If the SPI proves unstable at GA the tripwire is deleted and this collapses to the wrapper with nothing else disturbed, which is precisely why it was chosen in this shape.
- **Postgres RLS, below the ORM.** The fourth seat, first-class in the contract builder (`rlsEnabled`, `role`, `policySelect`/`policyInsert`/`policyUpdate`/`policyDelete`), and the only one that reaches raw SQL. Rejected on the merits, not on scope: OpenSaaS access predicates are **arbitrary TypeScript** returning Prisma filters, and there is no general translation from those to SQL policy expressions — a seat that can only express the subset that happens to compile is not a seat for this engine's access control. It also needs a per-connection `SET LOCAL`, which sits badly with the shared `pg.Pool` the driver adapter now requires. Nothing here stops an application adding RLS itself as defence in depth.
- **Carrying the full session into the extension via ALS**, so the middleware can re-derive scope independently. Rejected: it buys a capability nothing needs, and it makes ALS load-bearing along with the query-value-outlives-scope failure the spike demonstrated.
- **Running the tripwire in development and test only.** Rejected. The guarantee would evaporate exactly where it matters, and the cost of running it in production is one AST-node check.
- **Exempting auth and RAG by client instance** rather than by a second stamp. Rejected as too coarse: the exemption attaches to a client, so anything sharing that client inherits it, where a stamp attaches to the query that actually meant it.
- **Deferring the seat and specifying an abstraction instead.** Rejected. It would leave the map's downstream fog — the two-phase read, the write pipeline, generated types — blocked on a decision we are in a position to make, which is the whole reason the question was asked.

## Consequences

- **Two stamps exist; only an absent stamp is rejected.** The engine stamps queries it builds. The raw surface stamps "intentionally unscoped". A query carrying neither did not come from either and throws in `beforeCompile`. Deliberate bypass becomes an audited act with a name, rather than an absence the middleware cannot distinguish from a mistake.
- **`context.prisma` survives, renamed to state the bypass** (`context.unsafeRaw` or similar — the identifier is the build effort's to fix). ADR-0013 endorses the seam; what it never had was a name that warned. Keeping it also means the auth adapter needs no exemption machinery. The rename's blast radius is exactly the four consumers named above — core's internals, the auth adapter, RAG's vector search, and `examples/rag-openai-chatbot/scripts/install-pgvector.ts` — and the consumer sweep has to carry all four.
- **Core exports the access-filter builder as supported API**, so `packages/rag` stops carrying a copy of `checkAccess`/`mergeFilters`. This is the fix the seat question was really asked to deliver, and it lands independently of the query surface work.
- **`withSession`, `sudo` and interactive transactions are untouched.** Today's object-allocation rebind stands, ADR-0012 stands, and the per-request-client and ALS options are both off the table. The map's open question about where the request boundary sits no longer gates this architecture.
- **SPI instability is bounded to one deletable component.** If `beforeCompile` breaks or changes shape at GA, the tripwire is removed and the enforcement path is unaffected. This is the property that made the hybrid preferable to the wrapper alone rather than merely equal to it.
- **Raw SQL remains unfilterable — and, per the correction above, unobservable.** The tripwire cannot scope a raw query, and cannot refuse one either: raw plans never reach `beforeCompile`, so the unsafe surface's stamp is not what exempts them — the hook simply never sees them. Enforcement on that path is the caller's alone, and anything reaching for raw SQL is asserting it has handled its own scoping.
- **ADR-0013 is amended, not superseded.** Its subject is policy authorship; this record's subject is enforcement location. The note added to it says so, so a future reader does not have to re-derive that they are different axes.
