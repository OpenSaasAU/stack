# A computed field runs only when it is going to be returned

Computed fields ran unconditionally on every read: a fragment `query` selecting three fields still ran every `resolveOutput` on the list and discarded the rest, and ADR-0025's declared dependencies were fetched for all of them regardless. We decided a computed field is computed **if and only if it is going to be returned**, its declared relations are fetched on exactly the same condition, and — the price of making that safe — a hook sees the row's stored columns and its declared relations, and **no field's resolved output**. This is the deferral ADR-0025 recorded, taken up once its precondition was met.

"Computed field" here is any field carrying a `resolveOutput` hook, not only a virtual one. ADR-0025 already refused the virtual-only split when it put `needs` on the base field config — the same degradation reaches any field whose hook reads a relation — and re-drawing the line differently for this rule would leave the term meaning one thing for declarations and another for computation. Skipping a virtual avoids a hook and, through its declarations, real database work; skipping a stored field's hook avoids only the hook, since its column is fetched either way. That asymmetry is a difference in what the rule saves, not a reason for two rules.

The condition is **projection-aware, never access-aware**, and the two stay separated because they already are. A fragment's selection is known before the query is issued, so it can decide what to fetch; field-level `read` access takes the item, which needs the row, which needs the query. It never has to enter this condition, because Field Visibility already evaluates read access before running a hook and skips the hook on denial — access-driven skipping predates this decision and is untouched by it.

**Fetching selectively is the point, and it is why the compute rule had to move first.** ADR-0025 scoped declarations to fetching unconditionally precisely because the reverse order is incoherent: fetch narrowly while still computing everything and a hook runs with its declared relation absent, throwing on a read that never wanted the field. With computation selective, the fold can follow it. The cost is that a hook reading a relation it did not declare, which worked only because some _other_ field's declaration paid for the fetch, stops working. That accidental coupling is not a capability we are removing; it is the same "declaring it is what earns the data" rule ADR-0025 already stated, finally applying evenly.

**A computed field no longer sees another computed field's output, on any read path.** Today a virtual field receives the assembled, already-resolved object, so a virtual declared later in a list could read an earlier virtual's computed value — undocumented, untested, and dependent on declaration order, such that reordering two fields in a config silently changed a result. Skipping unselected computations would have turned that latent trap into a live one. We considered making it explicit instead, by widening `needs` to name sibling computed fields, and rejected it: it grows the declaration grammar and the generation-time closure check to preserve a behaviour nothing first-party uses, when the same value is available by computing from the stored columns both fields share. Enforcing it only where skipping happens was rejected outright — projection exists only on the fragment path, so the same field would return a value under an `include` read and `undefined` under a fragment read, which is exactly the shape-varies-by-path fault ADR-0024 was written to collapse.

A skipped field's key is **absent**, never present holding its pre-hook value. Beyond matching the "finds nothing there" rule, the raw form is unsafe: a field whose hook exists to wrap a value for safety — a password wrapping its stored hash — would otherwise expose the bare hash to any hook that read the key.

## Considered Options

- **Declaring sibling computed fields via `needs`**: rejected, as above — a wider grammar and a larger closure check to keep an order-dependent behaviour with no first-party user, when the same result is reachable from the stored columns both fields already read.
- **Restricting the rule to virtual fields**: rejected. It targets where the cost actually is, but reintroduces the virtual-vs-any split ADR-0025 refused, leaving "computed field" with two definitions.
- **Enforcing the no-computed-output rule only where skipping occurs**: rejected. Smallest diff, but it makes a field's value depend on which read shape asked for it.
- **Skipping the hook but still evaluating field-level `read` access** for a field that will not be returned: rejected. It preserves any side effect an access function has, but retains the cost the change exists to remove — ADR-0024 already noted those functions may themselves hit the database, and called skipping them the larger saving. `resolveOutput` was never a side-effect surface and neither was access; the change is observable in the same way ADR-0024's was.
- **Applying the rule only at the root of a read**: rejected on ADR-0025's own reasoning against root-only declarations — the same field would compute correctly at the root and be skipped or not one hop down according to position rather than according to what was written.

## Consequences

- **This break is silent, like ADR-0024's and ADR-0026's.** A virtual reading a sibling virtual returns a value computed from `undefined` rather than throwing. The changeset leads with detection: find `resolveOutput` hooks whose `item` reads a field that is itself computed — virtual fields, and stored fields carrying a `resolveOutput` such as a calendar day's formatted value or a password's wrapper.
- **It must land after ADR-0026.** While a bare-named relation still auto-expands its subtree, selective fetching wins nothing below the root, and the fold would be written against an expansion ADR-0026 removes and then rewritten. ADR-0026 also leaves the fold needing explicit per-level recursion, which is the same machinery this decision needs to fold selectively at every level.
- **`include` and bare reads compute exactly what they do today.** Projection exists only on the fragment path, so those reads return every computed field and therefore compute every one. What changes for them is only what a hook can see.
- **The deliberate preservation of access-function side effects for a hookless virtual field stops being coherent** and is reconciled here. Such a field returns nothing under any read, so under this rule it does no work at all.
- **ADR-0025 stands, with its deferral discharged.** Declarations still never widen what a caller receives; they are now also not paid for when the field that declared them is not being returned.
