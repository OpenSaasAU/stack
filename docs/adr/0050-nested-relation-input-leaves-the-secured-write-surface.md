# Nested relation input leaves the secured write surface

Status: accepted

`context.db`'s write terminals stop accepting nested relation input. A `create` or `update` payload carries scalars, and one relationship spelling — `connect` — which is **engine-owned sugar for a foreign-key assignment**, not a nested write. Every other shape ADR-0010's pipeline handled (`create`, `update`, `delete`, `connectOrCreate`, `disconnect`, `set`, `updateMany`, `deleteMany` under a relationship key) is removed with no replacement in the payload: a caller who needs several rows written atomically authors those writes and wraps them in `context.transaction` (ADR-0012), taking ADR-0047's row lock where they must not race. `packages/core/src/context/nested-operations.ts` is deleted.

**This is mostly a forced move, and the record should not dress it as a preference.** Prisma 8 keeps nested writes but cuts the kind vocabulary from nine to three — `create`, `connect`, `disconnect` — expressed as callbacks (`posts: (posts) => posts.connect([{ id: 5 }])`) rather than payload keys, with nested update and delete of existing related rows stated as unsupported and `disconnect` rejected inside `create` at both the type and runtime level. Six of the nine kinds we implement therefore have no ORM construct to lower onto. The remaining three are foreclosed by our own architecture: Prisma 8's typings record that annotations attached via `configure` apply to the logical `create()`/`update()` call but **do not flow into the constituent SQL statements issued for related rows**, and ADR-0049's tripwire throws on any query reaching `beforeCompile` without an engine stamp. A nested write's per-row statements arrive unstamped, so the tripwire refuses them — and because it fails closed (ADR-0022), the tripwire wins by construction. Nested writes and our security backstop are mutually exclusive on this runtime.

**`connect` survives on the foreign-key-owning side only, lowered to a foreign key.** There it is the one kind that is not a hidden second write: it sets a column on the row being written. It lowers to a scalar FK assignment (Prisma 8 keeps FK columns directly writable) preceded by the engine's own reachability query — **two statements the terminal builds itself, so both carry the stamp**. **Assigning `null` to the same field is its counterpart** and replaces nested `disconnect`: the same column, the same lowering, the same access shape.

**On any field that does not own the foreign key, `connect` is a generation error.** Through an inverse field — `User.posts`, whose `authorId` column lives on `Post`, or the non-owning side of a one-to-one — connecting does not set a column on the row being written at all: it is N updates against the related list, each owing that list's update access and its hooks. That is exactly the hidden second write this record removes, so it is refused wherever it appears rather than only across a junction; connecting through `User.posts` is authored as updates to those `Post` rows. ADR-0043 set the precedent by refusing `.include()` on the non-FK side of a one-to-one at generation rather than growing an exception. Lowering it to Prisma's nested `connect` callback was rejected for the annotation gap above, which also covers the implicit `SELECT` Prisma issues to resolve a connect criterion; that lowering additionally inherits Prisma's restriction that a nested `connect` accepts only unique-constraint criteria.

**Its access check is kept whole.** Connecting still requires **read/query access on the target row** — evaluated in the database as `findFirst({ where: { AND: [connection, accessFilter] } })`, so arbitrary nested-relation predicates and boolean combinators work and a non-existent id folds into the same check — **and** the owning relationship field's `create`/`update` field access (#588). Dropping the reachability half would turn the foreign key into a probing oracle: a caller learns a row exists from whether the constraint fires. That is the leak class ADR-0031 and ADR-0022 each spent a record closing, and it is not worth one statement. Merging the check into the write was not available: `INSERT` has no `withWhere` (#1033).

**A junction list is the same rule seen from its most common angle, and its replacement is named in the same breath.** ADR-0048 deleted implicit many-to-many, so an edge is a row in an ordinary list with its own access rules. Adding an edge is therefore **creating that junction row, gated on the junction list's own create access** — the mirror of ADR-0018's amendment for removal, and the shape Prisma's own documentation steers toward. Synthesising the junction-row create behind a `connect` was rejected on #1047's reasoning: it hides a write against a list the access engine is supposed to see.

**Every write still opens a transaction, on new grounds.** ADR-0010 made all writes transactional so the hook contract would not depend on whether a write happened to be nested — a reason that dies with the call shape. Two reasons replace it. First, an `afterOperation` that throws must roll back its write, and that contract cannot become a function of whether the config happens to declare a hook. Second, ADR-0028's compensation bracket needs a settle signal to defer a joined write's `afterTransaction` against, and a write with no transaction has none — so the conditional version would not merely be subtle, it would take a correctness fix with it.

## Context

ADR-0010 decomposed nested writes so that a record's side-effect hooks fire identically whether it was written top-level or nested (#569). The mechanism it chose — hooks around a _single_ Prisma nested persist — was chosen precisely because Prisma owned foreign-key ordering for free, and its rejected alternative, full persistence decomposition, was called "the higher-fidelity but higher-risk option." The result is 1301 lines carrying id-diff recovery of created rows, positional `inputData↔item` pairing, deferred `AfterTask` queues, and a nine-kind handler registry of which four kinds are documented pass-throughs.

**No first-party caller uses any of it beyond `connect`.** Every example that writes a relationship emits `{ connect: { id } }` (`examples/blog/lib/actions/posts.ts:17` and five siblings); the admin UI emits only `connect` (`packages/ui/src/lib/useItemForm.ts:56`); MCP advertises only `connect` (`packages/core/src/mcp/field-schema.ts:43`). **One nested consumer beyond `connect` does exist**, and an earlier sweep of this ticket missed it: ADR-0018's remove control routes through `removeRelated` (`packages/core/src/context/index.ts:572-594`), which issues a secured `model.update()` carrying `{ [field]: { disconnect: … } }`. Its intent is an update on the related list nulling the foreign key — which is why assigning `null` replaces it exactly — but the spelling is nested input, and the claim that nothing beyond `connect` uses nested input was wrong as first stated. Four resolutions had already narrowed what this ADR must answer: ADR-0041 curated the write surface to `create`/`update`/`delete` and excluded `upsert` because it "cannot stage two hook chains against one atomic database decision," ADR-0048 deleted implicit many-to-many, ADR-0049 made the engine stamp an annotation the tripwire requires, and #1037 established that write-side scoping is a terminal concern.

Prisma 8's shape was read from the published artifacts of `@prisma/orm-family-sql@8.0.0-rc.8` (typings and shipped runtime), not from documentation, which is unreachable from the research environment.

## Considered options

- **Nested relation input leaves the payload (chosen).** Honest about what the runtime supports, deletes the repo's largest block of security-sensitive code, and applies `upsert`'s exclusion consistently — a nested write stages _N_ hook chains against one atomic decision. Costs: a caller writing a parent and its children types more, and must order the writes.
- **Keep nested input for the three kinds Prisma 8 still has.** Rejected on the annotation gap: their constituent statements cannot carry the engine stamp, so the tripwire refuses them. Making the tripwire tolerate unstamped statements to accommodate this would convert a fail-closed backstop into a fail-open one for exactly the operations that write.
- **Keep nested input and re-own foreign-key ordering** (ADR-0010's rejected decomposition, now unavoidable if nesting survives). Rejected: it reintroduces the 1301 lines under a new name to serve a capability with no first-party consumer, and Prisma 8's own ordering is a sequential per-row statement graph rather than an engine-planned batch, so what decomposition buys back is smaller than ADR-0010 assumed.
- **Drop `connect` too, and have callers assign foreign keys.** Rejected: it leaks the physical column name into the admin UI, MCP's field schema and six examples, which is a step backwards from a config-declared relationship field, and it discards the reachability check with no replacement.

## Consequences

- **A required-foreign-key cycle is unwritable through the secured surface.** Caller-ordered writes resolve every acyclic case; a cycle needs deferrable constraints. The address is `context.prisma` (renamed per ADR-0038) with its costs stated — no access control, no hooks. This documents an existing limit rather than creating one: nothing in the repo declares such a cycle, and Prisma's own nested write cannot resolve one either.
- **`context.transaction` goes from an edge case to the main road**, and ADR-0028 becomes _more_ load-bearing, not less. Its deferral queue, transaction-ownership rule and unowned-join caveat are untouched — they were stated over transaction ownership generally, never over nesting. Only the enumerator simplifies: walking the input tree for "the lists involved in this write" now yields exactly one list. A reader who assumes #899's defect left with nested writes is wrong.
- **In-transaction and transaction-boundary hooks no longer fire per nested record**, because there are none. Hook parity between call shapes is now true by construction rather than by machinery.
- **The tripwire's viability rests on an unverified premise for multi-statement operations generally.** The annotation gap is stated for related rows; whether every statement Prisma issues for a _single_ logical write carries the caller's annotation — the `SELECT` that `update()` issues to find its target row, for instance — is not established. ADR-0049 assumed it does. Tracked as its own question rather than assumed here.
- **Consumer impact, and it is wider than a payload rename.** `nested-operations.ts` and its tests are deleted. MCP's `connect` field schema and the examples' `{ connect: { id } }` survive unchanged in spelling — all of them write the FK-owning side — but two first-party callers change shape, not just lowering: `removeRelated`'s disconnect branch becomes a `null` assignment for a to-one back-reference and a junction-row delete for what used to be a many-to-many (ADR-0048), and **`useItemForm`'s `many` branch (`packages/ui/src/lib/useItemForm.ts:56`) emits `connect` through an inverse field**, which is now a generation error — the admin UI must write those edges against the related list instead. Any application passing nested `create`/`update`/`delete`/`connectOrCreate` breaks with no codemod, per the map's standing no-backward-compatibility rule.
- **ADR-0010 is superseded** — its decision is reversed, but its Considered Options is the surviving record of why decomposition was avoided, which this ADR leans on. **ADR-0018 is amended** for the create side of a junction edge; **ADR-0041** for nested input's removal from the write subset; **ADR-0028** gains a pointer to the simplified enumerator.
- **Everything about Prisma 8 here is pre-release** (`8.0.0-rc.8` for the ORM family; the CLI is already out of step at `8.0.0-rc.12`) and read from typings and shipped JavaScript. One docblock in those artifacts is already provably stale, so the three-kind vocabulary and the annotation gap both need re-verification before the spec is frozen.
