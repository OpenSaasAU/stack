# The secured surface accepts a where vocabulary the engine lowers, and the filter grammar compiles to it

Status: accepted

[ADR-0041](0041-the-secured-surface-is-an-opaque-wrapper-over-a-prisma-8-collection.md) put `where` in the secured read subset without saying what it accepts, and deleted the fragment API that the admin UI's filter engine ([ADR-0017](0017-filter-grammar-is-an-and-only-url-contract.md)) composed its `where` into. Prisma 8's own `.where()` takes an equality-only object or a lambda over field proxies. We decided the secured surface accepts neither directly: `context.db.<List>.where(…)` takes a **Where vocabulary** — a small, closed, data-shaped predicate grammar the engine owns — and the terminal **lowers** it onto Prisma's lambda in one place. The filter engine's compilation target is that vocabulary, unchanged in kind from today: a pure data value the list view hands to `.where()`, with the access filter arriving as a second entry in the Collection's `filters[]`, which Prisma folds with `AndExpr.of`. Nobody hand-merges the AND any more.

The vocabulary is data because three producers already speak data and one of them cannot do otherwise. Access rules return filter objects (ADR-0038 rejected RLS on exactly that fact); MCP's `where` argument arrives as JSON over the wire and can never be a lambda; and the filter engine is pure by construction so the URL contract stays unit-testable with no ORM import. One grammar, one lowering, one predicate-time walk ([ADR-0031](0031-a-predicate-cannot-name-a-field-the-session-cannot-read.md)) — rather than a lowering per producer.

## Decisions

- **The vocabulary is trimmed to what the engine can lower, and nothing else parses.** Scalar: `equals`, `not`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte`, `contains`. Logical: `AND`, `OR`, `NOT`. Relation: `some`, `every`, `none`, on a relation of **any** cardinality. `equals: null` lowers to `IS NULL` and `not: null` to `IS NOT NULL`. Dropped from the Prisma 7 spelling: `is`/`isNot` (Prisma 8 has no to-one form — every relation predicate is an `EXISTS`, and its accessor is the same for a to-one and a to-many), `startsWith`/`endsWith`/`mode`/`search` (no producer in the repository), and every array and JSON operator. This is the measured demand plus `notIn`, which pairs `in` at no cost.
- **Lowering is total or it throws, `sudo` included.** A key the list does not declare or an operator outside the set is a `ValidationError` naming the list and the key, never a dropped clause. `prismaFilterToSQL`'s deleted docblock ([ADR-0045](0045-vector-search-is-an-engine-owned-terminal-over-a-native-vector-column.md)) is the case this rule exists for: an unhandled operator there _widened_ the WHERE, which is fail-open under [ADR-0022](0022-access-control-fails-closed-when-it-cannot-scope.md). `sudo` bypasses access checks; an unknown operator is a bug, not a permission, and bypassing it would be the same widening with a flag on it.
- **`contains` is engine-owned and case-insensitive.** Prisma 8 ships `like`/`ilike` with no `contains` and no escape helper — the pattern is bound verbatim, no `ESCAPE` clause is rendered. So the engine escapes `%`, `_` and `\` in the value, wraps it in `%`, and lowers to `ILIKE`. No field builder assembles a LIKE pattern. The switch from Prisma 7's case-sensitive `contains` is a deliberate meaning change to existing filter URLs (`name:ada` now matches `Ada`), taken under this map's standing preference for breaking changes; ADR-0017's guarantee is that a URL _parses_ identically, and it still does.
- **A relation predicate carries the related list's `query` access inside the `EXISTS`**, ANDed with the caller's nested predicate exactly as #916's `buildAccessScopedWhere` does today. **Denied means empty set**: `some` is false, `none` and `every` are true. That is `CONTEXT.md`'s session-relative rule applied to a predicate, and it keeps a relation token from distinguishing parent rows by a related list the session cannot query.
- **The URL grammar stays frozen at AND-only.** ADR-0017's reason — every shipped construct must parse identically forever — is about URL permanence, not the ORM, so Prisma 8 opens nothing. Universal `.select()` changes nothing here either: a predicate and a projection are independent, a computed field has no column and stays unfilterable, and a to-one label predicate does not need the label column selected.
- **A to-many count comparison shrinks to presence.** Prisma 8 cannot compare a relation count in a where — `count()` exists only as an include reducer, `having` only on `groupBy` — and the id-list resolver that used to fake it is the deletion ADR-0041 already made. So `orders:0` lowers to `none()`, `orders:>0` and `orders:>=1` to `some()`, and any other count degrades to free text under ADR-0017's own degradation rule. A bookmarked `orders:>5` stops filtering; it does not error.
- **Sorting by a to-many count goes.** Prisma 8's `orderBy` takes scalar columns only. A `?sort=` naming a to-many is unsortable and ignored, the same path a read-denied field's sort takes. The count _column_ stays — display is an include reducer.
- **Sort rides the where decision.** `orderBy` is the same vocabulary (a field name and a direction), the same predicate-time walk, the same total-or-throw lowering.
- **ADR-0031's reach into a URL filter is unchanged.** A field the session cannot read has no Filter spec, so a token naming it degrades to free text over readable fields; the engine's throw stays behind it as the backstop. The degrade discloses no more than the suggestion dropdown already does — the posture [ADR-0053](0053-the-mcp-vocabulary-omits-what-a-row-independent-rule-denies.md) took for field names — and a row-dependent `read` rule still means "not filterable in the admin UI".
- **The list view's total is `aggregate`.** `.where(condition).aggregate((a) => ({ count: a.count() }))`, ADR-0041's terminal; no `count` helper survives beside it.

## Considered options

- **Accept Prisma's lambda on the secured surface and walk the returned expression AST.** Better than it first looked: `@prisma/orm-family-sql/relational-core` exports every node class publicly and every expression carries `collectColumnRefs()`. Rejected on two grounds that survive that fact. MCP's `where` is JSON and would need a lowering anyway, so this buys a second grammar rather than replacing one. And the collector tags a column ref inside an `EXISTS` subquery with the child table name only, so on a self-referential relation (`Category.parent`) a parent-list ref and a child-list ref are indistinguishable — and ADR-0031 has to know which list's rule to evaluate. A predicate-time check that cannot tell whose field it is looking at is not a check.
- **Compile the filter to a query transformer**, `(q) => q.where(…)`, that the list view composes. Rejected: the Collection's native `filters[]` already gives the composition, and the pure module would gain a dependency on the wrapper type for nothing.
- **Compile each Filter spec straight to Prisma's lambda**, handing `toCondition` the field proxy. Rejected: it leaks the ORM into every third-party field builder and produces an opaque function the predicate-time walk cannot inspect.
- **Keep Prisma 7's full where spelling verbatim.** Rejected under ADR-0041's subset principle: a spelling the lowering does not implement is a dishonest passthrough or a throw waiting for a caller, and the measured demand is nine scalar operators.
- **Rebuild the count-filter resolver as an `id IN (…)` on the new surface.** Rejected: an unbounded id list is what ADR-0041 deleted on purpose.
- **Hand-assemble a correlated count subquery from the exported AST nodes.** No typed form exists, so this is our own SQL AST construction inside the security boundary, for a comparison nobody in the repository uses beyond presence.
- **Surface the engine's throw for a denied field named in a URL.** Rejected: ADR-0031 chose the degrade deliberately, and a bookmarked URL erroring a page buys no security the degrade lacks.

## Consequences

- **`packages/core/src/filter/` survives as the pure boundary it is.** `FilterCondition` stops being "a Prisma `where` fragment" and becomes a Where vocabulary value; the module still imports nothing from the ORM. `query-validation.ts` keeps its key walk and gains the operator check.
- **The relationship Filter spec changes shape.** A to-one label match emits `{ author: { some: { name: { contains } } } }`, not `is`; a to-many emits `some`/`none` for presence and `null` (degrade) for any other count. `RELATIONSHIP_COUNT_FILTER_KEY`, `RelationshipCountFilterMarker`, `resolveRelationshipCountFilters`, and the pass-through `resolveRelationshipLabelFilters` are deletions.
- **ADR-0053's "free-form `where`, lowered to `.where()`" now has a name and a bound.** MCP's schema description "Prisma where clause" becomes the vocabulary; the key-existence and predicate-time checks it cites run in the same terminal as before.
- **`examples/composable-dashboard/app/posts/page.tsx` is unaffected** — its `OR`/`contains` search is already inside the vocabulary. This and the MCP description join the map's consumer-sweep inventory rather than becoming tickets.
- **`aggregate`'s count throws `RUNTIME.DECODE_FAILED` beyond ±(2^53 − 1)**, inherited from ADR-0041; irrelevant to a list-view total and noted so nobody rediscovers it.
- **Every Prisma fact here is read from the shipped `.d.mts`/`.mjs` at `8.0.0-rc.8`** (`ComparisonMethodFns`, the Postgres target's single contributed `ilike` operation, `RelationFilterAccessor`, `combineWhereExprs`, `collectColumnRefs`), not from a compiler run. They join the map's CLI re-verification gate.
- **ADR-0017 and ADR-0041 are amended in place**; neither is superseded. ADR-0031 stands unchanged and is confirmed.
