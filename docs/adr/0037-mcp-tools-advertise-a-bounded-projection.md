# MCP tools advertise a bounded projection, not the engine's full reach

Since ADR-0024 the derived MCP `query` tool has issued a bare read, so an assistant gets scalars and foreign keys and follows a relation with a second call. We decided to let it ask instead — but for a **projection** (`fields`, the wire form of a fragment's field selection) rather than the `include` originally proposed, and against a **generated schema that enumerates two levels** of a list's own vocabulary, refusing anything it does not advertise. The schema is deliberately shallower than the engine's own reach: `READ_INCLUDE_MAX_DEPTH` is 5, so a schema-conforming request can never reach the depth refusal at all.

An `include` was the obvious shape and is the wrong one for this consumer. It answers "which relations", leaving the returned columns fixed, so it trades round-trips for bytes — and bytes are the whole argument. A tool result lands byte-for-byte in a context window; `include: { author: true }` on a wide list returns every column of the post _and_ every column of the author, when what the assistant wanted was two of them. A projection subsumes the include (naming a relation is an include) and lets the request be **narrower** than a bare read as easily as wider, which is the only version of this feature that can reduce context pressure rather than relocate it. It also inherits ADR-0027's rule for free: a fragment read computes only the fields it selects, where an `include` read computes every computed field at every level it touches.

Enumerating the vocabulary rather than accepting a free-form object is what makes the refusal rare instead of routine. The `create` and `update` tools in the same generator already enumerate their fields with types and enums; `where` and `orderBy` do not, and the difference is that an assistant guesses at the latter and finds out at runtime. An enumerated `fields` gives the model the relation names directly, so it does not have to infer them from foreign-key columns, and it makes a whole class of request unrepresentable rather than caught. Depth 2 is what keeps that enumeration finite: self-referential relationships (`Category.parent`) make a fully-expanded schema infinite, and the payload otherwise grows as fields × branching^depth, which is prohibitive well before 5. Two levels covers what an assistant actually asks for, and the third level is a second tool call — the same round-trip the bare-read default already assumes it will make.

## Considered Options

- **An `include`, as originally proposed**: rejected above on the byte argument. Worth recording that the issue's own reasoning defeats it — the motivation was that a five-level tree is harmful because every byte reaches a context window, and `include` monotonically increases bytes per call.
- **Ship the `include` first and widen to a projection later**: rejected. It means designing the input schema twice and changing the wire shape twice, on a surface whose consumers are assistants that will have learned the first shape.
- **A free-form object, matching `where` and `orderBy`**: rejected. It keeps the tool list small, but every mistake becomes a runtime refusal the model has to recover from, and relation names stay guessable-only. The existing free-form arguments are precedent for the problem, not for the solution.
- **`$ref` self-recursion instead of a fixed depth**: genuinely attractive — compact, terminates on cycles, arbitrarily deep. Rejected because models handle `$ref`-heavy schemas poorly, which would push depth back onto the runtime refusal for exactly the requests this design is trying to make unrepresentable.
- **Enumerating to the full `READ_INCLUDE_MAX_DEPTH` of 5**, so schema and engine agree exactly: rejected on payload size, and it needs a cycle cut for self-referential relations regardless, so it does not even buy a clean rule.
- **Serving anything the engine accepts, treating the schema as a hint**: rejected. Two depth limits would exist and the schema would understate what works, which is the ambiguity the enumeration was chosen to remove.
- **A static, session-independent schema**: rejected once the filtering was understood to be list-level. The disclosure it closes is "which lists exist", which is small but real, and the cost is only that `tools/list` stops being cacheable across sessions.
- **Naming the argument `select`**: rejected despite being what an assistant most likely expects from Prisma and GraphQL familiarity. `select` is documented in this codebase as _not honoured_ on a `context.db` read and called a footgun; giving one word two meanings across one product is worse than the unfamiliarity. `query` was rejected for reading badly inside a tool already named `_query`.
- **Configurable depth and nested ceiling**: rejected, following ADR-0026's position on the depth cap itself — changing a number in response to a caller who actually hits it beats guessing at a knob before anyone has asked for one.
- **Extending `fields` to `create`/`update`/`delete`**: deferred. A write returns one record the assistant just authored, so the context argument barely applies, and it would multiply the generated schema across four tools per list.

## Consequences

- **This lands a visible behaviour change, not just an added argument.** A list whose operation-level `query` access denies the session outright disappears from `tools/list` entirely, where today every list's tools are listed regardless. A client that expects a tool to exist will see it vanish. It ships as a minor with that called out, not as a patch.
- **`tools/list` becomes per-session**, so any client-side caching of the tool list is per-session too, and operation-level access functions — which may hit the database — now run on every listing.
- **It depends on the error surface landing first.** Strict refusal only works if the refusal reaches the model; while tool failures come back as JSON-RPC protocol errors the host may never show it, a strict schema is worse than a permissive one, because one wrong field name becomes an unrecoverable transport error.
- **The depth refusal becomes near-unreachable from this surface.** `AccessScopeDepthExceededError` remains, and a client that ignores the schema can still provoke it, but no schema-conforming request reaches depth 5. The cap keeps guarding `context.db` callers, who are unaffected by any of this.
- **A computed field's declared dependencies still fold against the engine's cap, not the schema's.** Schema depth 2 leaves three levels of headroom, so a projection that selects a computed field whose closure reaches deeper behaves exactly as an equivalent `context.db` read does today, including the runtime refusal if the fold overflows.
- **Nested pagination is bounded because it multiplies.** A nested to-many defaults to 5 and caps at 50, deliberately tighter than the root tool's 10 and 100, since the two compose into the row count of a single result. A to-many's count is requestable in place of its rows, so "how many are there" costs a few bytes rather than a speculative page.
- **Access control is untouched.** This changes what a caller may ask for, never what it may receive: field-level denial still drops values at read time, and a relation to a list the session cannot query is still dropped exactly as it is today.

## Amendment — the vocabulary is filtered at field grain too (ADR-0053)

[ADR-0053](0053-the-mcp-vocabulary-omits-what-a-row-independent-rule-denies.md) moves the grain of the per-session filtering from tools to fields without touching the principle. The `fields` projection schema, at both enumerated levels, and the `create`/`update` tools' `data` schemas omit a field whose rule is **row-independent** (ADR-0031's classifier, now named in `CONTEXT.md`) and denies the session; a rule that needs the row or the payload leaves the field advertised. A `create` tool whose required field is denied that way is not advertised at all, on the same reasoning this record used for a list whose `query` denies. The refusal for a dropped field is identical to the one for an unknown field. Tool-level filtering, depth 2, the wire shape and strict refusal all stand; "Access control is untouched" in the consequences still holds, because the schema decides disclosure and never visibility.

The same record replaces this record's lowering: `fields` is now a translator onto the secured surface (`.select()`, `.include()` refinements, `combine` for rows plus count), and the `_count` folding and `pickFields` trim are deleted with the fragment API (ADR-0041).
