# A row lock is an engine-owned two-statement terminal

Status: accepted

[ADR-0042](0042-transactions-lose-isolation-levels-and-errors-become-stack-owned.md) deleted `isolationLevel` and made `SELECT … FOR UPDATE` on the contended parent row the documented capacity gate — the replacement for `Serializable` + retry that [ADR-0012](0012-interactive-transactions-rebind-the-secured-context.md) was written for. It then recorded that the gate was **not writable through the secured surface**, because [ADR-0041](0041-the-secured-surface-is-an-opaque-wrapper-over-a-prisma-8-collection.md) owns which terminals the engine can scope, and handed the question on.

This record closes it. The secured surface gains a **`.forUpdate()` builder modifier**, transaction-only and enforced by the type, whose terminal executes **two statements**: the scoped ORM read that resolves access and yields primary keys, then an engine-written raw `SELECT … WHERE <pk> = ANY($1) ORDER BY <pk> FOR UPDATE` over exactly those keys. `pg_advisory_xact_lock()` gets a small seat of its own on the transaction context.

## Context

The ticket weighed a `.forUpdate()` terminal against reaching through the Unsafe surface for the lock statement alone. Investigation against the published Prisma 8 packages (`prisma@8.0.0-rc.12`, ORM line `8.0.0-rc.8`) removed the premise both options rested on: **Prisma 8 can emit no locking clause anywhere.**

- No lock method on `Collection`, and no lock field on `CollectionState`.
- No lock clause on the typed SQL builder either — `db.sql`'s `SelectQuery` exposes `select`/`where`/`orderBy`/`groupBy`/`having`/`distinct`/`limit`/`offset`/`annotate`/`build` and nothing more.
- `beforeCompile`'s `SelectAst` has no lock field and no `withLock`, and the lowered plan's `.sql` is a `readonly string`, so no later hook can append one.
- Decisively, the Postgres renderer's `renderSelect` emits `SELECT / FROM / JOIN / WHERE / GROUP BY / HAVING / ORDER BY / LIMIT / OFFSET` — **there is no slot after OFFSET for a locking clause at all.** Nothing in the ORM can produce one even if an AST field were added.
- Advisory locks are likewise raw-only; Prisma's own migration control plane reaches them through the raw driver, as `select pg_advisory_xact_lock(hashtext($1))`.

The only route to `FOR UPDATE` is `db.raw.sql` → plan → `tx.query(plan)` — **raw text**. That is what forecloses the shape the ticket assumed. A _single_ scoped `SELECT … FOR UPDATE` would need this stack's access filter rendered into SQL text, which is `prismaFilterToSQL` — the translator [ADR-0045](0045-vector-search-is-an-engine-owned-terminal-over-a-native-vector-column.md) deleted precisely because an unhandled operator _widens_ the WHERE clause, which is fail-open under [ADR-0022](0022-access-control-fails-closed-when-it-cannot-scope.md). Resurrecting it to build a lock is not a cost trade; it reintroduces the exact artifact this migration removed on security grounds.

Two statements sidestep it entirely. The access decision is made by the ORM read; the raw statement's predicate is then a list of primary keys, which needs no access reasoning of its own.

## Decision

- **`.forUpdate()` is a builder modifier, not a terminal or a terminal option.** ADR-0041's builders are synchronous and access resolves lazily in the terminal; the modifier survives that split trivially, because it sets a synchronous flag carrying no access semantics — the terminal reads it when deciding whether to issue the second statement.
- **It is reachable only on a transaction-bound builder**, a compile error elsewhere. `FOR UPDATE` outside an explicit transaction takes the lock and drops it at statement end: it compiles, runs, returns rows, and does nothing. [The transaction research](https://github.com/OpenSaasAU/stack/issues/1036) established that Prisma 8's `tx` is a distinct nominal type, so the restriction costs a type parameter rather than a runtime throw.
- **`forUpdate()` only.** No `forShare`, no `NOWAIT`, no `SKIP LOCKED`, though all are free at the SQL level once the engine writes the statement. `SKIP LOCKED` returns a row held by another transaction as _absent_, which is indistinguishable from a row the Access Filter denied — it would make Silent failure mean two things at once. `NOWAIT` needs a failure mode bolted onto the error set ADR-0042 has only just finished normalising. Each stays additive.
- **Two statements, both engine-issued.** The scoped ORM read runs first and resolves operation access, merges the Access Filter, and applies Field Visibility exactly as any read does. The engine then issues the raw lock statement over the primary keys that read returned.
- **The engine always emits `ORDER BY <pk>` before `FOR UPDATE`.** Because the engine writes the statement rather than the caller, lock acquisition order is deterministic across every session, which eliminates the overlapping-set deadlock class (two transactions locking the same rows in opposite orders) by construction rather than by advice.
- **`first()` and `all()` carry the modifier; `aggregate` and `nearest()` do not.** An aggregate returns no primary keys, so there is nothing to feed the second statement.
- **A terminal never returns a row it did not lock.** The lock is taken after the access read, so a row deleted in the interval locks nothing: `first()` yields `null` and `all()` yields the surviving subset. `null` therefore now means denied-or-vanished, which extends a conflation Silent failure already makes deliberately, and is not information the caller is entitled to distinguish.
- **The lock is taken on the identity row.** For a multi-table-inheritance variant the lock statement hits the base table, so a concurrent transaction touching only a child table's columns is not blocked; `include()`d relations are not locked either. This is sound because the parent row lock in the gate is a **mutex token**, not protection for the parent's own data — every racer contending on that entity takes the same token before counting children, which is the whole mechanism. `forUpdate()` locks the identity row, and says so.
- **`advisoryLock(key: string)` sits on the transaction context, not on `context.db`.** It locks a number rather than rows, so it belongs to no list, and there is nothing for the engine to scope. The key is hashed with `hashtext()`, matching what Prisma does internally. `hashtext` is 32-bit, so distinct keys can collide — a collision costs spurious serialisation, never a missed lock, which is the safe direction.

## Does a row lock pass ADR-0041's inclusion test?

ADR-0041 admits a method only if the engine knows how to scope it, and the ticket's doubt was whether an access-scoped lock is the same lock the caller wanted — the point of the gate being to lock the rows the _database_ will contend on.

Under the two-statement design it passes, and more cleanly than a one-statement lock would have. The locked set is **provably a subset of the readable set**, because the raw statement's predicate is literally the keys the scoped read returned; and "which rows did I lock" is answerable from the terminal's own return value, which the raw form does not offer. Denial is coherent rather than broken: nothing readable means nothing locked and `null` back, so the gate cannot run — correct, since the gate's premise is that you can read the parent row.

The residual property, recorded rather than solved: a caller whose Access Filter is narrower than the contended set **under-locks**, and a concurrent writer on another session may touch rows they never locked. That is identical to what scoped `update` and `delete` already do — you only ever act on rows you can see — and it does not bite in the capacity gate, where the parent is a single row and access on it resolves to a boolean rather than a narrowing.

## Considered Options

- **One raw statement with the Access Filter rendered to SQL text.** The obvious shape, and the reason the ticket existed. Rejected: it requires `prismaFilterToSQL`, deleted by ADR-0045 as fail-open under ADR-0022. Reintroducing a filter-to-text translator to build a security primitive inverts the reason it was deleted.
- **No new surface — the gate reaches through the Unsafe surface for the lock only**, with writes still going through `txContext.db`. Rejected on two counts. It puts a documented security-boundary bypass inside the pattern the docs recommend; and the lock statement is a _read of the parent row_, which is exactly what the engine exists to scope, so the caller would read a row they may not be allowed to read and then make a capacity decision on it. It is also more awkward than it looks: `tx` carries no `raw`, so the caller must close over the outer client's `db.raw`, build a plan, and hand it to `tx.query`.
- **Lock via a scoped no-op `update()`.** `where(...).update(...)` already merges the Access Filter and takes the identical row lock, at zero new surface and no raw SQL. Rejected: it demands _update_ access where the caller needs only to read the parent (in the gate the write is to a child list, not the parent), fires the whole Write Pipeline including hooks, bumps `updatedAt`, and writes WAL — a lock disguised as a mutation.
- **An option on the existing terminals** (`first({ lock: 'update' })`) rather than a builder modifier. Follows Prisma's own shape, and cannot be set-then-forgotten on a builder passed around. Rejected because the transaction-only restriction would then have to be spelled by varying every terminal's signature between the two surface shapes, instead of by one method's presence.
- **`first()` only, refusing multi-row locks.** Would remove the deadlock class by construction rather than by ordering. Rejected once `ORDER BY <pk>` was in hand: deterministic ordering addresses the same hazard without costing the legitimate multi-row cases.
- **Throwing when the row vanished between read and lock**, rather than returning the empty value. Rejected: it introduces a second failure mode into a surface whose denial semantics are deliberately silent, immediately after ADR-0042 normalised the error set. Re-reading and retrying once was also rejected — it puts an implicit retry policy in core, which ADR-0012 deliberately declined to do.
- **Amending ADR-0041 in place.** Rejected for the reason ADR-0041 itself gave for not rewriting ADR-0039, and following ADR-0045's precedent one ticket earlier: a record decided by a different question at a different time reads better closed by a successor than silently rewritten.

## Consequences

- **A lock costs two round trips**, unavoidable while the ORM can carry no lock clause. The first is a query the engine would have run anyway; the second is a primary-key lookup on an indexed column.
- **The lock statement is raw, so ADR-0038's tripwire cannot see it.** Raw plans bypass `beforeCompile` entirely, so the engine's own second statement is neither stamped nor refusable. This is the Unsafe surface's "raw SQL is outside this entirely" rule applying to the engine itself, and it is acceptable here for the reason the rule exists: scoping a raw statement is its author's job, and its author is the engine, whose predicate is keys it resolved through the secured path one statement earlier.
- **The generated context acquires a second shape.** The transaction-bound surface carries `forUpdate()` and `advisoryLock()` where the plain one does not. [ADR-0032](0032-generated-context-and-customdb-are-interfaces-not-type-aliases.md)'s rule extends to it unchanged — it is a generated `interface`, not a type alias.
- **`CLAUDE.md`'s interactive-transaction example is rewritten** to the lock form, completing the rewrite ADR-0042 asked for but could not supply a secured spelling of.
- **A GA re-verification item.** If Prisma 8 GA ships a locking clause on the `Collection` or on `db.sql`, this collapses to a one-statement modifier. That is purely additive — the surface, the transaction restriction, the vanished-row rule and the advisory seat are all unchanged by it, and only the terminal's internals move. Nothing here needs reversing if the fact changes.
- **The nested-writes question is sharpened, not reopened.** `where(...).update(...)` already takes its own row locks and a read-side modifier adds no obligation to the Write Pipeline. But the engine now owns a locking primitive with deterministic primary-key ordering, which is directly relevant to [ADR-0010](0010-nested-writes-decompose-into-a-single-transaction.md)'s decomposition of nested writes into one transaction — sibling writes acquiring locks in inconsistent order is exactly the deadlock shape that primitive addresses.
- **Everything here was reasoned against `8.0.0-rc.8`**, read from published package sources. Prisma's documentation is egress-blocked from the session that established these facts, so none of the five negatives above was confirmed against Prisma's own docs or a stated rationale for the omission.
