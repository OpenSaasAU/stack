# The configured ORM client stays behind an async seam; document the synchronous escape hatch instead of adding one

Status: accepted (amended 2026-08-30 — see below)

> **Further amended 2026-09-02 by [What is the local dev loop when the Prisma 8 CLI has no standalone prisma dev?](https://github.com/OpenSaasAU/stack/issues/1095)** (Prisma 8 map). The "one shared module for connection selection" this record insists on now has a name: core's `resolveDatabaseUrl()` ([ADR-0063](0063-the-dev-database-is-a-stack-run-in-process-postgres-shared-with-the-test-harness.md)) — `DATABASE_URL` if set, else the running Dev database's state file, else a throw. The generated context and `prisma.config.ts` call it, and a synchronous-construction consumer's pool factory should too, so a second client under `pnpm dev` reaches the same database as the first.

> **Further amended 2026-09-02 by [Do ADR-0008 and ADR-0011 survive a contract-constructed client?](https://github.com/OpenSaasAU/stack/issues/1067)** (Prisma 8 map). The amendment below says a synchronous-construction consumer builds its second client "from the generated contract and the connection directly". [ADR-0054](0054-the-generated-bundle-loads-natively-under-plain-node-from-the-committed-contract.md) spells that out: the shared plain module that used to hold `prismaClientConstructor` now holds the `pg` pool factory that `opensaas.config.ts` names as `db.client.pg` (ADR-0049), and the consumer builds `postgres<Contract>({ contractJson, pg: pgFactory() })` from the same `import … from '../prisma/contract.json' with { type: 'json' }` the generated context uses. Still a second connection, still the raw client, still one shared module for connection selection. The lazy-`Proxy` recipe is unchanged, and the generated `getPrisma()` is where the factory is called — after the config promise resolves, so the Promise-valued-config case this record describes is handled where it always was.

> **Amended 2026-09-02 by [What does the auth plugin hand better-auth when there is no Prisma Client?](https://github.com/OpenSaasAU/stack/issues/1086)** (Prisma 8 map). The adapter the lazy `Proxy` defers is no longer better-auth's Prisma adapter — which drives Prisma Client's per-model delegates and cannot be pointed at a Prisma 8 client — but the stack-authored Auth adapter of [ADR-0060](0060-better-auth-is-driven-by-a-stack-authored-auth-adapter-over-the-unsafe-surface.md), built from the resolved context's Unsafe surface. The recipe and `createAuth(config, rawOpensaasContext)`'s signature are unchanged: the `Proxy` defers method calls, not client construction, which is exactly why the adapter's shape never reached it.

> **Amended by [What is the local dev loop and the provider story once SQLite is gone?](https://github.com/OpenSaasAU/stack/issues/1040)** (Prisma 8 map). The **decision stands**: client access stays behind an async seam, and there is still no synchronous framework accessor — config resolution remains async because plugins can contribute config asynchronously. What changes is the **third recipe's mechanism**. It is written around re-running the app's own `prismaClientConstructor` against the generated `PrismaClient`, and Prisma 8 deletes that option: its config is `defineConfig({ contract, db: { connection } })`, with no client class handed to the app to wrap. Under Prisma 8 a synchronous-construction consumer builds its second client from the **generated contract and the connection** directly. Everything the original recipe warns about carries over unchanged — it is still a **second connection**, still the **raw** client with none of `context.db`'s access control or hooks, and adapter/connection selection must still come from one shared module rather than being re-derived by hand. The other two recipes are untouched: `await getContext()` is unaffected, and the lazy-`Proxy`-over-`rawOpensaasContext` pattern that `@opensaas/stack-auth`'s `createAuth` uses defers method calls, not client construction, so it never depended on `prismaClientConstructor` at all.

The generated bundle exposes the configured Prisma client only through **async** seams — `getContext()`, `context.prisma`, and `rawOpensaasContext` (a `Promise<Context>`) — and that stays true. There is **no new synchronous, framework-provided client accessor**. Config resolution is async by design (plugins can contribute config asynchronously, so the context factory must `await getConfig()` before it can build the client), which means the framework's own singleton client cannot be constructed without an `await` anywhere in the chain. A module-init-time consumer that must construct its own client synchronously (typically a third-party library with a synchronous-construction contract, e.g. an auth adapter built at import time) is not a framework gap to close — it is documented as a **recipe**: import the generated `PrismaClient` and the app's own `prismaClientConstructor` and build a second, independent client instance from the same single source of truth the generated context uses.

## Context

Filed as issue #682: a module-init-time consumer (concretely, a third-party ORM adapter — the same shape better-auth's own Prisma adapter has) needs a client instance constructed synchronously at import time, but the only sanctioned path to the stack's configured client is `getContext()`/`context.prisma`, both async. The issue asked to decide between (a) a synchronous, client-only accessor, or (b) a documented integration recipe.

The framework already solved the _general_ "module-init consumer, async config" problem for its own better-auth wiring, without a synchronous seam: `createAuth()` (`packages/auth/src/server/index.ts`) accepts `rawOpensaasContext` — the async raw-context Promise — and returns a `Proxy` synchronously. Every property access on that Proxy lazily awaits the underlying `getAuthInstance()`, which itself awaits `rawOpensaasContext` before calling `betterAuth()`. So `export const auth = createAuth(config, rawOpensaasContext)` can sit at module scope (satisfying Next.js's route-handler import conventions) even though the real `betterAuth()` instance, and the `context.prisma` it wraps via `prismaAdapter(context.prisma, { provider })`, aren't built until the promise resolves.

That pattern only works because better-auth's _own_ adapter construction is itself deferrable behind the Proxy. A consumer whose contract truly requires a resolved client object at import time — not just deferred method calls — cannot use the Proxy trick; the Proxy defers the _methods_, not the underlying client value. For that shape, the only correct move is a second, independently-constructed client, built the same way the generated context builds its singleton (same `prismaClientConstructor`, same generated `PrismaClient` import), so there's a single source of truth for connection/adapter selection even though there are two client instances.

Also, the generated `rawOpensaasContext` doc comment (`packages/cli/src/generator/context.ts`) said "Raw context for synchronous initialization" — misleading, since `rawOpensaasContext` is an async IIFE resolving to `Promise<Context>`, not a synchronous value. Fixed as part of this change: the comment now describes it as a Promise meant to be _passed_ to a lazy-Proxy consumer like `createAuth`, not awaited at module scope.

## Considered options

- **Document two recipes (await-capable vs. synchronous-construction) instead of adding an API (chosen).** No new public surface, no change to the async-config-resolution design. Every consumer shape the issue describes already has a working path: `await getContext()`/`context.prisma` for request-scoped code; `rawOpensaasContext` + a lazy Proxy (as `createAuth` demonstrates) for module-init consumers that only need to defer method calls; a hand-built second client from the generated `PrismaClient` + the app's own `prismaClientConstructor` for module-init consumers that need a resolved client value synchronously. The cost is entirely documentation — consumers must discover and apply the pattern themselves.
- **Add a synchronous, client-only accessor (`getPrismaSync()` or similar).** Rejected. Infeasible without a redesign: the client cannot be constructed before `getConfig()` resolves, and `getConfig()` is async because plugins can contribute config asynchronously. A "synchronous" accessor would either have to throw until warmed by a prior async call (a footgun — works in dev after the first request, breaks on cold start) or force config resolution to become synchronous everywhere, which is a much larger change than this issue's scope.
- **Add an async `getClient()`/`getPrisma()` export alongside `getContext()`.** Rejected as redundant. `getContext()` already returns `context.prisma`; a second async accessor returning the same value adds a second name for the same seam without adding capability, working against the stated goal of keeping the generated surface small.

## Consequences

- **No new generated export.** `getContext()`, `context.prisma`, and `rawOpensaasContext` remain the complete client-access surface; this ADR closes the "should we add an API" question rather than opening one.
- **The synchronous escape hatch is a documented pattern, not a framework feature.** A consumer that builds its own client this way owns a **second client instance/connection**, separate from the framework's singleton, and that client is the **raw Prisma client** — it carries none of `context.db`'s access control or hooks. Both trade-offs are intentional for this use case (a third-party adapter typically wants exactly the raw client) and must be stated wherever the recipe is documented, not left implicit.
- **Single source of truth stays the app's `prismaClientConstructor`.** The recipe reuses the same generated `PrismaClient` import and the same `prismaClientConstructor` the generated context calls — it does not re-derive adapter/connection selection by hand. Projects with more than one synchronous consumer should factor `prismaClientConstructor` invocation into a small shared module so both the generated context and the hand-built client stay in sync if the adapter setup changes.
- **`rawOpensaasContext`'s generated doc comment is corrected** (`packages/cli/src/generator/context.ts`) to describe it as a `Promise<Context>` intended for the lazy-Proxy pattern, not a synchronous value — this affects newly generated `.opensaas/context.ts` files, not a runtime behavior change.
