# The generator emits a TypeScript contract module, not PSL

`pnpm generate` builds `prisma/schema.prisma` by string concatenation — 603 lines of PSL assembly in `packages/cli/src/generator/prisma.ts`, asserted by 3639 lines of string-containment tests. Under Prisma 8 the generator's target becomes a **TypeScript `defineContract` module**, emitted standalone and fully literal, and `pnpm generate` then shells out to `prisma contract emit` to produce the committed `contract.json` and `contract.d.ts`. **PSL stops being emitted at all** — `prisma/schema.prisma` ceases to exist.

[#1032](https://github.com/OpenSaasAU/stack/issues/1032) removed the third option before this decision started: emitting `contract.json` directly is not supported, because the hashes are computed _by_ emission and a hand-written contract has no way to acquire a valid signature. That leaves PSL text against the TypeScript builder, and Prisma's own documentation names our exact situation as the builder's reason to exist — "parts of the schema are assembled programmatically from other static definitions". A generator is that case in its purest form. The builder also replaces string assembly with typed calls: `rel.belongsTo(User, { from: 'userId', to: 'id' })` takes a model _object_, so a mistyped model reference is a compile error where today it is a `@relation` string that parses fine and fails at emit.

Prisma calls PSL the preferred mode and says "you give up nothing by staying with PSL". That is advice to humans authoring a schema by hand, and it is right for them. It is not advice to a program assembling one, which gets nothing from a text format it must produce with template literals and cannot type-check.

**The emitted module is standalone and fully literal.** The builder imposes purity rules — no `process.env`, no clock, no random, no side effects, and plain values only, since functions, class instances and `Date` do not serialize — and `opensaas.config.ts` violates every one of them. So the generator evaluates the config and emits a contract module that imports nothing from it. Purity then holds **by construction** rather than by a discipline nothing enforces, and the emitted file is readable on its own. It also keeps ADR-0008 and ADR-0011 (bundle loadability of the config) a separate concern: the contract is a build-time artifact, not something loaded through the config's own loader.

**Nothing regex-shaped survives.** `extendPrismaSchema` was regex over generated PSL and is dropped; so is its field-level sibling, the `{ fkLine, relationLine }` pair used to reach `onDelete`/`onUpdate`. Both are replaced by first-class options rather than by a structured transform, because every legitimate use they served now has a home in the contract: multi-schema Postgres is namespaces (`domain.namespaces` / `storage.namespaces` / `roots[].namespace`), preview features are extension packs, output paths already live in `prisma.config.ts`, and referential actions are `constraints.foreignKey(...)` options over five named actions. A general "modify the artifact" seam would be a place for those five to be reinvented badly.

## Considered Options

- **Keep emitting PSL text.** The least-change option and the mode Prisma documents best. Rejected: it keeps string concatenation as the mechanism and keeps every model reference stringly-typed, on a migration that is rewriting the generator regardless. The one real argument for it — that `contract infer` writes PSL, so introspection output would match our output — does not apply, since adopting live databases is out of scope for this map.
- **PSL now, the TypeScript builder later.** Rejected as two generator rewrites where one will do. The migration has no compatibility obligations to stage around.
- **Emit `contract.json` directly.** Foreclosed by #1032 rather than rejected here: unsupported, and unsignable.
- **Emit PSL alongside the contract as a human-readable reference.** Rejected. Prisma is explicit that a project declares exactly one source of truth and that the other form must be kept out of the project or treated as generated. The emitted `contract.json` and `contract.d.ts` are committed and diffable and serve the review use case; a second generated view of the same truth is something that can drift and something a developer will eventually edit by mistake.
- **A contract module that imports shared definitions from the config**, keeping one source of truth in the file tree. Rejected: purity would then depend on nothing impure being reachable through those imports, which is an invariant with no enforcement and a failure mode (a `process.env` read three imports deep) that surfaces as an emit error far from its cause.
- **A typed post-processing hook** (contract in, contract out) replacing `extendPrismaSchema`'s string hook with a structured one. Rejected for now: the three uses it would serve each have a first-class home, and a general seam invites schema surgery the migration is trying to end. It can be added when a real case appears that the named options cannot express.
- **Preserving index `sort:` by lowering it to an expression index** where the target permits. Rejected: the construct is deliberately absent from Prisma 8 on SQL targets (the contract's index entry is `columns: string[]`, with nowhere to put a direction), and emulating a dropped construct costs generator complexity to preserve a declaration that will read as supported when it is not.
- **Dropping `db.indexes` entirely** in favour of the contract's own index surface, which is richer (partial, expression, type, options). Rejected: the field-name-to-column resolution and its validation errors are the value `db.indexes` adds, and they are worth keeping. The richer surface can be exposed later without removing this one.
- **Keeping `getPrismaType` and translating PSL type names to codecs internally.** Rejected: the mapping is lossy in both directions and would hide the contract's richer types (the three `BigInt` variants, `typeParams`, value objects) behind a vocabulary that cannot express them. A fallback path alongside the new method was rejected for the same reason plus the cost of two code paths.
- **Reading the relationship graph back from the emitted contract** rather than deriving it from config. Rejected on ordering: ADR-0025's declaration closure is computed _during_ generation, before emission, so consuming the contract would invert the dependency and force a two-phase generate.

## Consequences

- **`prisma/schema.prisma` stops existing**, along with `packages/cli/src/generator/prisma.ts`'s PSL assembly, the `generator client` / `datasource db` blocks, and `previewFeatures = ["multiSchema"]`. `prisma-config.ts`'s output changes shape entirely: `definePrismaConfig({ orm: ormConfig({ contract, extensions, db }) })`.
- **The field-builder contract breaks for every third-party field package.** `getPrismaType`, `getPrismaColumns` (ADR-0006's multi-column path) and `getPrismaRelation` are replaced by a contract-shaped method returning codec, native type, nullability and column mapping. `@opensaas/stack-rag`, `@opensaas/stack-storage` and `@opensaas/stack-tiptap` all move. This is the deliberate cost of not translating: it is stated as a break rather than softened with a fallback.
- **`pnpm generate` stays one command but gains a subprocess.** It writes the contract source and `prisma.config.ts`, then invokes `prisma contract emit`. Both emitted artifacts are committed; CI re-runs emission and fails on a dirty tree, which is the workflow Prisma documents. **This is unverified** — the `prisma` CLI is broken at `8.0.0-rc.8`, so the shell-out and its flags rest on documentation. Re-check before the spec freezes.
- **`db.indexes` keeps its API, minus `sort`.** Field-name-to-column resolution and its validation errors survive unchanged. A `sort` entry becomes a generate-time error naming the list and the entry, not a silent drop. Named entries emit as `name:` (a wire name with a content-hashed physical name) rather than today's `map:`, since `map:`'s purpose — adopting an exact existing physical name — is table adoption, already out of scope for this map.
- **Relationships gain typed `onDelete` / `onUpdate`** over the contract's five referential actions, replacing the string-munging hook. Prisma's own scorecard marks `onUpdate` as implemented-but-untested, which is worth knowing before relying on it.
- **`.opensaas/types.ts` shrinks substantially.** It stops re-deriving scalar read and write shapes — `contract.d.ts` emits `FieldOutputTypes` and `FieldInputTypes` separately, with per-field `nullable` and `codecId` — and keeps only what the contract cannot express: virtual and computed field types, hook argument types, the write-narrowing overrides (#608), and the access-controlled surface ADR-0039 defines. How much survives is bounded by that ADR's surface, which is not yet designed in detail.
- **The test strategy changes shape, not just content.** The generated contract module is snapshotted as our own deterministic output; a few representative configs additionally run emission and assert structurally on `contract.json`. An entire class of assertion — column padding, attribute ordering, blank lines — stops existing, because Prisma's canonicalizer owns formatting. The structural half depends on a working CLI.
- **The relationship graph is still derived from config**, with the contract's relation types available as a cross-check rather than as the source. ADR-0025 and ADR-0023 are unaffected in substance.
- **What the deleted PSL constructs _become_ is not settled here.** `@default(cuid())` → `cuid(2)`, `@updatedAt` → application-side `temporal.updatedAt()`, and implicit many-to-many → explicit junction models are each a behaviour change rather than a rename — most sharply the last, since a junction becomes an ordinary list with its own access rules, and the second, since `updatedAt` stops being a database-level guarantee. Recorded separately.
