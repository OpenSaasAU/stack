# The extension contract space is a generator emission, and Prisma runs `CREATE EXTENSION`

Status: accepted

[ADR-0049](0049-extension-packs-are-declared-the-tripwire-is-stack-owned.md) decided that declaring an extension pack drives three emissions and that `CREATE EXTENSION vector` "is the deployment's job", because running it from `db:update` would need privileges the stack should not assume and "cannot work on `prisma dev` at all". [#1070](https://github.com/OpenSaasAU/stack/issues/1070) measured both halves false at `prisma@8.0.0-rc.12`: an extension pack is a **contract space** with a migration of its own, Prisma plans `CREATE EXTENSION IF NOT EXISTS vector` ahead of the app's DDL on every path, and it did so on PGlite. This record decides that the **extension contract space is the fourth generator emission**, that **Prisma runs `CREATE EXTENSION`** everywhere, and that the deployment's job narrows to provisioning.

## Context

Everything below was read from the `8.0.0-rc.8` packages and run against the `rc.12` CLI on [#1096](https://github.com/OpenSaasAU/stack/issues/1096); the PGlite runs used `@prisma/dev@0.25.2`, the Postgres runs a Homebrew 14.20 without pgvector.

- **The extension space is pack-shipped, fixed content.** `@prisma/orm-extension-pgvector/control` embeds one migration package — `20260601T0000_install_vector_extension` (`migrationHash 12b0…`, `providedInvariants: ['pgvector:install-vector-v1']`), a head ref at storage hash `3d2c…`, and an empty-models contract whose `storage.types.vector` carries the `pg/vector@1` codec — and hands them to the toolchain through `contractSpaceFromJson`. The op is `CREATE EXTENSION IF NOT EXISTS vector` with a `pg_extension` precheck and postcheck. Nothing about it is derived from the app: its content is a function of the installed pack version alone.
- **`migration plan` only copies it to disk.** Phase 1 of the plan pipeline, `runContractSpaceSeedPhase`, writes `migrations/<space>/<package>/{migration.json,ops.json}`, `migrations/<space>/refs/head.json` and the space's snapshot at `migrations/snapshots/<hash>/contract.{json,d.ts}` — five files — then phase 2 plans the app space. The function is exported from the public subpath `@prisma/orm-toolchain/cli/control-api`, takes `{ migrationsDir, extensions }` with the `/control` descriptors, and is idempotent: a second call reports `action: 'unchanged'`. No CLI subcommand runs phase 1 alone; `migration plan` always writes an app package as well, and refuses `--to @empty`.
- **`db init` and `db update` read the space from disk and never write it.** Their shared loader checks the layout before planning and refuses a declared-but-absent space with `MIGRATION.CONTRACT_SPACE_LAYOUT_VIOLATION — [declaredButUnmigrated] pgvector` (`--dry-run` included). With the five files present and **no app space on disk at all**, `db update --dry-run` plans `pgvector.install-vector-extension` then `table.Doc` across two spaces, and `db init` on PGlite applied both and signed both markers.
- **A pre-installed extension is skipped, not conflicted.** The runner checks each op's postcheck first and records `runner: { skipped: true, reason: 'postcheck_pre_satisfied' }` when it already holds. With `CREATE EXTENSION vector` run by hand before `db init`: `Applied 1 operation(s) across 2 space(s), database signed` — two planned, one executed, both markers written, `db verify` clean, a following `db update` a no-op across both spaces.
- **A server without pgvector fails cleanly.** `MIGRATION.RUNNER_FAILED … could not open extension control file … vector.control` (`sqlState 58P01`, `failingSpace: pgvector`), reproduced locally; the app space is untouched because every apply runs in one transaction.
- **pgvector is not a trusted extension.** Upstream `vector.control` at 0.8.6 (and PGlite's bundled 0.8.0) carries no `trusted = true`, so `CREATE EXTENSION vector` needs a superuser or a provider grant. The Dev database and CI's container run as superuser; Neon, Supabase and RDS grant the app role the extension; a locked-down Postgres does not.
- **`db update` already writes under `migrations/`.** Against the project's default URL it writes the post-command contract to the snapshot store and advances `migrations/app/refs/db.json` — the `db` ref the offline planner resolves `--from` through. ADR-0003's "writes no migration directory" was true of migration _packages_ only.
- **The three-file emission stands, with the spellings corrected.** `contract emit` succeeds without `extensions` in `prisma.config.ts` when the TypeScript contract carries the pack, but `db init` then fails at `expandNativeType` for `pg/vector@1`; the runtime client needs the `/runtime` descriptor for the same codec. The builder key is `defineContract({ extensions: { pgvector } }, …)` with the `/pack` descriptor — not `extensionPacks` — and the field is `field.column(type.pgvector.Vector(n))`.

## Decisions

- **The extension contract space is the fourth emission of one declaration.** `pnpm generate` calls `runContractSpaceSeedPhase({ migrationsDir, extensions })` from `@prisma/orm-toolchain/cli/control-api` with the `/control` descriptors of every declared pack, after it writes the contract module and `prisma.config.ts` and before it shells to `contract emit`. The five files it writes are **committed**, regenerated on every `generate`, and covered by the same dirty-tree check ADR-0040 already runs on `contract.json`: they are derived from `db.extensions` and the installed pack version exactly as the other three emissions are, and a stale copy is a wrong-version migration, which is the one thing CI should catch. `migration plan` does not enter the dev loop, `db:update` gains no first-run step, and a pack upgrade that ships a new package shows up as a generate diff.
- **Prisma runs `CREATE EXTENSION`, on every path.** The Dev database installs it on the first `opensaas dev` (ADR-0063's boot reconcile carries the seeded space), CI's container installs it under `db update`, production installs it under `db migrate` from the committed space. There is no stack-run DDL and no documented hand step on the route.
- **The deployment's job narrows to provisioning.** Make the extension available on the server and either let the migrating role create it or pre-create it — which Prisma detects and skips. The privilege requirement is stated plainly in the RAG docs and beside the Database escape: pgvector is untrusted, so the migrating role needs superuser or a provider grant, and where neither is on offer a DBA runs `CREATE EXTENSION vector` once and the migration records it as satisfied. Prisma's own error stands unwrapped when the server lacks the extension; it names the space, the file and the SQL state.
- **`examples/rag-openai-chatbot/scripts/install-pgvector.ts` is deleted, not ported.** ADR-0049 kept it as the documented owner of `CREATE EXTENSION` and ADR-0056 planned its port to the raw tag. It has no job left: on the Dev database Prisma installs the extension, on an escape `db update` does, and a script running as the app role cannot install where the migration role cannot. `PGVECTOR_SETUP.md`, the example README and QUICKSTART, `docs/content/how-to/rag.md` and `docs/content/reference/rag.md` are rewritten to "make pgvector available; `pnpm db:update` enables it", and `packages/rag`'s README and CLAUDE.md drop their `CREATE EXTENSION` step.
- **The descriptor names the package; the generator derives the subpaths.** `db.extensions` becomes `[{ name: 'pgvector', from: '@prisma/orm-extension-pgvector' }]`. One declaration now needs three façades — `/pack` for the contract module, `/control` for `prisma.config.ts` and the seed phase, `/runtime` for the generated client — and Prisma's convention is that every extension publishes them. The generator appends the subpath per emission and fails `generate` naming the pack and the missing subpath when the package's `exports` lack one (Supabase's pack has no `/control` and is exactly that error today).
- **ADR-0049's emission map is restated.** One `db.extensions` entry drives: the contract module (`defineContract({ extensions: { <name> } }, …)`, importing `<from>/pack`), `prisma.config.ts` (`ormConfig({ …, extensions: [<name>] })`, importing `<from>/control`), the generated runtime client (`postgres({ …, extensions: [<name>] })`, importing `<from>/runtime`), and the extension contract space under `migrations/`. `ormConfig`'s `extensions` is required, so the map does not shrink; ADR-0049's re-verification item on it is closed.
- **The test harness seeds the same space.** ADR-0057's `createTestContext` builds the schema with the control client's `dbUpdate`, and the refusal it recorded — "refuses a pack-declaring contract without the extension's on-disk migration package" — is the loader's layout check working as designed. The harness calls the same seed phase into its own migrations directory before `dbUpdate`, from the same descriptors, so pgvector tests run on the default PGlite harness with no escape.

## Considered options

- **`opensaas db update` seeds on its first run.** Keeps `generate` free of a migrations write, but splits ownership of a derived artifact across two commands and leaves a fresh clone's `db update --dry-run` refusing until something else has run. Rejected: the artifact is a function of the declaration, and the declaration's emitter is the generator.
- **Run `prisma migration plan` and discard the app package.** The raw Prisma path, one command. Rejected: it writes an app baseline the dev loop does not want, refuses when nothing is planned, and defaults its origin to the `db` ref — three behaviours to work around for one file copy the public API does directly.
- **Leave `migration plan` to the app author** (Prisma's documented deploy-first baseline). Rejected: a project with `ragPlugin` would meet `declaredButUnmigrated` on its first `dev`, on an artifact it never asked for and could not author.
- **Generate the space at build time and keep it out of git.** Rejected: production `db migrate` reads it from disk on the deploy host, and ADR-0040 already commits the sibling artifacts for the same reason; one gitignored member of a committed set is a special case with no gain.
- **Keep the hand step as the documented primary path with Prisma's op as a safety net.** Rejected: two owners for one DDL, and the Dev database needs nobody's hand. The idempotency finding is what makes the hand step _unnecessary_ rather than _forbidden_ — a DBA who pre-creates the extension is provisioning, and the record above says so.
- **Port `install-pgvector.ts` as an escape-only helper.** Rejected: same role, same privilege, no case it covers that `db update` does not.
- **Wrap Prisma's missing-extension failure in a stack error.** Rejected: the envelope already names the failing space, the control file and `58P01`; a wrapper would restate it.

## Consequences

- **ADR-0049 is amended in place**: its `CREATE EXTENSION` consequence inverts, the descriptor's `from` becomes the package name, `extensionPacks` becomes `extensions`, and "three emissions" becomes four. **ADR-0003** loses its "writes no migration directory" premise for the dev loop and its pgvector escape reasoning (already retired by ADR-0063). **ADR-0040**'s artifact list gains the extension space. **ADR-0045**'s amendment line no longer says the extension is the deployment's job. **ADR-0056**'s port of `install-pgvector.ts` becomes a deletion, and its raw-DDL guardrail note loses its only first-party consumer. **ADR-0057**'s third re-verification item is answered: the refusal is by design and the seed phase is the fix. `CONTEXT.md`'s **Extension pack** entry is corrected and gains **Extension contract space**.
- **The consumer sweep widens.** `packages/cli/src/commands/generate.ts` gains the seed call and the dirty-tree check covers `migrations/<space>/**` and the space's snapshot; the root `.gitignore`'s `prisma/migrations/` line goes, since `migrations/` is a committed directory under Prisma 8 — the `db` ref included, per Prisma's own model; `ragPlugin`'s `addExtension` passes the package name; the descriptor-to-subpath resolution and its generate-time error land beside ADR-0049's missing-pack error; `install-pgvector.ts` and `PGVECTOR_SETUP.md` are deleted and the RAG how-to, reference, example README/QUICKSTART and `packages/rag` docs rewrite their pgvector section to provisioning; ADR-0057's harness seeds the space; the deploy guide gains the privilege paragraph beside the Database escape.
- **Two riders, recorded for whoever hits them.** The `rc.12` CLI blocks when spawned with a piped-but-unwritten stdin even under `--no-interactive` (`stdio: ['ignore', …]` or `--json` with stdin closed is the working shape — `opensaas dev`'s spawn should use it). And the seed phase is `@prisma/orm-toolchain`'s public control API, but the toolchain is pinned at `rc.8` behind an `rc.12` CLI: re-verify the export at GA alongside the map's other CLI-dependent conclusions.
- **Numbered 0065.** 0063 and 0064 were merged from [#1095](https://github.com/OpenSaasAU/stack/issues/1095) and [#1097](https://github.com/OpenSaasAU/stack/issues/1097) while this ticket was open; no open `claude/wayfinder-*` branch claimed a later number at push time.
